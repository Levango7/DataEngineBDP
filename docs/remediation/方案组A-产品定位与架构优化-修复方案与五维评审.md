## 一、高严重度（1个）

### 问题1：过度设计——15个骨架组件
- **严重程度**：高
- **问题描述**：45个组件中15个为骨架/Mock（component-maturity.md §三），AI层8个骨架（vector-engine/llm-gateway/llmops/ml-platform/knowledge-engine/model-finetuning/registry/llm-gateway-evaluation），多集群联邦3个全骨架（karmada-api/failover/federated-query）。在80%完成度下铺面过广，维护负担与交付信心倒挂。
- **修复方案**：
  1. **冻结骨架组件扩展**：在 ROADMAP.md 新增"骨架冻结期"章节，v2.1~v2.2 周期内不再新增骨架组件，现有15个骨架组件标记为 `frozen-until-mvp`。
  2. **分类处置**：
     - **优先激活**（有真实需求）：knowledge-engine（RAG 链路）、llm-gateway（AI 入口）→ v2.2 切真实实现
     - **合并降维**：karmada 三子模块合并为单一 `karmada-federation` 组件（见问题14）；llm-gateway-evaluation 并入 llm-gateway
     - **降级为规划**：model-finetuning/registry/knative → 从 platform/ 移至 `design/planned/` 目录，从构建矩阵剔除
     - **保留骨架**：industry-templates（模板资产天然骨架）、vector-engine（Milvus 已接，默认 Mock 合理）
  3. **更新 component-maturity.md**：新增"处置决策"列，标注每个骨架组件的去留决策与目标版本。
  4. **CI 调整**：`.github/workflows/ci.yml` 中为降级为规划的组件移除构建 job，减少 CI 资源消耗。
- **成本性**：3/5 — 需整理13个组件的处置决策、移动文件、更新CI/矩阵/ROADMAP，约0.5-1人月
- **风险性**：2/5 — 冻结和降级为规划不影响现有功能；合并 karmada 需调整引用，风险可控
- **收益性**：5/5 — 直接降低维护负担、CI 时间、认知复杂度，提升交付信心；是后续所有优化的前提
- **兼容性**：4/5 — 降级为规划的组件从 platform/ 移出，已有引用需更新路径（少量）；API 契约不变
- **可持续性**：5/5 — 建立"骨架冻结→按需激活"机制，避免再次过度铺面
- **五维总分**：19/25
- **评审结论**：✅ 推荐做

### 问题3：SaaS与私有化定位矛盾
- **严重程度**：中
- **问题描述**：设计原则"K8s在客户机器上自建"（§2.2）与L5"多租户数据云SaaS"定位存在矛盾——自建K8s面向私有化，SaaS面向公有云托管，两者交付模式冲突。
- **修复方案**：
  1. **在产品原型设计 v0.4 §2 新增"交付模式澄清"小节**：
     - **私有化交付（主模式）**：K8s在客户机器自建，多租户面向"客户内部多业务线"，非对外SaaS
     - **托管SaaS（可选模式，v2.3+）**：由平台运营方在自有集群上提供托管多租户，K8s对租户透明
     - 明确两者共享同一代码库，通过 `DELIVERY_MODE=private|saas` Profile 切换
  2. **在 §1.4 "对内+对外"小节补充**：对外交付以"私有化+年度订阅"为主，SaaS托管为远期可选。
  3. **在 design/ 新增 `交付模式决策_ADR.md`**：记录私有化 vs SaaS 的决策依据、共存机制、切换方案。
  4. **检查 L5 层组件**：open-api-catalog/asset-exchange 的定位调整为"私有化下的内部资产流通"，非对外SaaS计费。
- **成本性**：2/5 — 文档调整 + 少量配置项设计，约3-5人天
- **风险性**：2/5 — 澄清定位不影响现有实现；若后续选择SaaS需额外开发，但当前不触发
- **收益性**：4/5 — 消除定位矛盾，避免团队在两种模式间摇摆；明确主交付模式降低复杂度
- **兼容性**：5/5 — 不改变代码，仅澄清语义
- **可持续性**：4/5 — 交付模式决策长期有效，但SaaS模式若启动需复审
- **五维总分**：17/25
- **评审结论**：✅ 推荐做

### 问题4：出账闭环未实现
- **严重程度**：中
- **问题描述**：FinOps（服务级，成本归集依赖真实Prometheus）、asset-exchange（SQLite级）、open-api-catalog（AK/SK计量已实现）三者成熟度不足，出账→结算→分账闭环未端到端跑通。
- **修复方案**：
  1. **分阶段实施**（与五维评审批次5 P-03 对齐）：
     - **阶段1（v2.2）出账**：finops/cost-model 接入真实 Prometheus 指标采集（已有 PrometheusQueryClient），产出租户级成本账单 JSON。在 finops/ 新增 `billing/` 子模块，实现账单生成器。
     - **阶段2（v2.2）结算**：asset-exchange 补充结算接口（已有发布/订阅/结算仓储接口），对接 finops 账单数据。
     - **阶段3（v2.3）分账**：open-api-catalog 的 AK/SK 计量数据汇入 finops，实现按 API 调用量分账。
  2. **在 docs/ 新增 `出账闭环设计_v1.0.md`**：绘制出账→结算→分账数据流，明确三组件接口契约。
  3. **在 finops/README.md 新增"闭环状态"小节**：标注当前 2/3 环节就绪，分账待 v2.3。
  4. **测试**：新增 `tests/integration/test_billing_closed_loop.py`，验证 finops→asset-exchange→open-api-catalog 数据流。
- **成本性**：4/5 — 需实现账单生成器、补结算接口、集成测试，约2-3人月
- **风险性**：3/5 — 涉及金额计算，精度与一致性风险；依赖真实 Prometheus 环境
- **收益性**：4/5 — 商业化闭环关键能力，落地后支撑计费运营
- **兼容性**：4/5 — 新增接口不影响现有功能；finops API 扩展向后兼容
- **可持续性**：4/5 — 出账闭环是长期运营基础，但计费规则变更需维护
- **五维总分**：19/25
- **评审结论**：✅ 推荐做（分阶段，v2.2 先出账+结算）

### 问题6：rule-engine职责过载
- **严重程度**：中
- **问题描述**：rule-engine/README.md 明确同时负责 DQ（数据质量）+ MASK（数据脱敏）+ ALERT（告警）三项职责，单一组件承载三类治理逻辑，耦合度高。
- **修复方案**：
  1. **短期（v2.2）保持现状，补充隔离**：
     - 在 rule-engine 源码中确保 DQ/MASK/ALERT 三类规则的执行器（DqRuleExecutor/MaskRuleExecutor/AlertRuleExecutor）完全隔离，无共享可变状态
     - 新增架构守护测试：验证三类规则执行互不影响
  2. **中期（v2.3）评估拆分**：
     - 若 MASK 脱敏逻辑复杂度增长（如需动态策略、国密集成），将 MASK 拆为独立 `mask-engine` 组件
     - ALERT 若与监控告警闭环深度耦合，拆入 `observability` 或 `alert-manager`
     - DQ 保留在 rule-engine（与 dqctl CLI 协同）
  3. **在 rule-engine/README.md 新增"职责边界与演进规划"小节**：明确三项职责的隔离机制与拆分条件。
  4. **在 design/ 新增 ADR `rule-engine职责演进决策.md`**：记录保持 vs 拆分的决策依据与触发条件。
- **成本性**：2/5 — 短期隔离测试约3-5人天；中期拆分约1-2人月（按需触发）
- **风险性**：2/5 — 短期隔离不改变功能；中期拆分需调整 dqctl 调用，风险可控
- **收益性**：3/5 — 隔离降低耦合风险；拆分收益取决于脱敏/告警复杂度增长
- **兼容性**：4/5 — 短期 API 不变；中期拆分需保持 API 兼容（路由转发）
- **可持续性**：4/5 — 明确演进路径，避免职责继续膨胀
- **五维总分**：15/25
- **评审结论**：✅ 推荐做（短期隔离优先，拆分按需）

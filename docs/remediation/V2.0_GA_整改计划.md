## 2. P0 级问题 — 必须立即处理（第1周止血）

### R-001 硬编码JWT/密钥已入git历史

| 属性 | 值 |
|------|-----|
| **优先级** | P0 — 安全泄露 |
| **工作量** | 3人天 |
| **责任角色** | 安全合规工程师 + 后端工程师 |
| **当前状态** | 4处硬编码密钥已进入git历史 |

#### 问题描述

以下4处硬编码凭据已进入git历史，视为已泄露：

1. **Go服务兜底密钥**（3处）：
   - `platform/catalog/internal/auth/auth.go` — JWT签名密钥硬编码
   - `platform/llm-gateway/internal/auth/auth.go` — JWT签名密钥硬编码
   - `platform/observability/internal/auth/auth.go` — JWT签名密钥硬编码

2. **裸金属配置**（1处）：
   - `design/deploy/services/baremetal/config.yaml` — JWT密钥 + DSN密码 + `insecure_skip_verify: true`

#### 整改措施

**步骤1：密钥轮换（0.5人天）**
- 生成新的JWT签名密钥（每个服务独立密钥）
- 生成新的数据库DSN密码
- 在密钥管理系统（KMS/HSM）中注册新密钥

**步骤2：代码改造为fail-fast环境变量（1人天）**
- 参照 `design/deploy/services/operations/main.py` 的 `ADMIN_TOKEN` 模式（正例）
- 每个服务的 `auth.go` 启动时从环境变量读取密钥，缺失则 panic
- `config.yaml` 中的密钥字段改为 `${ENV_VAR}` 引用

```go
// 改造前（错误）
var jwtSecret = []byte("change-me-hardcoded-secret")

// 改造后（正确）
var jwtSecret = []byte(mustGetenv("JWT_SIGNING_KEY"))

func mustGetenv(key string) string {
    v := os.Getenv(key)
    if v == "" {
        log.Fatalf("FATAL: environment variable %s is required", key)
    }
    return v
}
```

**步骤3：git历史清理（1人天）**
- 使用 `git filter-repo` 清除历史中的密钥字符串
- 注意：此操作会重写历史，需协调所有clone方重新拉取
- 替代方案：在密钥管理系统中标记旧密钥为"已泄露/已废弃"，确保旧密钥不可用

**步骤4：CI加gitleaks阻断（0.5人天）**
- 在 `.github/workflows/ci.yml` 中添加 gitleaks 扫描步骤
- 设置为阻断式（非警告式）

```yaml
# CI gitleaks 配置
- name: Gitleaks Scan
  uses: gitleaks/gitleaks-action@v2
  env:
    GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  # 默认阻断式，发现泄露即失败
```

#### 验收标准
- [ ] `grep -r "change-me" platform/` 返回零结果
- [ ] `grep -r "hardcoded" platform/` 返回零结果
- [ ] 4个服务无 `JWT_SECRET` 环境变量时启动 panic
- [ ] CI gitleaks 扫描通过
- [ ] 旧密钥在KMS中标记为废弃

### R-002 60/60 Helm chart lint全失败

| 属性 | 值 |
|------|-----|
| **优先级** | P0 — 部署完全不可用 |
| **工作量** | 5人天 |
| **责任角色** | DevOps工程师 + 后端工程师 |

#### 问题描述

- `design/deploy/charts/` 下60个Helm chart实测 **60/60 全部 `helm lint` 失败**
- 根因：`_helpers.tpl` 模板换行bug导致labels字符串粘连，渲染出非法YAML
- 雪上加霜：spark/trino/doris的deployment.yaml逐字节相同（克隆骨架未差异化）
- values覆盖仅13/60，47个chart缺少组件级values

#### 整改措施

**步骤1：修复 _helpers.tpl 换行bug（1人天）**
- 定位 `_helpers.tpl` 中 labels 模板的换行问题
- 修复后验证：`helm lint design/deploy/charts/<任意chart>` 通过

```yaml
# 修复前（bug示例）
{{- define "labels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}app.kubernetes.io/instance: {{ .Release.Name }}
{{- end -}}

# 修复后
{{- define "labels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end -}}
```

**步骤2：差异化克隆骨架chart（2人天）**
- 逐个检查spark/trino/doris等组件的deployment.yaml
- 为每个组件填充正确的镜像、端口、环境变量、资源限制
- 确保无两个chart的deployment.yaml完全相同

**步骤3：补齐47个chart的values.yaml（1.5人天）**
- 为缺少values的47个chart创建组件级values.yaml
- 参照 `design/deploy/values/` 下已有的13个values模板
- 每个values包含：image、replicas、resources、env、persistence

**步骤4：全量helm lint验证（0.5人天）**
- 编写验证脚本：遍历60个chart执行 `helm lint`
- 目标：60/60 通过

```bash
#!/bin/bash
# helm-lint-all.sh
CHARTS_DIR="design/deploy/charts"
FAIL=0
for chart in "$CHARTS_DIR"/*/; do
  if ! helm lint "$chart" > /dev/null 2>&1; then
    echo "FAIL: $chart"
    FAIL=$((FAIL+1))
  fi
done
echo "Result: $((60-FAIL))/60 charts passed"
exit $FAIL
```

#### 验收标准
- [ ] `helm lint design/deploy/charts/*` 60/60通过
- [ ] 无两个chart的deployment.yaml完全相同
- [ ] 60个chart均有组件级values.yaml
- [ ] 至少3个chart可 `helm install --dry-run` 通过

## 8. 风险与注意事项

### 8.1 git历史重写风险

R-001和R-007涉及git历史修改：
- `git filter-repo` 会重写历史，所有clone方需重新拉取
- 建议在低峰期执行，提前通知所有协作者
- 备选方案：不重写历史，仅在KMS中废弃旧密钥

### 8.2 方案选择风险

R-009和R-010各有方案A（补实现）和方案B（改口径）：
- 方案A工作量大（各5人天）但保持宣称一致性
- 方案B工作量小（各1人天）但降低产品能力声明
- **建议**：先执行方案B止血，后续迭代再补方案A

### 8.3 CI修复后的连锁反应

R-003修复CI门禁后，可能暴露更多隐藏的测试失败：
- 建议先修复R-004（asset-exchange）再启用CI阻断
- 预留1-2天处理CI启用后新发现的失败

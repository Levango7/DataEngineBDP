## P-01: 多集群联邦异地机房场景落地

### 现状核实

| 子模块 | 代码现状 | 缺口 |
|--------|----------|------|
| karmada-api | SQLite 持久化策略元数据（骨架）；注释明确"生产环境通过 controller-runtime client 写入 Karmada 控制面" | 未接 Karmada 控制面 API 写入，策略只存本地 DB |
| failover-engine | 已初始化 Karmada 客户端 + Prometheus 客户端（代码骨架完整）；健康检查器 + 副本权重分配器 + 故障迁移管理器均已接线 | 事件持久化注释写"生产环境：持久化到 FailoverEvent 表"——未实现；PROMETHEUS_URL 未配置时只用 karmada API |
| federated-query | RealClusterMetadataProvider 通过 Karmada REST API 获取联邦集群列表 + Catalog API 拉取元数据；有 mTLS 配置 | 代码层面已接真实多集群，但未在真实异地机房环境端到端验证 |

**结论**：federated-query 代码骨架最完整；karmada-api 缺控制面写入；failover-engine 缺事件持久化。整体未在异地机房真实验证。

### 五维评审

#### 风险性：高
- **技术风险**：Karmada 控制面 API 版本兼容性（v1alpha1 可能变更）；异地机房网络分区下的脑裂风险
- **运维风险**：多集群故障迁移涉及生产工作负载搬迁，误触发可能导致服务中断
- **缓解措施**：先在 staging 双集群验证，failover 策略默认 enabled=false，手动触发首次迁移

#### 收益性：高
- 用户明确强调"大数据会涉及异地机房场景，这是关键需求"
- 企业版核心卖点：异地容灾 + 联邦查询是政企客户刚需
- 落地后可直接支撑金融/政府行业的异地双活/三活方案

#### 成本性：高（3-4 人月）
- karmada-api 接控制面写入：0.5 人月
- failover 事件持久化 + Prometheus 指标接入：0.5 人月
- 异地机房端到端验证（含网络配置、mTLS、脑裂处理）：2-3 人月
- **降低成本策略**：先接一个 Karmada 控制面（非全部），先验证 federated-query（已有代码基础）

#### 兼容性：中
- karmada-api 从 SQLite 切换到控制面写入，API 层不变（REST 接口相同），对前端无影响
- failover-engine 事件持久化新增表，不影响现有功能
- **风险**：Karmada 控制面不可达时的降级策略需明确（回退到本地 DB 还是拒绝写入）

#### 持续性：高
- Karmada 是 CNCF 孵化项目，社区活跃，长期维护有保障
- 建议建立"联邦能力成熟度"迭代计划：L1 单集群 → L2 多集群只读 → L3 多集群读写 → L4 自动 failover → L5 异地双活

### 分阶段实施建议

| 阶段 | 内容 | 成本 | 里程碑 |
|------|------|------|--------|
| 阶段1 | federated-query 在 staging 双集群端到端验证（已有代码） | 0.5 人月 | 联邦查询可用 |
| 阶段2 | karmada-api 接控制面写入 + failover 事件持久化 | 1 人月 | 策略同步到控制面 |
| 阶段3 | failover 接 Prometheus 指标 + 自动迁移验证 | 1 人月 | 自动 failover 可用 |
| 阶段4 | 异地机房全链路验证（网络/mTLS/脑裂） | 1-1.5 人月 | 异地双活验收 |

## P-03: 商业化定价落地

### 现状核实

| 能力 | 代码现状 | 缺口 |
|------|----------|------|
| 计量 | MeteringController 接收 sql-gateway 查询计量，幂等防重 | ✅ 已实现 |
| 定价 | PricingController 动态单价配置（ON_DEMAND/RESERVED/TIERED） | ✅ 已实现 |
| 成本计算 | CostController 成本计算与报告 | ✅ 已实现 |
| 账单聚合 | BillingAggregatorService 按租户/日期窗口聚合账单 + 按日趋势 | ✅ 已实现 |
| 账单导出 | BillExportController CSV/Excel 导出 | ✅ 已实现 |
| 分账 | AllocationController 分账配置管理 + 执行；AllocationService 按比例分账 | ✅ 已实现（配置+执行） |
| **出账** | 无周期账单汇总→生成正式账单→推送客户的流程 | ❌ 未实现 |
| **支付** | 无支付网关对接代码（搜索 payment/gateway 无结果） | ❌ 未实现 |
| **分账后半段** | 分账执行有，但分账结果→各子空间账单→通知未闭环 | ❌ 部分缺失 |

**结论**：前半段（计量→定价→成本→账单聚合→导出）完整；后半段（出账→支付→分账通知）缺失。

### 五维评审

#### 风险性：高
- **财务风险**：出账/支付涉及真金白银，计算错误直接导致客户投诉或收入损失
- **合规风险**：支付网关对接需 PCI DSS 合规，分账涉及多方结算
- **缓解措施**：出账先走"账单生成+人工审核+邮件推送"，支付先对接一个网关（如 Stripe），分账先记账不自动划款

#### 收益性：高
- 商业化闭环是 SaaS 产品的生命线，没有支付就没有收入
- 企业版面向政企客户，出账→支付→分账闭环是签约前提
- 分账能力是多工作空间组织架构的刚需

#### 成本性：高（3-4 人月）
- 周期账单汇总 + 出账流程（定时任务→生成账单→推送）：1 人月
- 支付网关对接（选型+集成+回调处理+对账）：1.5 人月
- 分账后半段闭环（分账结果→子空间账单→通知）：0.5 人月
- 财务对账 + 审计日志：0.5-1 人月
- **降低成本策略**：先出账（不接支付），支付先对接一个网关，分账先记账不划款

#### 兼容性：中
- 出账新增定时任务和账单表，不影响现有计量/定价/查询
- 支付网关对接为新增模块，不影响现有功能
- **风险**：账单格式变更可能影响已对接的 BI 报表

#### 持续性：高
- 商业化能力需持续迭代（多支付渠道、发票合规、税务计算）
- 建议建立"商业化成熟度"迭代：L1 计量 → L2 出账 → L3 支付 → L4 分账 → L5 发票/税务

### 分阶段实施建议

| 阶段 | 内容 | 成本 | 里程碑 |
|------|------|------|--------|
| 阶段1 | 周期账单汇总 + 出账流程（生成→审核→推送） | 1 人月 | 月度账单自动生成 |
| 阶段2 | 支付网关对接（选一个：Stripe/支付宝） | 1.5 人月 | 在线支付可用 |
| 阶段3 | 分账后半段闭环 + 通知 | 0.5 人月 | 分账结果可查 |
| 阶段4 | 财务对账 + 审计日志 + 发票 | 1 人月 | 商业化闭环验收 |

- **降低成本策略**：复用 asset-exchange 的 DeliveryStatus 状态机模式，先实体后编排

#### 兼容性：高
- 新增合同实体和交付流程，不影响现有功能

- **风险**：低，纯新增

#### 持续性：中

- **技术风险**：不同环境（信创 CPU/公有云 K8s 版本/私有云网络）兼容性问题未知
- **缓解措施**：先在 staging 环境验证（一个环境通过好过零个），逐步扩展

#### 收益性：高
- "四环境零改动交付"是企业版核心承诺，实测后可直接作为销售凭证
- 信创环境支持是政企/政府客户硬性门槛
- 每多验证一个环境，打开一个细分市场

#### 成本性：中（1-2 人月）
- 编写四环境部署验证脚本（参数化部署配置）：0.5 人月
- staging 环境验证（复用 K3s 配置）：0.2 人月
- 公有云验证（需云账号 + 集群）：0.5 人月
- 信创验证（需信创环境——**最大瓶颈**）：0.5-1 人月
- **降低成本策略**：先 staging + 公有云（有资源），信创待客户环境验证

#### 兼容性：高
- 新增部署配置和验证脚本，不修改现有代码
- 参数化部署配置（values-{env}.yaml）不影响现有 K3s/local 配置

#### 持续性：高
- 四环境验证纳入 CI 后长期保障交付质量
- 建议建立"环境交付矩阵"持续更新：每发版验证四环境

## 评审结论

6 个产品策略问题均为**高成本高收益**的旗舰功能落地问题。核心策略是：

4. **持续性规划**：建立成熟度矩阵，季度迭代，CI 集成防回归

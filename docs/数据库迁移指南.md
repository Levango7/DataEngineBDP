# 数据库迁移指南

> 适用范围：`platform/` 下所有含 JPA 实体的 Java 模块（17 个）。
> 背景：生产 profile 统一 `spring.jpa.hibernate.ddl-auto: validate`（只校验不改表），
> 因此**必须**由迁移工具负责建表。本仓在 v2.1.0-RC 之前既无迁移框架也无任何 DDL，
> 等于"生产环境没人建表"。现由 Flyway 承担，机制与闸门均已落地。

## 1. 现状

| 项 | 状态 |
| --- | --- |
| 迁移工具 | Flyway（版本由 `spring-boot-dependencies` 管理，当前 12.4.0） |
| 已接入模块 | `platform/encaps-layer`（20 表）、`platform/finops/billing`（1 表） |
| 待补模块 | 15 个，见 [docs/db-migration-backlog.yaml](db-migration-backlog.yaml) |
| 防回归闸门 | `scripts/check-db-migration-coverage.py`（已挂 CI） |
| 基线生成器 | `scripts/gen-db-baseline.sh <模块目录>` |

## 2. 为什么一个库多 schema

所有 Java 服务的 `DB_URL` 默认都指向同一个 PostgreSQL 库 `shuqing`。若各自 Flyway
直接建到 `public`，会互相撞表名（例如 encaps-layer 与 encaps-tenant 都有租户表）。
约定：**每服务独立 schema**，服务间不跨 schema 读写。

```yaml
# application-prod.yml 模板
spring:
  datasource:
    url: ${DB_URL:jdbc:postgresql://postgresql:5432/shuqing?currentSchema=<service>}
  flyway:
    enabled: true
    schemas: ${FLYWAY_SCHEMA:<service>}   # 闸门会检查这一项，缺了会 FAIL
    create-schemas: true
    baseline-on-migrate: false
    locations: classpath:db/migration
  jpa:
    hibernate:
      ddl-auto: validate
```

`application.yml`（dev 默认）保持 `spring.flyway.enabled: ${FLYWAY_ENABLED:false}`：
基线脚本是 PostgreSQL 方言（含 `oid`、`timestamptz`），**不能在 H2 上执行**，
所以 dev 仍走 H2 + `ddl-auto: update` 的零配置路径。

## 3. 为一个模块接入迁移

```bash
export JAVA_HOME=<JDK17 路径>        # 本仓 mvn 默认可能落在 JDK 8
bash scripts/gen-db-baseline.sh platform/sql-gateway
# 再按 §2 模板补 pom 依赖与 application-prod.yml，并从 backlog 清单删除该模块
python scripts/check-db-migration-coverage.py
```

pom 需要三个依赖（版本都由 BOM 管理，不要写死）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-flyway</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

后续结构变更：**不要改** `V1__baseline.sql`（Flyway 校验已应用脚本的 checksum），
新增 `V2__xxx.sql`。

## 4. 基线脚本怎么来的（以及为什么不能手写）

`gen-db-baseline.sh` 启动模块的 Spring 上下文，用 Hibernate 的 schema-generation
能力把实体模型按 PostgreSQLDialect 导出为 DDL 文件（不连真实库、不建表）：

```
-Dspring.jpa.properties.hibernate.dialect=org.hibernate.dialect.PostgreSQLDialect
-Dspring.jpa.properties.jakarta.persistence.schema-generation.scripts.action=create
-Dspring.jpa.properties.jakarta.persistence.schema-generation.scripts.create-target=target/baseline-postgres.sql
```

手写 DDL 会漏字段/漏精度（`numeric(18,4)`、`timestamptz`、`@Lob → oid`），
而 prod 是 `validate` —— 差一个字段就启动失败。

## 5. Spring Boot 4 的三个坑（本轮实测踩过，务必注意）

1. **只加 `flyway-core` 不会执行迁移。** Boot 4 把 Flyway 自动装配拆到了
   `spring-boot-flyway` 模块。缺失时的症状：Hibernate 抢在建表前 validate，报
   `Schema validation: missing table [...]`，看起来像"迁移没跑"，实际是自动装配没生效。
2. **`spring.jackson.serialization.write-dates-as-timestamps` 已失效。** Boot 4 用
   Jackson 3（包名 `tools.jackson`），该键无对应枚举，会导致属性绑定失败、
   **应用在任何 profile 下都起不来**。Jackson 3 默认就输出 ISO-8601，删掉即可。
3. **请求 DTO 里的原始类型字段，客户端省略即绑定失败。** Jackson 3 默认
   `FAIL_ON_NULL_FOR_PRIMITIVES`，`private boolean overwrite;` 在请求体不带该字段时报
   `Cannot map null into type boolean`。DTO 一律用包装类型（`Boolean`）+ null 安全访问器。

## 6. 已验证到什么程度

`platform/finops/billing` 用真实 PostgreSQL 16.15 完整跑通：Flyway 建 schema+表 →
Hibernate validate 通过 → 应用启动 → `POST /api/finops/v1/billing/generate` 返回 201
且账单落库。其余模块的基线尚未生成，因此**尚未**做同等验证，请以 §3 步骤逐个补齐。

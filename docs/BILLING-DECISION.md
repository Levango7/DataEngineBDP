# 计费与商业化决断方案

> 状态：**待决策** ｜ 评估日期：2026-09-01 ｜ 决策人：产品负责人
>
> 背景：L5 产品层的资产流通（asset-exchange）与 API 目录（open-api-catalog）
> 已有计量数据采集（AK/SK 计量、订阅/结算仓储、SQLite 存储），但
> "计费→出账→支付→分账"商业闭环从未决断技术路线。本文给出两个可选方案、
> 成本/风险对比与建议，**供决策后立项实施**。

**结论：计量层已就绪，缺的是从"计量数据"到"能收到钱"的后半段。**

## 二、方案 A：轻量内建（自研计费最小闭环）

**范围**：周期账单汇总引擎 + 简易对账单（线下转账/对公）+ 管理端账单页。

- 出账：按租户+周期（月/日）从计量表汇总生成账单实体，状态机（草稿→确认→已支付→关闭）
- 支付：不做在线支付网关——账单邮件导出 + 线下对公转账 + 管理员手工核销
- 分账：平台/租户两级固定比例，无多方分润

**成本估算**：1 人月（后端账单引擎 + 管理端页面 + 测试）
**适用**：客户数 < 50、企业间结算为主（政企/私有化交付场景天然线下付款）
**风险**：低——纯内逻辑，无外部依赖

## 方案 B：完整商业化（对接支付+分账）

**范围**：方案 A + 在线支付网关（微信支付/支付宝企业）+ 多方分润 + 发票对接。

**成本估算**：3~4 人月 + 支付通道资质申请（营业执照/ICP/银行账户，周期 1~2 个月）+ 每笔 0.6% 通道费
**适用**：SaaS 公有云多租户、自助付费客户
**风险**：
- 支付资质与合规（资金流涉及二清风险，需持牌或服务商模式——法律咨询前置）
- 分账引擎复杂度（多方分润规则引擎是独立产品级工程）

## 三、建议

**推荐方案 A 先行**，理由：

1. 当前产品主推**私有化交付**（信创/本地/私有云），客户为政企——付款方式天然对公线下，方案 A 已满足
2. 公有云 SaaS 自助付费的客户数当前为零，方案 B 的投入无收入承接
3. 方案 A 是方案 B 的子集：账单引擎/状态机可完全复用，后做 B 不推翻 A

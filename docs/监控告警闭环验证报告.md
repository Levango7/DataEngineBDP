## 1. 概述

本报告记录 DataEngineBDP 平台监控告警闭环的完整设计、验证清单与当前状态。
告警闭环指：**指标采集 → 规则评估 → 告警触发 → 路由分发 → 通知送达 → 人工响应 → 恢复确认** 的全链路。

### 1.1 告警体系架构

```
┌─────────────┐    ┌──────────────┐    ┌───────────────┐    ┌─────────────┐
│  Prometheus  │───→│ Alertmanager │───→│  通知渠道      │───→│  值班响应    │
│  (规则评估)  │    │  (路由/抑制)  │    │  (PD/邮件/IM) │    │  (SOP/Runbook)│
└─────────────┘    └──────────────┘    └───────────────┘    └─────────────┘
       ↑                                        │
       │                                        ↓
┌─────────────┐                          ┌─────────────┐
│  node-exporter│                          │  Grafana     │
│  kube-state   │                          │  (可视化)    │
│  service-metrics│                        └─────────────┘
└─────────────┘
```

### 1.2 告警分级体系

| 级别 | severity label | 通知渠道 | 时效要求 | 重复间隔 | 典型场景 |
|------|---------------|----------|----------|----------|----------|
| 严重 | `critical` | PagerDuty + 邮件 | 7x24 立即 | 5 分钟 | 服务宕机、资源耗尽、DB 连接池满 |
| 重要 | `warning` | 邮件 | 30 秒聚合 | 30 分钟 | 资源水位高、连接失败率高 |
| 一般 | `info` | Slack | 1 分钟聚合 | 4 小时 | 容量提醒、配置变更 |

> **与现有 P0/P1/P2 体系的关系**：现有 `platform/observability/rules/` 采用 P0/P1/P2 三级（电话/邮件/钉钉），
> 本批次新增 `alert-rules/` 采用 critical/warning/info 三级（PagerDuty/邮件/Slack），作为 CRD 化部署的补充。
> 两套体系通过 namespace/label 隔离可并存，生产环境按需选用。

- warning 触发时抑制同源的 info

## 3. 响应 SOP（标准操作流程）

### 3.1 critical 告警响应 SOP

| 步骤 | 操作 | 负责人 | 时限 |
|------|------|--------|------|
| 1 | PagerDuty/邮件收到告警，确认告警内容 | 值班工程师 | 立即 |
| 2 | 查看 runbook_url 链接的处置手册 | 值班工程师 | 5 分钟内 |
| 3 | 登录 Grafana 对应 Dashboard 查看指标趋势 | 值班工程师 | 5 分钟内 |
| 4 | 初步定位故障原因，执行应急处置 | 值班工程师 | 15 分钟内 |
| 5 | 在 PagerDuty/IM 群同步处置进展 | 值班工程师 | 每 30 分钟 |
| 6 | 故障恢复后确认告警已 resolve | 值班工程师 | 恢复后立即 |
| 7 | 编写故障复盘报告（如影响 > 30 分钟） | 值班工程师 + 负责人 | 24 小时内 |

### 3.2 warning 告警响应 SOP

| 步骤 | 操作 | 负责人 | 时限 |
|------|------|--------|------|
| 1 | 邮件收到告警，确认告警内容 | 负责工程师 | 30 分钟内 |
| 2 | 查看 runbook_url 处置手册 | 负责工程师 | 1 小时内 |
| 3 | 评估是否需要立即处理或可排期处理 | 负责工程师 | 1 小时内 |
| 4 | 执行处置或创建工单排期 | 负责工程师 | 视紧急度 |
| 5 | 确认告警 resolve | 负责工程师 | 处置后 |

### 3.3 info 告警响应 SOP

| 步骤 | 操作 | 负责人 | 时限 |
|------|------|--------|------|
| 1 | Slack #alerts-info 频道收到通知 | 相关工程师 | 工作时间 |
| 2 | 知悉并评估是否需要关注 | 相关工程师 | 工作时间 |
| 3 | 如需处理则创建工单 | 相关工程师 | 视情况 |

## 5. 部署步骤

### 5.1 部署告警规则

```bash
# 1. 语法预检（dry-run）
kubectl apply --dry-run=client -f platform/observability/alert-rules/service-down-alerts.yaml -n monitoring
kubectl apply --dry-run=client -f platform/observability/alert-rules/resource-threshold-alerts.yaml -n monitoring
kubectl apply --dry-run=client -f platform/observability/alert-rules/db-connection-alerts.yaml -n monitoring
kubectl apply --dry-run=client -f platform/observability/alert-rules/alert-routing.yaml -n monitoring

# 2. 正式部署
kubectl apply -f platform/observability/alert-rules/service-down-alerts.yaml -n monitoring
kubectl apply -f platform/observability/alert-rules/resource-threshold-alerts.yaml -n monitoring
kubectl apply -f platform/observability/alert-rules/db-connection-alerts.yaml -n monitoring
kubectl apply -f platform/observability/alert-rules/alert-routing.yaml -n monitoring

# 3. 验证规则已加载
kubectl get prometheusrule -n monitoring
```

### 5.2 验证规则评估

```bash
# 检查 Prometheus 是否加载了规则（通过 port-forward 访问 Prometheus UI）
kubectl port-forward -n monitoring svc/prometheus-operated 9090:9090

# 浏览器访问 http://localhost:9090/rules 确认规则可见
# 浏览器访问 http://localhost:9090/alerts 确认告警状态
```

### 5.3 端到端闭环测试

```bash
# 1. 人为制造服务不可达（在 dev 环境测试）
kubectl scale deployment encaps-layer -n dataengine-dev --replicas=0

# 2. 等待 5 分钟，确认 EncapsLayerDown 告警触发
# 3. 确认 PagerDuty/邮件收到 critical 告警通知
# 4. 恢复服务
kubectl scale deployment encaps-layer -n dataengine-dev --replicas=1

# 5. 确认收到 resolve 通知
```

### 6.3 并存策略

- **现有 P0/P1/P2 体系**：适用于裸 Prometheus + Alertmanager 部署（ConfigMap 挂载方式）
- **新增 critical/warning/info 体系**：适用于 kube-prometheus-stack CRD 化部署
- 两套体系通过 **Prometheus label `prometheus`** 和 **namespace** 隔离，可并存于同一集群
- 生产环境建议统一为一套，避免告警重复

## 1. 概述

本报告记录 DataEngineBDP 平台监控告警闭环的完整设计、验证清单与当前状态。
告警闭环指：**指标采集 → 规则评估 → 告警触发 → 路由分发 → 通知送达 → 人工响应 → 恢复确认** 的全链路。

### 1.1 告警体系架构

```
┌─────────────┐    ┌──────────────┐    ┌───────────────┐    ┌─────────────┐
│  Prometheus  │───→│ Alertmanager │───→│  通知渠道      │───→│  值班响应    │
│  (规则评估)  │    │  (路由/抑制)  │    │  (PD/邮件/IM) │    │  (SOP/Runbook)│
└─────────────┘    └──────────────┘    └───────────────┘    └─────────────┘
       ↑                                        │
       │                                        ↓
┌─────────────┐                          ┌─────────────┐
│  node-exporter│                          │  Grafana     │
│  kube-state   │                          │  (可视化)    │
│  service-metrics│                        └─────────────┘
└─────────────┘
```

### 1.2 告警分级体系

| 级别 | severity label | 通知渠道 | 时效要求 | 重复间隔 | 典型场景 |
|------|---------------|----------|----------|----------|----------|
| 严重 | `critical` | PagerDuty + 邮件 | 7x24 立即 | 5 分钟 | 服务宕机、资源耗尽、DB 连接池满 |
| 重要 | `warning` | 邮件 | 30 秒聚合 | 30 分钟 | 资源水位高、连接失败率高 |
| 一般 | `info` | Slack | 1 分钟聚合 | 4 小时 | 容量提醒、配置变更 |

> **与现有 P0/P1/P2 体系的关系**：现有 `platform/observability/rules/` 采用 P0/P1/P2 三级（电话/邮件/钉钉），
> 现行只有一套体系（P0/P1/P2 + `pending/`），配 `platform/observability/alertmanager/` 路由；
> v1.0 设想的 `alert-rules/`（critical/warning/info + PagerDuty/Slack）从未落地，见文首口径校对。
> 两套体系通过 namespace/label 隔离可并存，生产环境按需选用。

## 3. 响应 SOP（标准操作流程）

### 3.1 critical 告警响应 SOP

| 步骤 | 操作 | 负责人 | 时限 |
|------|------|--------|------|
| 1 | PagerDuty/邮件收到告警，确认告警内容 | 值班工程师 | 立即 |
| 2 | 查看 runbook_url 链接的处置手册 | 值班工程师 | 5 分钟内 |
| 3 | 登录 Grafana 对应 Dashboard 查看指标趋势 | 值班工程师 | 5 分钟内 |
| 4 | 初步定位故障原因，执行应急处置 | 值班工程师 | 15 分钟内 |
| 5 | 在 PagerDuty/IM 群同步处置进展 | 值班工程师 | 每 30 分钟 |
| 6 | 故障恢复后确认告警已 resolve | 值班工程师 | 恢复后立即 |
| 7 | 编写故障复盘报告（如影响 > 30 分钟） | 值班工程师 + 负责人 | 24 小时内 |

## 5. 部署步骤

### 5.1 部署告警规则

```bash
# 规则以「事实来源 + 图表副本」方式交付：改规则只改事实来源，再同步副本
bash scripts/sync-alert-rules.sh            # 同步到 design/deploy/charts/prometheus/files/rules/
bash scripts/sync-alert-rules.sh --check    # CI 同款校验（副本不得残留占位符）
python scripts/check-alert-rule-contract.py # 契约变量 / 规则数 / 跨文件重名门禁
helm template prometheus design/deploy/charts/prometheus | grep -c "kind: ConfigMap"  # 渲染确认

# 集群侧：规则随 prometheus chart（ConfigMap 挂载）与 alertmanager 配置部署
kubectl get configmap -n monitoring | grep -i alert
```

### 5.2 验证规则评估

```bash
# 检查 Prometheus 是否加载了规则（通过 port-forward 访问 Prometheus UI）
kubectl port-forward -n monitoring svc/prometheus-operated 9090:9090

# 浏览器访问 http://localhost:9090/rules 确认规则可见
# 浏览器访问 http://localhost:9090/alerts 确认告警状态
```

### 5.3 端到端闭环测试

```bash
# 1. 人为制造租户工作空间不可达（在 dev 环境选一个承载工作空间的服务缩容）
kubectl scale deployment <workspace-服务> -n dataengine-dev --replicas=0

# 2. 等待 2 分钟（TenantWorkspaceDown for=2m），确认 P0 告警触发
# 3. 确认 p0-pager（电话/短信网关）收到通知
# 4. 恢复服务
kubectl scale deployment <workspace-服务> -n dataengine-dev --replicas=1

# 5. 确认收到 resolve 通知
```

## 一句话结论

**架构设计和代码骨架是真实且完整的，但所有外部依赖（K8s/Trino/Doris/Milvus/NebulaGraph 等）目前全部处于 Mock 或 TODO 状态，前后端从未联调。真实完成度约 40~50%，与 README 宣称的"v2.0 GA、成熟度 85/100"存在显著差距。** ROADMAP.md 里 v1.1"替换 Mock"和 v1.2"端到端跑通"的任务一项都未勾选，与实际状态吻合。

## 一、导航菜单内容异常的根因（已确认）

您看到的现象完全属实，有两个叠加的原因：

### 原因 1：46% 的菜单是纯占位页

侧边栏共 35 个菜单项，其中 **16 个直接指向同一个 `Roadmap.vue` 占位组件**（`frontend/src/router/index.ts:169-184`），点进去只显示"该模块已纳入产品规划，敬请期待"：

| 分组 | 空壳菜单项 |
| --- | --- |
| 基础设施（全组空壳） | 机器供应、K8s 集群、容器网络、容器存储、弹性调度 |
| 数据引擎（7/8 空壳） | 统一存储、批计算 Spark、流计算 Flink、OLAP Doris、消息流 Kafka、时序 IoTDB、多模型引擎 |
| 数据治理（1/6 空壳） | 元数据管理 |
| 开发工具（3/6 空壳） | 调度编排、标签画像、机器学习 |

### 原因 2：已实现的页面依赖的后端根本没启动

其余 19 个"完整实现"的页面全部走真实 HTTP 请求：前端 `baseURL=/api/v1`，Vite 代理指向 `localhost:9080`（APISIX 网关）。项目**没有任何前端 mock 层**，而 APISIX 和后端微服务都需要 K8s/Helm 部署——本地没跑起来时，所有 API 返回错误，页面表现为空白、加载失败或报错。

另有两处小瑕疵：
- `Analyze.vue:15-37`：GMV 趋势图和渠道占比图是纯 CSS 高度模拟的假数据，不是 ECharts 动态渲染。
- `Workspaces.vue:77-97`：工作空间抽屉里的成员/项目 tab 是硬编码假数据。

### 补充：前端目前无法构建

`frontend/` 下没有 `node_modules`，需要先 `npm install` 才能运行。

## 二、后端真实度审计（逐组件证据）

| 组件 | 真实度 | 关键证据 |
| --- | --- | --- |
| encaps-layer（封装层） | 🟡 半真 | K8s 客户端用真实 fabric8 库，但 `K8sClientConfig.java:39-42` 有 `app.k8s.mock-enabled` 开关，无真实集群时走模拟 |
| sql-gateway（SQL 网关） | 🟡 半真 | `BackendProxyService.java:27-33` 用 WebClient 真实代理 Trino/Doris HTTP 接口（有熔断器），但 `DorisScanStatsClient.java:51-60` 的扫描字节采集直接 `return null` 并标注 `TODO(real-cluster)`；无真实引擎时返回 DEGRADED |
| catalog（资产目录，Go） | 🟡 接口真/存储假 | 接口层完整，`catalog_test.go:18-25` 显示存储层是内存 map（mockStore） |
| vector-engine（Go） | 🔴 默认 Mock | `main.go:58-69`：`STORE_TYPE=mock` 是默认值；真实 Milvus 需 build tag `milvus_enabled`，未启用时自动回退 mock |
| llmops（Python） | 🔴 默认 Mock | `main.py` 强制 `LLMOPS_STORE_TYPE=mock`；真实 MLflow 需手动配置注入 |
| knowledge-engine（Python） | 🔴 默认 Mock | `settings.py:48-51` 配置默认指向 nebula/llm，但 Dockerfile 第 52-53 行又覆盖回 mock |

### 测试与构建状态

- `java-test-logs/` 目录**为空**——Java 测试日志从未产出过。
- `.pytest_cache/v/cache/lastfailed` 中有 **35 条失败记录**（主要是 k3s 链路测试），说明 pytest 真跑过但大面积失败。
- `vector-engine-build.log` 显示 Docker 镜像构建本身是成功的。
- 集成测试是真代码，但验证的多是"降级/mock 路径"（如 `test_docker_sql_gateway.py:17` 明确写"无真实 Trino/Doris 时返回 DEGRADED 属预期"）。

### PoC 脚本状态

`scripts/poc/run-poc.sh`（470 行）不是假把式——它真实调用 `ske.sh up`、`helm upgrade`、curl API。但关键的 E2E 阶段只执行 `SELECT 1`（第 355 行），不触及真实数据读写；且依赖完整的 SKE K8s 集群，本地难以直接跑通。

## 四、本地运行方案现状

- docker-compose 文件共 5 个，均为局部组件（middleware、doris-lite、karmada、集成测试），**没有全局一键启动**。
- 无 Makefile。
- `platform/bootstrap.sh` 只创建 K8s namespace/Quota/NetworkPolicy，不启动应用。
- 前端代理目标 `localhost:9080` = APISIX 网关（需 Helm 部署），这是前端页面的总入口。

## 五、下一步方向建议（按优先级）

### 阶段 1：打通最小可演示链路（建议立即做）

1. **启动 Doris 轻量环境**（本次已用项目自带 compose 启动），验证建库建表查询。
2. **本地直跑 sql-gateway**（`mvn spring-boot:run`，8081 端口），将 Doris 配置指向 `localhost:18030`，用 `verify-sql-gateway.sh` 的思路验证：列出引擎 → 执行 SQL → 拿到 Doris 返回结果。这一步做完，"验证 Doris 能力"即闭环。
3. **前端跑起来并加 mock 兜底**：`npm install && npm run dev`；给 16 个 Roadmap 占位页做降级提示优化（至少明确告知哪些功能未实现）。

### 阶段 2：消灭 Mock（对应 ROADMAP v1.1，这才是真正提升成熟度的工作）

按价值排序建议接入顺序：
1. sql-gateway 接真实 Trino + Doris（Doris 本次就绪，Trino 可用单容器镜像）
2. catalog 接真实 PostgreSQL/Elasticsearch 存储
3. encaps-layer 接真实 K8s（您有 Docker Desktop，可考虑 k3s 替代自研 SKE 做本地开发集群）
4. Keycloak + APISIX 鉴权链路落地，前端 9080 入口打通

### 阶段 3：端到端 PoC（对应 ROADMAP v1.2）

MySQL → Iceberg → Spark → Doris 数据流真实跑通，治理闭环跑通。

### 给 vibe coding 的特别提醒

- **README 的宣称要修正或降级**：v2.0 GA、85/100、2000+ 测试通过等表述与代码实际状态不符。如果是对外展示项目，建议改为"框架版 v0.x，集成开发中"，避免演示时被问倒。

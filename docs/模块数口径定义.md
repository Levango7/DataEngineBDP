# 模块数口径定义

> 版本：v1.0 ｜ 日期：2026-09-12 ｜ 状态：生效
> 适用范围：全仓库文档（README / ROADMAP / CONVENTIONS / component-maturity / ADR / 设计文档）
> 目标：消除"49 vs 44 vs 41 vs 39"四种模块数口径混用问题，建立单一事实来源。

## 1. 四种口径定义

项目在不同维度下使用不同的"模块数"计数，各口径有明确的统计边界与用途：

| 口径 | 数值 | 统计边界 | 来源 | 用途 |
| --- | --- | --- | --- | --- |
| **设计模块数** | **49** | 产品原型设计 §3.3 的逻辑模块清单（含未实现规划模块） | `design/多平台多租户大数据平台_产品原型设计_v0.4.md` §3.3 | 产品规划、能力全景、详细设计文档编号 |
| **自研组件数** | **45** | `platform/` 下按构建文件（pom.xml / go.mod / pyproject.toml）实测的自研组件数，含子模块拆分 | `docs/component-maturity.md` | 工程实现盘点、成熟度矩阵、技术栈统计 |
| **独立部署单元** | **41** | ADR-001 定义的独立部署单元数（按构建文件实测，含库形态组件不独立部署的扣减） | `design/详细设计/_ADR-001_微服务框架与中间件选型.md` §1 | 部署架构、运维盘点、服务网格覆盖 |
| **platform/ 目录数** | **39** | `platform/` 下一级子目录数（含 operations-api） | 文件系统实测 | 目录结构导航、组件定位 |

> **历史口径注记**：自研组件数在 operations-api 纳入矩阵前为 **44**（Java 22 / Go 11 / Python 11）。operations-api（Python FastAPI）纳入后为 **45**（Java 22 / Go 11 / Python 12）。本文档以纳入后口径为准。

## 2. 口径差异来源

四种口径数值不同的根本原因在于**统计边界与粒度**差异：

### 2.1 设计模块数 49 → 自研组件数 45

- 设计模块数 49 包含产品原型设计的全部逻辑模块，含**未实现规划模块**（如 L5.6 数据资产流通扩展、X3 审计合规独立模块等）。
- 自研组件数 45 仅统计 `platform/` 下有构建文件的实际工程组件。
- 差值 4 = 规划中未落地模块（设计文档有、代码无构建文件）。

### 2.2 自研组件数 45 → 矩阵实列 42

- 自研组件数 45 含子模块拆分：governance 拆为 3 个子模块（metadata-collector / lineage-analyzer / real-time-pipeline）、finops 拆为 2 个服务（cost-model / dashboard）、karmada 拆为 3 个子模块（api / federated-query / failover）。
- 组件成熟度矩阵中 governance 合并为 1 行（3 子模块）、finops 合并为 1 行（2 服务）、karmada 保持 3 行。
- 矩阵实列 = 45 − (3−1) − (2−1) = 45 − 2 − 1 = **42 条**。

### 2.3 自研组件数 45 → 独立部署单元 41

- 自研组件数 45 含**库形态组件**（common-security、storage-io、flink-cdc、chunker），库不独立部署而是被其他服务依赖。
- 独立部署单元 41 = 45 − 4（库形态组件）。
- ADR-001 §1 背景描述的"41 个独立部署单元"即此口径。

### 2.4 自研组件数 45 → platform/ 目录数 39

- 自研组件数 45 含子模块拆分后的独立构建单元（governance 3 + finops 2 + karmada 3 = 8 个子模块），但子模块在 `platform/` 下是嵌套目录（如 `platform/governance/metadata-collector/`），不是一级子目录。
- platform/ 目录数 39 = 45 − (3−1) − (2−1) = 45 − 2 − 1 = **39 个一级子目录**（governance 1 + finops 1 + karmada 1 作为一级目录，子模块嵌套其下）。

## 3. 口径对照表（49 → 45 → 42 → 41 → 39 映射）

```
设计模块数 49  （产品原型 §3.3，含未实现规划模块）
      │
      │  −4 规划未落地模块
      ▼
自研组件数 45  （platform/ 构建文件实测，含子模块拆分，含 operations-api）
      │
      ├──→ 矩阵实列 42  （governance 3合1 + finops 2合1，−3 行）
      ├──→ 独立部署单元 41  （−4 库形态组件：common-security/storage-io/flink-cdc/chunker）
      └──→ platform/ 目录数 39  （governance/finops 子模块嵌套，−6 一级目录）
```

## 4. 使用规范

| 场景 | 应使用的口径 | 示例 |
| --- | --- | --- |
| 产品能力规划、详细设计编号 | 设计模块数 49 | "§3.3 定义 49 个设计模块" |
| 工程实现盘点、技术栈统计 | 自研组件数 45 | "platform/ 下 45 个自研组件（Java 22 / Go 11 / Python 12）" |
| 组件成熟度矩阵行数 | 矩阵实列 42 | "矩阵实列 42 条（含子模块合并）" |
| 部署架构、运维盘点 | 独立部署单元 41 | "41 个独立部署单元（ADR-001）" |
| 目录结构导航 | platform/ 目录数 39 | "platform/ 下 39 个一级子目录" |

- **禁止**：混用口径（如"44 个模块"既指设计模块又指自研组件）。
- **禁止**：使用未经本文件定义的口径数字。
- 引用模块数时必须标注口径名称（如"自研组件数 45"而非裸数字"45"）。

## 5. 子模块拆分说明

部分一级目录下含多个独立构建的子模块，子模块有独立构建文件但共享父目录：

| 一级目录 | 子模块 | 构建文件 | 语言 | 矩阵中的表现 |
| --- | --- | --- | --- | --- |
| governance | metadata-collector / lineage-analyzer / real-time-pipeline | 各自 pom.xml | Java | 合并为 1 行（governance） |
| finops | cost-model / dashboard | 各自 pom.xml | Java | 合并为 1 行（finops） |
| karmada | api / federated-query / failover | go.mod / pom.xml / go.mod | Go + Java | 拆为 3 行（karmada-api / karmada-federated-query / karmada-failover） |

- governance：3 个子模块在矩阵中合并为 1 行，因共享治理中台业务边界与 NebulaGraph 图存储依赖。
- finops：2 个服务在矩阵中合并为 1 行，因共享 FinOps 成本运营业务边界。
- karmada：3 个子模块在矩阵中保持 3 行，因分属不同语言（Go/Java/Go）与不同成熟度阶段。

## 6. CI 校验建议

建议在 CI 中加入口径对账脚本，本文件作为单一事实来源：

- 自研组件数扫描：`find platform/ -name "pom.xml" -o -name "go.mod" -o -name "pyproject.toml" | wc -l` 应与本文档定义一致。
- platform/ 目录数扫描：`ls -d platform/*/ | wc -l` 应为 39。
- 矩阵实列扫描：`docs/component-maturity.md` 中表格数据行数应为 42。

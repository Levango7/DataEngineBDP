## 1. 四种口径定义

项目在不同维度下使用不同的"模块数"计数，各口径有明确的统计边界与用途：

| 口径 | 数值 | 统计边界 | 来源 | 用途 |
| --- | --- | --- | --- | --- |
| **设计模块数** | **49** | 产品原型设计 §3.3 的逻辑模块清单（含未实现规划模块） | `design/多平台多租户大数据平台_产品原型设计_v0.4.md` §3.3 | 产品规划、能力全景、详细设计文档编号 |
| **自研组件数** | **46** | `platform/` 下按构建文件（pom.xml / go.mod / pyproject.toml）实测的自研组件数，含子模块拆分 | `docs/component-maturity.md` | 工程实现盘点、成熟度矩阵、技术栈统计 |
| **独立部署单元** | **42** | ADR-001 定义的独立部署单元数（按构建文件实测，含库形态组件不独立部署的扣减） | `design/详细设计/_ADR-001_微服务框架与中间件选型.md` §1 | 部署架构、运维盘点、服务网格覆盖 |
| **platform/ 目录数** | **38** | `platform/` 下一级子目录数（含 operations-api） | 文件系统实测 | 目录结构导航、组件定位 |

> **历史口径注记**：自研组件数在 operations-api 纳入矩阵前为 **44**（Java 22 / Go 11 / Python 11）。operations-api（Python FastAPI）纳入后为 **46**（Java 24 / Go 10 / Python 12）。本文档以纳入后口径为准。

## 2. 口径差异来源

四种口径数值不同的根本原因在于**统计边界与粒度**差异：

### 2.1 设计模块数 49 → 自研组件数 46

- 设计模块数 49 包含产品原型设计的全部逻辑模块，含**未实现规划模块**（如 L5.6 数据资产流通扩展、X3 审计合规独立模块等）。
- 自研组件数 46 仅统计 `platform/` 下有构建文件的实际工程组件。
- 差值 3 = 规划中未落地模块（设计文档有、代码无构建文件）。

### 2.2 自研组件数 46 → 矩阵实列 43

- 自研组件数 46 含子模块拆分：governance 拆为 3 个子模块（metadata-collector / lineage-analyzer / real-time-pipeline）、finops 拆为 2 个服务（cost-model / dashboard）、karmada 拆为 3 个子模块（api / federated-query / failover）。
- 组件成熟度矩阵中 governance 合并为 1 行（3 子模块）、finops 合并为 1 行（2 服务）、karmada 保持 3 行。
- 矩阵实列 = 46 − (3−1) − (2−1) = 46 − 2 − 1 = **43 条**。

### 2.3 自研组件数 46 → 独立部署单元 42

- 自研组件数 46 含**库形态组件**（common-security、storage-io、flink-cdc、chunker），库不独立部署而是被其他服务依赖。
- 独立部署单元 42 = 46 − 4（库形态组件）。
- ADR-001 §1 背景描述的"42 个独立部署单元"即此口径。

### 2.4 自研组件数 46 → platform/ 目录数 38

- 自研组件数 46 含子模块拆分后的独立构建单元（governance 3 + finops 2 + karmada 3 = 8 个子模块），但子模块在 `platform/` 下是嵌套目录（如 `platform/governance/metadata-collector/`），不是一级子目录。
- platform/ 目录数 38 = 46 − (3−1) − (2−1) − (karmada 嵌套 3) − (llm-gateway/evaluation 嵌套 1) = 46 − 2 − 1 − 2 − 1 = **38 个一级子目录**（governance 1 + finops 1 + karmada 1 作为一级目录，子模块嵌套其下）。

## 3. 口径对照表（49 → 46 → 43 → 42 → 38 映射）

```
设计模块数 49  （产品原型 §3.3，含未实现规划模块）
      │
      │  −3 规划未落地模块
      ▼
自研组件数 46  （platform/ 构建文件实测，含子模块拆分，含 operations-api）
      │
      ├──→ 矩阵实列 43  （governance 3合1 + finops 2合1，−3 行）
      ├──→ 独立部署单元 42  （−4 库形态组件：common-security/storage-io/flink-cdc/chunker）
      └──→ platform/ 目录数 38  （governance/finops/karmada 子模块嵌套，−8 一级目录）
```

## 4. 使用规范

| 场景 | 应使用的口径 | 示例 |
| --- | --- | --- |
| 产品能力规划、详细设计编号 | 设计模块数 49 | "§3.3 定义 49 个设计模块" |
| 工程实现盘点、技术栈统计 | 自研组件数 46 | "platform/ 下 46 个自研组件（Java 24 / Go 10 / Python 12）" |
| 组件成熟度矩阵行数 | 矩阵实列 43 | "矩阵实列 43 条（含子模块合并）" |
| 部署架构、运维盘点 | 独立部署单元 42 | "42 个独立部署单元（ADR-001）" |
| 目录结构导航 | platform/ 目录数 38 | "platform/ 下 38 个一级子目录" |

- **禁止**：混用口径（如"44 个模块"既指设计模块又指自研组件）。
- **禁止**：使用未经本文件定义的口径数字。
- 引用模块数时必须标注口径名称（如"自研组件数 46"而非裸数字"46"）。

## 5. 子模块拆分说明

部分一级目录下含多个独立构建的子模块，子模块有独立构建文件但共享父目录：

| 一级目录 | 子模块 | 构建文件 | 语言 | 矩阵中的表现 |
| --- | --- | --- | --- | --- |
| governance | metadata-collector / lineage-analyzer / real-time-pipeline | 各自 pom.xml | Java | 合并为 1 行（governance） |
| finops | cost-model / dashboard | 各自 pom.xml | Java | 合并为 1 行（finops） |
| karmada | api / federated-query / failover | go.mod / pom.xml / go.mod | Go + Java | 拆为 3 行（karmada-api / karmada-federated-query / karmada-failover） |

- governance：3 个子模块在矩阵中合并为 1 行，因共享治理中台业务边界与 NebulaGraph 图存储依赖。
- finops：2 个服务在矩阵中合并为 1 行，因共享 FinOps 成本运营业务边界。
- karmada：3 个子模块在矩阵中保持 3 行，因分属不同语言（Go/Java/Go）与不同成熟度阶段。

## 6. 可部署单元口径（2026-09-26 实测新增）

前面几个口径都只数"代码有多少块"，不回答"客户环境能不能装起来"。补一个部署口径：

| 口径 | 数值 | 说明 |
| --- | --- | --- |
| 自研组件数 | 46 | 构建文件实测（24 pom + 10 go.mod + 12 pyproject） |
| 库形态组件 | 4 | `common-security`、`flink-cdc`、`storage-io`、`chunker` —— 无启动入口/无端口，**不应计入部署单元** |
| 服务形态组件 | 42 | 46 − 4 |
| **有 Helm Chart 的服务** | **35** | 42 − 7（下表） |

**7 个"是服务但没有 Chart"的组件**（生产环境无法部署，其 API 前缀也因此不可达）：
`encaps-tenant`、`encaps-data`、`encaps-gateway`、`data-standard`、`master-data`、
`operations-api`、`governance/real-time-pipeline`。

另有两处会让"35"偏乐观，引用该数时必须一并说明：

1. `finops/billing`、`finops/cost-model`、`finops/dashboard` 三个子模块**共用一个名为 `finops` 的
   Chart**（镜像 `harbor.shuqing.io/shuqing/finops`）——按子模块算 3 个部署单元，按 Chart 算 1 个。
2. `design/deploy/charts/karmada` 的镜像是上游 `registry.k8s.io/karmada/karmada-apiserver`，
   **不能承载平台自研的 karmada-api / failover 接口**；平台侧这两个子模块实际无可用 Chart。

## 7. CI 校验建议

本文件作为单一事实来源，以下脚本已实际挂载 CI（`.github/workflows/ci.yml` 的 standards 作业）：

- 迁移覆盖：`python scripts/check-db-migration-coverage.py`（服务必须"有迁移或登记待补"）。
- 路由覆盖：`python scripts/gen-apisix-routes.py --check`（前缀必须"有路由或有待裁决记录"）。
- 告警指标：`python scripts/check-alert-metric-coverage.py`（规则只能引用已登记指标）。
- 计数对账（待补）：`find platform -name pom.xml -o -name go.mod -o -name pyproject.toml` 应为 46；
  `ls -d platform/*/ | wc -l` 应为 38；`find design/deploy/charts -name Chart.yaml | wc -l` 实测 **88**（成立）。
- 部署口径（待补）：建议新增 `check-deployment-coverage.py`，把"服务必须有 Chart"变成硬门禁，
  使第 6 节的 35 不再依赖人工维护。

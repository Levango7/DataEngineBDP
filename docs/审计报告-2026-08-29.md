## 二、功能现状：已具备 vs 缺少（产品视角）

### 已具备（有真实代码支撑）
1. **统一 SQL 网关**：28K 行，Calcite + 手写解析 + 跨源归并，真实 Trino/Doris/Spark/Flink 代理（Docker 容器化 IT 8 用例自述）；/sql/execute 租户以 JWT 优先（SqlRoutingService.java:187-193）。
2. **封装层/多租户**：encaps-layer 18K 行，K8s 翻译 + JwtAuthFilter 实现 X-Tenant-Id vs claim 比对 403（JwtAuthFilter.java:153-181），是 §9.5 的正面范例。
3. **规则引擎 + 治理闭环**：rule-engine 11K 行；governance 9K 行（metadata-collector/lineage-analyzer/real-time-pipeline 三件套），血缘字段级解析 + NebulaGraphClient。
4. **湖仓引擎接入**：flink-cdc（Kafka→Iceberg WAL）、stream-batch-scheduler（真实 Flink/Spark 提交，容器化验证 13 用例）。
5. **前端 69 个页面**：Vue3 + TS strict + Pinia，37 个 API 模块均真实 axios 调用（client.ts 401 单飞去重、403/500 分级提示），非 toast 占位（大部）。
6. **工程化资产**：88 个 Chart 已补 templates（HPA/PDB/Ingress 自述已加）、12 个 CI workflow、cosign+SBOM、SonarQube workflow、JWT 轮换机制、7 份 jwt_auth.py 镜像副本**逐字节一致**（md5 5f6b8c45… ×7 ✅）。

### 缺少/未闭合（按产品价值排序）
1. **AI 层整体是"演示模式"**：llm-gateway 未配真实 Provider 时兜底 Mock；llmops/registry/knowledge-engine/model-finetuning 默认 mock；vector-engine 默认内存 Mock（需 `-tags milvus_enabled` 重编译）；registry DeploymentManager `mock_mode=True` 默认（app/core/deployment_manager.py:36）——**不启动容器即标记 running 并伪造 endpoint**（component-maturity.md 自述）。→ 旗舰版卖点名不副实。
2. **四环境交付零实测**：信创/本地/公有云/私有云仅配置模板（README 明示"均为配置模板"），ERRATUM 自认 0/6 验证通过。→ "零改动交付"是纸面承诺。
3. **跨源查询租户隔离未闭环**（详见 §四 P0-1）。
4. **数据质量/血缘/目录的"真数据"链路**依赖外部引擎就绪（Kafka/Trino/Doris/Milvus/NebulaGraph），本地开箱只能跑 mock。
5. **缺少的产品线**：无数据集成可视画布（仅 API）、无 IDE（Theia 仅配置）、无多集群联邦前端管理（karmada 只有 API+CRD）、无移动端/多语言 i18n、无租户自助开通流程前端闭环、无计量计费的可视化账单（finops 有 API 但前端仅雏形）。

## 三、产品设计/定位评估与改良建议

### 3.1 定位合理性
- **合理处**：SKE 底座 + 封装层屏蔽引擎差异 + 四环境交付 + 政企/信创合规（等保三级、国密 SM2/3/4 有真实实现 105 测试）——瞄准国内政企数据平台市场，定位清晰，与 NebulaGraph/Milvus/Doris 等真实引擎集成方向正确。
- **问题 1：野心与资源错配**。"数据操作系统"愿景 + 37 组件 + 10+ 行业模板，但 AI 层 8 个组件全是演示模式。**建议**：v2.1-RC 起明确"旗舰版 AI 能力需显式配置外部服务"，把 mock 兜底改为 fail-fast（启动时检测 Provider 未配即拒绝启动，而非静默降级），防止交付现场"看起来能用、实际是假数据"。
- **问题 2：行业模板过度扩张**。README 称"覆盖 15+ 行业"（ROADMAP 目标），实际内置 7 个（3 旧+4 新）。建议收敛到 3 个深度行业（金融/政务/能源），做"可真实落库的 DDL+DAG"，而不是继续堆模板数量。
- **问题 3：命名/口径混乱影响商业化叙事**。37 组件（仓库）vs 49 模块（CONVENTIONS 产品口径）vs 30+ 微服务（审核报告）vs 21 GA（release）——对外材料必须统一到一个口径（建议：产品 49 模块、仓库 37 组件、发布 21+10）。
- **问题 4：chunker（10.8K 行）是孤岛**。component-maturity 自认"未被任何平台服务引用"。建议：要么接入 RAG 链路（knowledge-engine 的 embedding 前置），要么砍掉，10K 行死代码是负资产。

## 四、缺陷清单（证据链）

### P0（阻断交付 / 安全）

**P0-1 未登记的租户越权风险：sql-gateway 跨源查询租户 ID 取自请求体且无 claim 比对**
- `platform/sql-gateway/.../sqlgateway/controller/SqlGatewayController.java:296-297`：`crossSourceExecutor.execute(request.getSql(), dialect, request.getTenantId())`
- `platform/sql-gateway/.../sqlgateway/model/CrossSourceRequest.java:30`：`private String tenantId;`
- 下游透传：`SourceQueryTask.java:131-140` → `proxyToDoris(sql, tenantId)` / `proxyToTrino(sql, tenantId)`；`BackendProxyService.java:163` 明示 `X-Trino-User` 头用于"审计与资源隔离"。
- **后果**：已认证用户 A 可在 body 中填 tenantB，以 tenantB 身份执行跨源查询 → 跨租户数据/审计越权。违反 CONVENTIONS §9.5（"服务端不得信任请求体中的裸租户值…不一致必须 403"），且**未登记在 §9.8 偏差表**。对照：/sql/execute 路径（SqlRoutingService.java:187-193）是 JWT 优先——同一服务两套行为。
- **修法**：crossSource 路径改从 `TenantContext.getTenantId()` 取租户，body.tenantId 仅作显式校验（不一致 403）。

**P0-2 前端 emoji 功能图标（违反团队 P0-1 规则）**
- `frontend/src/views/Develop.vue:34-35`：`📁`、`📄` 作为文件/文件夹图标
- `frontend/src/views/Gateway.vue:121`、`components/ErrorBoundary.vue:30`：`⚠`
- 全仓共 4 处命中。**修法**：换项目锁定 SVG 图标库对应图标。

## 六、具体 Bug 清单（可复现级别）

1. **跨租户越权**（P0，见上）— body tenantId 直通 Trino user。
2. **跨源失败返回 200**（P1）— 前端/网关无法按状态码告警，`status="FAILED"` 靠调用方自觉。
3. **registry 假运行**（P1）— `mock_mode=True` 时 `containerId` 伪造，运维看板会显示"已运行"实际无容器。
4. **llm-gateway 缺省 Mock Provider**（P1）— 未配置即返回非真实模型输出，AI 助手"看起来可用"。
5. **两个 shell 脚本语法错**（P1）— 交付包内 `scripts/smoke-test.sh`、`scripts/setup-karmada-multicluster.sh` 直接执行即报错。
6. **前端 emoji 图标**（P0-2 规则违反，P2 功能影响）— Develop.vue 文件夹/文件图标。
7. **AUTH_MODE 默认 none**（P1 配置陷阱）— 生产漏配环境变量 = 匿名 admin，且只告警一次。

# 维护模式口径说明

> **适用范围**：本仓（Levango7/DataEngineBDP）。与燧石 Flint 无关——两者无代码关联，本口径不约束 Flint。
> **依据**：README 顶部「项目状态：MAINTENANCE（2026-10-03 起）」声明。
> **现状提示**：该声明目前仅存在于工作区修改中（`git diff README.md`），尚未进入任何提交。本文件随代码一并入库，是把「维护模式」落到版本化的第一份可判定文书；若与 README 声明冲突，以本文件为准并回头同步修订 README。

## 1. 为什么需要本口径

README 的维护模式声明只有一句话：不再新增功能，仅修复 P0 缺陷与安全补丁。它没有定义：

- 什么算「新增功能」（判定边界）
- 「缺陷」如何分级、谁能豁免
- 哪些目录冻结、代码是保留还是迁出

口径不明会走向两个相反的错误：要么把**已声明能力的实现缺口**也当作「新功能」冻结，能力永远补不上；要么以「修补」为名不断塞入新组件，冻结形同虚设。本文件给出可判定的边界。

## 2. 判定规则

### 2.1 属于「新增功能」（维护模式下不允许）

满足任一即算：

1. 新增服务形态组件（含任何 Helm Chart 可部署单元）
2. 新增设计模块，或改变《模块数口径定义》中的任何计数
3. 新增对外交付单元（四环境交付清单新增条目）
4. 新引入中间件 / 引擎 / 存储后端，或新增独立的有状态组件

### 2.2 不属于「新增功能」（按能力缺口修补处理）

需**同时**满足：

1. 改动落在**既有组件**内，且该组件已在 README 特性矩阵中声明
2. **不新增**可部署单元，不改变交付面与模块计数
3. 补齐的是该组件**已声明能力**的**实现缺口**（此前为空实现 / 模拟 / 未落地）
4. 改动自包含，不牵动其他组件的接口

### 2.3 适用方式

每次按 §2.2 归类时，提交信息必须显式标注：

```text
按《维护模式口径说明》§2.2 归类为能力缺口修补
```

未标注的改动视为普通变更，仍受「不再新增功能」约束。

## 4. 边界（防止口径被放宽）

1. 不适用于新增服务形态组件——即使它「很小」
2. 不适用于新增设计模块，或任何改变模块数口径的改动
3. 不适用于为 Flint 预研 / 预埋的能力——Flint 与本仓无代码关联，不得以「将来迁出」为由在本仓入库
4. 单次适用只覆盖单次提交；不得援引同一判定无限扩展同一组件的范围
5. 本口径是并行豁免项，不改变 P0 / 安全补丁的优先顺序

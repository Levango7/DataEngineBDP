## 第3章 整改项详细记录

### 3.1 整改项 ZG-001：通信网络可信验证

#### 3.1.1 问题描述

等保测评项 8.1.2.3 可信验证：30% 数据面节点（共 18 台）未启用基于可信根的启动度量，未在系统启动时对引导程序、系统配置文件进行可信验证，存在启动完整性无法保证的风险。

#### 3.1.2 整改目标

全部 60 台数据面节点启用 TPM 2.0 + IMA 度量，启动时对引导程序、内核、系统配置文件进行可信度量，度量值上报至管理中心集中校验。

#### 3.1.3 技术整改措施

1. **硬件核查与启用 TPM 2.0**：对 18 台未启用 TPM 2.0 的节点进入 BIOS 启用 TPM 2.0 模块，确认 TPM 芯片状态为 active。
2. **配置可信启动**：在节点上安装 `tboot` 与 `ima-evm-utils`，配置 grub 引导可信启动，对引导程序、内核、initrd 进行度量。
3. **配置 IMA 度量策略**：在 `/etc/ima/ima-policy` 中配置度量规则，对 `/usr/bin`、`/usr/lib`、`/etc` 关键目录下的可执行文件与配置文件进行度量。
4. **度量值上报**：通过 `ima-log` 采集度量日志，经 Filebeat 上报至管理中心 Loki，并写入 ClickHouse 可信基线库。
5. **集中校验**：管理中心定时拉取度量值与可信基线库比对，发现异常立即告警并隔离节点。

#### 3.1.4 管理整改措施

1. **修订安全基线**：在《数据引擎大数据平台安全配置基线 V2.0》中新增"可信启动"章节，明确 TPM 2.0 + IMA 度量要求。
2. **更新部署 SOP**：在节点部署 SOP 中增加"启用 TPM 2.0 + IMA 度量"步骤，新节点上线必须满足可信启动要求。
3. **培训运维人员**：组织 2 场可信计算培训，覆盖全部运维人员，培训内容包括 TPM 2.0 原理、IMA 度量配置、可信基线维护。

#### 3.1.5 整改前后对比

| 对比项 | 整改前 | 整改后 |
| --- | --- | --- |
| TPM 2.0 启用节点数 | 42 / 60（70%） | 60 / 60（100%） |
| IMA 度量覆盖节点数 | 42 / 60（70%） | 60 / 60（100%） |
| 度量值上报管理中心 | 否 | 是 |
| 可信基线集中校验 | 否 | 是（每小时校验 1 次） |
| 启动完整性异常告警 | 无 | 实时告警 + 自动隔离 |

#### 3.1.6 验证方法与结果

- **验证方法**：使用自研可信验证核查脚本，对全部 60 台数据面节点进行 TPM 2.0 状态、IMA 度量配置、度量值上报、集中校验链路核查。
- **验证结果**：全部 60 台节点 TPM 2.0 状态为 active，IMA 度量配置正确，度量值实时上报管理中心，集中校验链路正常。**验证通过**。

### 3.2 整改项 ZG-002：区域边界可信验证

#### 3.2.1 问题描述

等保测评项 8.1.3.6 可信验证：边界防火墙、负载均衡等 6 台网络设备未配置基于可信根的可信验证机制，设备启动完整性无法保证。

#### 3.2.2 整改目标

全部 6 台边界网络设备启用 Secure Boot，启动时对固件、引导程序、系统镜像进行可信度量，度量值纳入管理中心可信基线库。

#### 3.2.3 技术整改措施

1. **设备能力评估**：对 6 台网络设备进行 Secure Boot 支持能力评估，其中 4 台设备原生支持 Secure Boot，2 台老旧设备需升级固件后支持。
2. **固件升级**：对 2 台老旧设备升级至最新固件版本（v7.2.4），升级后支持 Secure Boot。
3. **启用 Secure Boot**：在 6 台设备上启用 Secure Boot，配置可信根证书为厂商根证书 + 公司自签名根证书。
4. **度量值采集**：通过 SNMP + 设备厂商 API 采集设备启动度量值，经 Filebeat 上报至管理中心。
5. **纳入可信基线库**：在管理中心 ClickHouse 可信基线库中新增 6 台网络设备的可信基线，每小时校验 1 次。

#### 3.2.4 管理整改措施

1. **修订采购规范**：在《网络设备采购技术规范》中明确"必须支持 Secure Boot"为强制要求。
2. **更新上线 SOP**：在网络设备上线 SOP 中增加"启用 Secure Boot + 度量值上报"步骤。
3. **建立可信基线维护流程**：制定《网络设备可信基线维护规程》，明确固件升级、基线更新、异常处理流程。

#### 3.2.6 验证方法与结果

### 3.3 整改项 ZG-003：计算环境可信验证

#### 3.3.2 整改目标

全部 6 个 Python 微服务容器启用进程可信度量，启动时对 Python 解释器、依赖包、入口脚本进行哈希度量并上报管理中心校验。

#### 3.3.3 技术整改措施

1. **IMA 度量工具集成**：在 6 个 Python 服务的容器镜像中集成 `ima-evm-utils` 与 `python-trustee`（自研 Python 进程度量工具）。
2. **度量规则配置**：在容器启动脚本中配置度量规则，对 `/usr/local/bin/python`、`/usr/local/lib/python3.11/site-packages`、入口脚本进行 SM3 哈希度量。
3. **依赖包锁定**：使用 `pip-tools` 生成 `requirements.txt` 锁定依赖版本，构建时对依赖包进行哈希校验。
4. **度量值上报**：容器启动时通过 `python-trustee` 采集度量值，经 Filebeat 上报至管理中心 Loki + ClickHouse。
5. **集中校验**：管理中心将度量值与构建时生成的可信基线（SBOM + 哈希清单）比对，发现异常立即告警并重启容器。
6. **镜像签名验证**：在 K8s 部署配置中启用 `cosign` 镜像签名验证，仅允许启动已签名镜像。

#### 3.3.4 管理整改措施

1. **修订镜像构建规范**：在《容器镜像构建规范 V2.0》中新增"Python 服务可信度量"章节。
2. **更新 CI/CD 流水线**：在 GitLab CI 流水线中增加"生成 SBOM + 哈希清单 + 镜像签名"步骤。
3. **建立可信基线维护流程**：制定《Python 服务可信基线维护规程》，明确依赖升级、基线更新流程。

### 3.4 整改项 ZG-004：个人信息保护

#### 3.4.1 问题描述

等保测评项 8.1.4.11 + 密评个人信息保护项：元数据目录中约 18% 个人信息字段（共 347 个字段）未打标 PIILabel，3 张含身份证号的表（`user_identity`、`customer_kyc`、`employee_profile`）未配置动态脱敏策略，存在数据泄露与《个人信息保护法》合规风险。

#### 3.4.2 整改目标

完善元数据 PIILabel 标识覆盖全部个人信息字段，对身份证号、手机号、银行卡号等敏感字段配置 SM4-CTR 动态脱敏策略，并增加访问审计。

#### 3.4.3 技术整改措施

1. **个人信息字段盘点**：组织数据治理部对全平台 1926 张表、48 万个字段进行个人信息字段盘点，识别出 1928 个个人信息字段。
2. **PIILabel 标识完善**：在元数据目录中对 1928 个个人信息字段打标 PIILabel，标识字段类型（身份证号 / 手机号 / 银行卡号 / 邮箱 / 地址 / 姓名 / 其他）与敏感等级（L1-L4）。
3. **脱敏策略配置**：在 SQL 网关层配置动态脱敏策略：
   - 身份证号：保留前 6 位 + 后 4 位，中间用 `*` 替换，底层存储采用 SM4-CTR 加密。
   - 手机号：保留前 3 位 + 后 4 位，中间用 `*` 替换。
   - 银行卡号：保留后 4 位，前面用 `*` 替换。
   - 邮箱：保留首字符 + 域名，本地名用 `*` 替换。
   - 地址：保留省市，详细地址用 `*` 替换。
   - 姓名：保留姓氏，名字用 `*` 替换。
4. **3 张表专项整改**：对 `user_identity`、`customer_kyc`、`employee_profile` 3 张表的身份证号字段配置 SM4-CTR 加密存储 + 动态脱敏策略，并迁移历史数据。
5. **访问审计增强**：在 SQL 网关层增加个人信息字段访问审计，记录访问人、访问时间、访问字段、脱敏前后值（仅记录哈希），审计日志保留 6 个月。
6. **权限收紧**：对个人信息字段的访问权限进行最小权限收紧，仅授权业务必要角色，删除冗余授权。
7. **数据分级标识**：在数据资产目录中对含个人信息的数据集打标"PII"分级标识，并配置相应的访问审批流程。

#### 3.4.4 管理整改措施

1. **修订数据分类分级制度**：在《数据引擎大数据平台数据分类分级管理制度 V2.0》中完善个人信息分类分级标准。
2. **修订脱敏管理规范**：制定《个人信息脱敏管理规范》，明确脱敏策略、脱敏审批、脱敏审计要求。
3. **修订访问控制策略**：在《数据访问控制策略》中增加个人信息字段访问的最小权限与审批要求。
4. **培训数据使用人员**：组织 4 场个人信息保护培训，覆盖全部数据使用人员，培训内容包括《个人信息保护法》、平台脱敏机制、访问审批流程。
5. **建立个人信息保护影响评估流程**：制定《个人信息保护影响评估（PIPIA）规程》，新增涉及个人信息的功能必须经过评估。

| --- | --- | --- |

  4. 审查数据资产目录，验证 PII 数据集打标。

### 3.5 整改项 ZG-005：网络设备国密证书升级

#### 3.5.1 问题描述

密评网络与通信层面"网络设备身份鉴别"项：10% 旧网络设备（共 4 台，2 台负载均衡 + 2 台旧防火墙）仍使用 RSA-2048 证书，未升级至 SM2 国密证书，存在过渡期合规风险。

#### 3.5.2 整改目标

全部 4 台旧网络设备完成国密证书升级，或通过 APISIX 网关侧统一封装为 SM2 证书，实现国密证书全覆盖。

#### 3.5.3 技术整改措施

1. **设备能力评估**：对 4 台旧网络设备进行国密证书支持能力评估，2 台负载均衡设备（F5 BIG-IP v16.1）原生支持国密证书，2 台旧防火墙（某厂商 v6.5）不支持。
2. **负载均衡设备证书升级**：在 2 台 F5 BIG-IP 上导入 SM2 证书（由公司 PKI 签发），配置客户端 SSL Profile 使用 SM2 证书，启用 GM SSL 协议。
3. **旧防火墙方案调整**：2 台旧防火墙不支持国密证书，采用"APISIX 网关侧统一封装"方案：
   - 在 APISIX 网关与旧防火墙之间增加一层国密代理（基于 GmSSL 实现）。
   - 客户端到 APISIX 网关使用 SM2 证书建立 TLS 1.3 + GM 连接。
   - APISIX 网关到旧防火墙使用 RSA 证书建立内部 TLS 连接（内网可信通道）。
   - 旧防火墙到后端服务使用 SM2 证书建立 GM 连接。
4. **证书签发**：由公司 PKI（基于 CFSSL + 国密扩展）签发 SM2 证书，证书有效期 1 年，启用 OCSP 在线校验。
5. **证书分发与轮换**：建立证书自动化分发与轮换机制，使用 `cert-manager` + 自研 GM issuer 实现证书自动签发、分发、轮换。
6. **兼容性测试**：完成国密证书升级后，与全部上下游系统进行兼容性测试，确保业务正常。

#### 3.5.4 管理整改措施

1. **修订采购规范**：在《网络设备采购技术规范》中明确"必须支持国密 SM2 证书"为强制要求。
2. **制定证书管理规范**：制定《商用密码证书管理规范》，明确证书签发、分发、轮换、销毁流程。
3. **建立证书监控**：在监控中心增加证书有效期监控，证书到期前 30 天告警。
4. **培训运维人员**：组织 1 场国密证书管理培训，覆盖网络运维与基础设施运维人员。

## 〇、评分标准与综合公式

| 维度 | 1分 | 5分 | 说明 |
| --- | --- | --- | --- |
| 风险性 | 极低（改了不易出事） | 极高（改了极易破坏现有功能） | 越低越好 |
| 收益性 | 极低（改了价值小） | 极高（改了价值大） | 越高越好 |
| 成本性 | 极低（改了省时省力） | 极高（改了费时费力） | 越低越好 |
| 兼容性 | 极差（对现有系统/浏览器不兼容） | 极好（兼容无忧） | 越高越好 |
| 持续性 | 极差（改了难长期维护） | 极好（一劳永逸） | 越高越好 |

**综合优先级 = 收益性 + 兼容性 + 持续性 − 风险性 − 成本性**

> 综合分越高越优先实施。取值范围 [-8, 15]。

## 二、逐项五维评审

### U-01：暗色主题覆写不全面（15个Vue文件硬编码 `background:#fff`）

**修复思路**：将 `#fff` 替换为 `var(--ds-bg-surface)`，从根源消除硬编码。

| 维度 | 分数 | 依据 |
| --- | --- | --- |
| 风险性 | **2** | design-tokens.css 已定义 `--ds-bg-surface: #ffffff`（亮）→ `#1e293b`（暗），theme.ts 双选择器机制成熟（`data-theme` + `prefers-color-scheme`）。替换是纯 CSS 变量替换，亮色下渲染结果不变。风险点：需确认 20 处 `#fff` 均为"表面背景"语义而非"反白文字/渐变端点"——grep 结果显示均为 `background:` 属性，语义明确，无歧义。 |
| 收益性 | **4** | 暗色主题是已上线功能（theme.ts 完整 + localStorage 持久化），15个文件白底不跟随是**已上线功能的可见缺陷**，修复后暗色体验完整，用户可感知。 |
| 成本性 | **2** | 20处机械替换，可用正则批量处理。每处需人工确认语义（区分 `#fff` 表面 vs `#fff7ed` 警告底色——后者不应替换），但总量小。 |
| 兼容性 | **5** | `var()` 浏览器兼容性已验证（项目已大量使用 `--ds-*` 变量），无新兼容风险。 |
| 持续性 | **5** | 从根源消除硬编码，后续新页面只要用 `var(--ds-bg-surface)` 即自动支持暗色，一劳永逸。 |

**综合分：4 + 5 + 5 − 2 − 2 = 10**

**结论**：✅ **推荐实施**。低风险高收益，机制成熟，是5个问题中ROI第二高的。

**实施建议**：
1. 仅替换 `background: #fff;` / `background:#fff` → `background: var(--ds-bg-surface);`，**不替换** `#fff7ed`（警告底色）、`#fff3cd`（提示底色）、`#fffbeb`（琥珀底色）等带色调的值。
2. 替换后跑暗色主题视觉回归（重点查 TopBar、StatusBar、SearchPortal、TenantManagement 等含 `#fff` 的组件）。

### U-02：响应式断点不统一（5种值 → 规范3档640/1024/1440px）

**修复思路**：在 design-tokens.css 定义断点常量，统一所有 `@media` 查询。

| 维度 | 分数 | 依据 |
| --- | --- | --- |
| 风险性 | **4** | ①断点位移（1100→1024、720→640）会改变所有页面的响应式触发时机，平板/移动端在临界宽度（1024px、640px附近）可能布局错位。②**硬断言测试** AuthDashboardAnalyze.test.ts 断言 1100px/720px，改断点**必破坏测试**，需同步改测试。③涉及30+个Vue文件的 `@media` 块。 |
| 收益性 | **3** | 断点统一是规范要求（§9），但当前 1100/720px 两档已覆盖28个页面且工作正常，收益主要是"规范性/可维护性"而非"功能性/用户感知"。 |
| 成本性 | **3** | 需改30+个 `@media` 查询 + 更新硬断言测试 + 视觉回归验证3个断点区间（<640 / 640-1024 / 1024-1440 / >1440）。**注意：CSS自定义属性不能直接用于 `@media` 查询条件**（`@media (max-width: var(--bp))` 无效），纯CSS方案需用 `@custom-media`（CSS Extensions）或预处理器，或退而求其次在规范中定义常量供人工参照。 |
| 兼容性 | **4** | 断点值改变不影响浏览器兼容，只影响布局触发时机。 |
| 持续性 | **4** | 统一后新页面有明确断点参照。但 CSS 原生无法 `@media (max-width: var())`，断点常量只能作为**文档参照**而非**代码约束**，持续性打折。 |

**综合分：3 + 4 + 4 − 4 − 3 = 4**

**结论**：⚠️ **可实施但需谨慎**。中风险中收益，最大障碍是硬断言测试和 CSS 原生断点常量限制。建议作为第二阶段任务。

**实施建议**：
1. 先改测试：将 AuthDashboardAnalyze.test.ts 的 1100px/720px 断言更新为 1024px/640px。
2. 用全局正则替换 `@media (max-width: 1100px)` → `@media (max-width: 1024px)`，`@media (max-width: 720px)` → `@media (max-width: 640px)`。
3. 单独处理 1280px（main.css 1处）、960px（Login.vue 1处）、900px（SearchPortal.vue 1处）——逐处确认靠档方向。
4. 在 design-tokens.css 注释中记录断点常量（供人工参照），并在 lint 规则中禁止非标准断点值。

### U-03：动画一致性（非标准曲线 + 9s超长动画 + 无 `prefers-reduced-motion` 降级）

**修复思路**：统一曲线为 `var(--ease-smooth/spring)`，添加 `prefers-reduced-motion` 降级。

| 维度 | 分数 | 依据 |
| --- | --- | --- |
| 风险性 | **2** | ①曲线替换是视觉微调（ease-in-out→var(--ease-smooth) 差异极小）。②9s→4s 改时长影响登录页/注册页背景动画节奏，但4s仍为循环动画，视觉可接受。③`prefers-reduced-motion` 降级是**纯增量**（新增全局 `@media` 块），不改变现有默认行为，零回归风险。 |
| 收益性 | **5** | 三重收益：①`prefers-reduced-motion` 降级是 **WCAG 2.1 无障碍合规要求**，规范§7.1明确要求，缺失是合规缺陷。②9s超长动画违反规范（最长4s gridPulse），且影响首次加载体验。③非标准曲线破坏动效一致性。修复收益高（合规+体验+一致性）。 |
| 成本性 | **2** | ①非标准曲线约5处替换（DevMl/ChatPanel/DagVisualizer/Register/Login/SearchPortal）。②9s动画2处改时长（Register.vue regFloat、Login.vue orbFloat）。③`prefers-reduced-motion` 新增1个全局 `@media` 块——**规范§7.1已给出完整代码**，直接复制即可。 |
| 兼容性 | **5** | `prefers-reduced-motion` 浏览器支持率 >95%（caniuse），`var()` 曲线已在 TopBar/Sidebar/StatusBar 使用，无新兼容风险。 |
| 持续性 | **5** | 全局降级块一次添加永久生效（所有动画自动降级），曲线统一后新动画有明确参照变量。 |

**综合分：5 + 5 + 5 − 2 − 2 = 11**

**结论**：✅ **最优先实施**。低风险高收益，`prefers-reduced-motion` 是无障碍合规必须，且规范已给出可直接复用的代码。是5个问题中ROI最高的。

**实施建议**：
1. **第一步（零风险）**：在 main.css 末尾添加规范§7.1的 `prefers-reduced-motion: reduce` 全局降级块（直接复制规范代码）。
2. **第二步**：将 `ease-in-out` / `ease` / `linear` 替换为对应 `var(--ease-smooth)`（shimmer 骨架屏的 `linear` 可保留，规范§7第5项明确 shimmer 用 linear）。
3. **第三步**：将 `regFloat 9s` / `orbFloat 9s` 改为 `4s`（与规范最长 gridPulse 4s 对齐）。
4. 跑登录页/注册页视觉回归确认动画节奏可接受。

### U-05：4px间距阶梯未执行（main.css 90处 + Vue 434处非4倍数）

**修复思路**：按映射表分批替换非4倍数值，先消除小数像素。

| 维度 | 分数 | 依据 |
| --- | --- | --- |
| 风险性 | **5** | ①524处间距修改，每处都可能影响布局。②规范§4.4.5**明确警告**："当前仅记录映射，**不修改 main.css 实际值**，避免破坏现有布局"。③13px→12px、14px→16px 等**靠档会改变元素尺寸**，可能触发溢出/换行/错位/对齐失效，尤其 `width`/`height` 类的非4倍数（如 26px→28px 改图标尺寸）。④涉及71个Vue文件，回归面巨大。 |
| 收益性 | **2** | 4px网格是规范要求，但**当前布局已工作正常**，收益主要是"规范性/审美一致性"。用户无感知，无功能收益。 |
| 成本性 | **5** | ①524处修改。②每处需判断靠档方向（7px→8px向上、9px→8px向下、10px→8或12二选一、13px→12px、18px→16或20二选一），**靠档判断无自动化方案**，需逐处人工确认布局紧凑度。③71个Vue文件 + main.css 视觉回归。④小数像素（12.5px等）取整需确认渲染差异。 |
| 兼容性 | **3** | 像素值改变不影响浏览器兼容，但可能影响第三方组件（如ECharts、AG-Grid）的布局假设，导致嵌入组件错位。 |
| 持续性 | **3** | 修改后需建立 stylelint 规则（`declaration-property-value-allowed-list`）防止回退，但524处的靠档判断无自动化方案，人工维护成本高，且新开发者可能再次引入非4倍数。 |

**综合分：2 + 3 + 3 − 5 − 5 = −2**

**结论**：❌ **不建议本批次实施**。高风险低收益，规范文档本身建议暂缓。综合分为负，ROI最低。

**替代建议**：
1. **本批次仅做**：在 stylelint 中添加 4px 间距规则（`declaration-property-value-allowed-list` 限制 padding/margin/gap 为4倍数），**仅对新增代码生效**（不追溯存量），防止增量回归。
2. **小数像素单独处理**：12.5px / 11.5px / 13.5px / 10.5px 等小数像素（约70处）可单独消除（取整风险低于靠档），但需确认渲染差异。
3. **存量迁移**：留待组件级重构时逐处替换（规范§4.4.5建议的方案），不搞批量替换。

3. **CSS 原生断点常量限制**：CSS 自定义属性不能直接用于 `@media` 查询条件（`@media (max-width: var(--bp))` 无效）。U-02 的"在 design-tokens.css 定义断点常量"只能作为**文档参照**，无法成为**代码约束**，需靠 stylelint 规则补足。

5. **`prefers-reduced-motion` 是合规必须**：U-03 中的降级块缺失是 WCAG 2.1 无障碍合规缺陷，建议无论其他问题是否实施，**至少先补全此降级块**（零风险纯增量）。

## 六、结论

批次3的5个UI规范问题中：
- **2个推荐立即实施**（U-03 动画一致性、U-01 暗色覆写），综合分10-11，低风险高收益。
- **2个可实施但需分阶段/谨慎**（U-02 响应式断点、U-07 字号阶梯），综合分2-4，中风险中收益。

## 第1章 部署架构

### 1.1 整体部署架构

平台基于 Kubernetes + Helm + ArgoCD 部署，整体架构：

```text
┌──────────────────────────────────────────────────────────┐
│  Git 仓库（deploy/argocd/<env>/）                          │
│  └─ values-base.yaml + 环境覆盖 + 租户覆盖                  │
└────────────────────────┬─────────────────────────────────┘
                         │ GitOps 同步
                         ▼
┌──────────────────────────────────────────────────────────┐
│  ArgoCD 控制器（L0.15）                                    │
│  └─ 应用同步状态可视化 + 一键回滚                          │
└────────────────────────┬─────────────────────────────────┘
                         │ Helm 渲染
                         ▼
┌──────────────────────────────────────────────────────────┐
│  K8s 集群（3 master + N worker）                           │
│  ├─ dataengine-system 命名空间（平台组件）                 │
│  ├─ tenant-<id> 命名空间（租户隔离）                       │
│  └─ 监控/日志/告警命名空间                                 │
└──────────────────────────────────────────────────────────┘
```

### 1.2 K8s 集群规划

#### 1.2.1 节点规划

| 角色 | 数量 | 规格 | 用途 |
| --- | --- | --- | --- |
| master | 3（生产）/ 1（测试） | 8C 16G 200G SSD | K8s 控制面 |
| worker | ≥ 3 | 16C 64G 500G SSD | 平台组件 + 引擎 |
| 引擎节点 | 按需 | 32C 128G 1T NVMe | Spark/Flink/Trino/Doris |
| 存储节点 | 按需 | 8C 32G 多盘 | 数据湖（HDFS/对象存储） |

#### 1.2.2 关键组件

| 组件 | 用途 | 命名空间 |
| --- | --- | --- |
| ArgoCD | GitOps 发布 | `argocd` |
| cert-manager | 证书管理 | `cert-manager` |
| Prometheus | 指标采集 | `monitoring` |
| Grafana | 大盘展示 | `monitoring` |
| Loki | 日志聚合 | `monitoring` |
| Alertmanager | 告警路由 | `monitoring` |
| Spark Operator | Spark 作业管理 | `dataengine-system` |
| Flink Operator | Flink 作业管理 | `dataengine-system` |
| Trino Coordinator | Trino 查询协调 | `dataengine-system` |
| Doris Operator | Doris 集群管理 | `dataengine-system` |

### 1.4 ArgoCD GitOps

#### 1.4.1 GitOps 流程

1. 运维修改 `deploy/argocd/<env>/values.yaml`。
2. 提交 PR，触发评审。
3. 评审通过合并到主分支。
4. ArgoCD 检测到变更，自动同步到集群。
5. 同步状态可在 ArgoCD UI 查看。

#### 1.4.2 ArgoCD 常用操作

```bash
# 命令示例：查看应用同步状态
argocd app list
argocd app get <app-name>

# 命令示例：手动同步
argocd app sync <app-name>

# 命令示例：回滚到上一版本
argocd app rollback <app-name>

# 命令示例：查看同步历史
argocd app history <app-name>
```

### 1.5 多集群联邦

生产环境采用 Karmada 多集群联邦：

- 主集群：承载控制面 + 元数据库。
- 数据集群：按租户/引擎分布，承载计算与存储。
- 灾备集群：异地容灾，异步复制。
- 跨集群调度：Karmada 纳管，按策略分发作业。

## 第2章 日常运维

### 2.1 健康检查

#### 2.1.1 每日巡检清单

| 检查项 | 命令/路径 | 期望状态 | 处置 |
| --- | --- | --- | --- |
| 节点状态 | `kubectl get nodes` | 全 Ready | NotReady 节点排查 |
| 控制面 Pod | `kubectl get pods -n dataengine-system` | 全 Running | 重启失败 Pod |
| 引擎 Pod | `kubectl get pods -n tenant-*` | 全 Running | 重启失败 Pod |
| 监控告警 | Grafana Alert 面板 | 无活跃告警 | 按 SOP 处置 |
| 磁盘使用 | `kubectl df` / Grafana | < 80% | 清理或扩容 |
| CPU 使用 | Grafana 集群大盘 | < 80% | 扩容或限流 |
| 内存使用 | Grafana 集群大盘 | < 80% | 扩容或调优 |
| 备份任务 | 备份大盘 | 昨晚成功 | 重跑备份 |
| 证书到期 | cert-manager 大盘 | > 30 天 | 续期 |
| 密钥到期 | 密钥管理大盘 | > 30 天 | 轮转 |

#### 2.1.2 巡检脚本示例

```bash
# 命令示例：每日巡检脚本
#!/bin/bash
echo "=== 节点状态 ==="
kubectl get nodes -o wide | grep -v Ready

echo "=== 异常 Pod ==="
kubectl get pods -A | grep -v Running | grep -v Completed

echo "=== 磁盘使用 ==="
kubectl top nodes --sort-by=memory

echo "=== 最近告警 ==="
kubectl logs -n monitoring alertmanager-0 --tail=20
```

### 2.2 日志查看

#### 2.2.1 kubectl 日志

```bash
# 命令示例：查看 Pod 日志
kubectl logs <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace> --tail=100
kubectl logs <pod-name> -n <namespace> --since=1h
kubectl logs <pod-name> -n <namespace> -c <container>
kubectl logs -f <pod-name> -n <namespace>  # 实时跟随
```

#### 2.2.2 Loki 日志查询

通过 Grafana Log 面板，使用 LogQL 查询：

```logql
# 查询 dataengine-system 命名空间的 ERROR 日志
{namespace="dataengine-system"} |= "ERROR"

# 查询某 Pod 最近 1 小时日志
{pod="platform-console-xxx"} | json | line_format "{{.level}} {{.msg}}"

# 查询所有命名空间的异常
{namespace=~"tenant-.*"} |= "Exception" | json
```

#### 2.2.3 日志保留策略

| 类型 | 热数据 | 冷归档 | 总保留 |
| --- | --- | --- | --- |
| 平台日志 | 7 天 | 180 天 | 187 天 |
| 引擎日志 | 3 天 | 90 天 | 93 天 |
| 审计日志 | 30 天 | 7 年 | 7 年 + 30 天 |

### 2.3 配置变更

#### 2.3.1 GitOps 变更流程

1. 在 Git 仓库 `deploy/argocd/<env>/` 修改 values.yaml。
2. 本地 `helm template` 验证渲染结果。
3. 提交 PR，描述变更内容与影响。
4. 评审人评审（生产环境须 ≥ 2 人评审）。
5. 合并后 ArgoCD 自动同步。
6. 在 ArgoCD UI 观察同步状态。
7. 同步后验证功能正常。

#### 2.3.2 紧急变更

- 紧急情况可 ArgoCD 手动同步（事后补 PR）。
- 紧急变更须 24 小时内补 PR 与评审。
- 紧急变更记录入变更管理台账。

#### 2.3.3 变更审计

- Git 历史：所有变更可追溯。
- ArgoCD 同步历史：同步时间/结果/操作人。
- 审计日志：配置变更入审计。

## 第3章 监控告警

### 3.1 监控架构

基于 L0.9 可观测基座，三层监控：

```text
采集层：Node Exporter + Kube State Metrics + 组件 Exporter + 业务 Exporter
   ↓
存储层：Prometheus（指标）+ Loki（日志）+ Tempo（追踪）
   ↓
展示层：Grafana 大盘（平台视图 + 租户视图）
   ↓
告警层：Alertmanager → 邮件/钉钉/短信/电话
```

### 3.2 监控大盘

#### 3.2.1 平台总览大盘

路径：Grafana → 平台总览

包含面板：

- 集群健康：节点数/Pod 数/异常数。
- 资源使用：CPU/内存/磁盘/网络。
- 租户状态：租户数/活跃租户/冻结租户。
- 作业统计：运行中/成功/失败/排队。
- 引擎状态：Spark/Flink/Trino/Doris 健康。

#### 3.2.2 集群详情大盘

- 节点详情：每节点 CPU/内存/磁盘/Pod 数。
- Pod 详情：Pod 资源使用/重启次数/OOM。
- 网络流量：入向/出向带宽。
- 存储详情：PV 使用率/IOPS/延迟。

#### 3.2.3 引擎监控大盘

| 引擎 | 关键指标 |
| --- | --- |
| Spark | 作业数/Executor 数/Task 失败率/Shuffle 量 |
| Flink | 作业数/Checkpoint 延迟/反压/状态大小 |
| Trino | 查询数/查询延迟/排队数/内存使用 |
| Doris | 查询数/查询延迟/BE 负载/物化视图命中 |

#### 3.2.4 租户视图大盘

- 单租户资源使用（CPU/内存/存储）。
- 单租户作业统计。
- 单租户账单与趋势。

### 3.3 告警规则

#### 3.3.1 告警分级

| 级别 | 触发条件 | 通知方式 | 响应时效 |
| --- | --- | --- | --- |
| P0 | 控制面不可用 / 数据丢失风险 | 电话 + 短信 + 钉钉 | 5 分钟 |
| P1 | 引擎不可用 / 大量作业失败 | 短信 + 钉钉 | 15 分钟 |
| P2 | 单租户异常 / 性能下降 | 钉钉 + 邮件 | 30 分钟 |
| P3 | 容量预警 / 证书到期 | 邮件 | 4 小时 |

#### 3.3.2 典型告警规则

```yaml
# 告警规则示例：节点 NotReady
- alert: NodeNotReady
  expr: kube_node_status_condition{condition="Ready",status="true"} == 0
  for: 5m
  labels:
    severity: P0
  annotations:
    summary: "节点 {{ $labels.node }} NotReady"
    description: "节点已 NotReady 超过 5 分钟，可能影响调度"

# 告警规则示例：Pod 重启次数过多
- alert: PodRestartTooMany
  expr: increase(kube_pod_container_status_restarts_total[1h]) > 5
  for: 5m
  labels:
    severity: P1
  annotations:
    summary: "Pod {{ $labels.pod }} 1 小时内重启超过 5 次"

# 告警规则示例：磁盘使用率高
- alert: DiskUsageHigh
  expr: 100 - (node_filesystem_avail_bytes / node_filesystem_size_bytes * 100) > 80
  for: 10m
  labels:
    severity: P2
  annotations:
    summary: "节点 {{ $labels.instance }} 磁盘使用率超过 80%"
```

#### 3.3.3 告警抑制与静默

- **抑制**：同源告警 5 分钟内去重，避免告警风暴。
- **静默**：维护窗口临时静默，路径 Alertmanager → Silence。
- **路由**：按标签（severity/tenant/engine）路由到不同值班组。

### 3.4 告警响应 SOP

收到告警后按以下 SOP 响应：

1. **确认告警**（1 分钟）：查看 Grafana 上下文，确认告警真实性。
2. **判断影响面**（2 分钟）：确定影响哪些租户/作业/用户。
3. **定位根因**（5–10 分钟）：kubectl / 日志 / 大盘定位。
4. **执行处置**（按需）：重启 / 扩容 / 回滚 / 切流 / 限流。
5. **验证恢复**（2 分钟）：告警消除 + 功能验证。
6. **复盘归档**（24 小时内）：复盘报告含根因/处置/改进。

> 详细 SOP 见 `design/运维/监控告警SOP.md`。

### 3.5 监控告警 FAQ

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| Grafana 大盘空白 | 数据源未配置 / 时间范围错 | 检查数据源与时间范围 |
| 告警未触发 | 规则未生效 / for 持续时间未到 | 检查规则状态 |
| 告警风暴 | 抑制未配置 | 配置抑制规则 |
| 告警通知不到 | 通知渠道配置错 | 检查 Alertmanager 配置 |

## 第4章 故障排查

### 4.1 故障排查通用流程

```text
1. 现象确认 → 2. 影响面判断 → 3. 根因定位 → 4. 处置 → 5. 验证 → 6. 复盘
```

#### 4.1.1 常用排查命令

```bash
# 命令示例：集群级排查
kubectl get nodes                    # 节点状态
kubectl get pods -A | grep -v Running  # 异常 Pod
kubectl get events -A --sort-by=.lastTimestamp | tail -20  # 最近事件

# 命令示例：Pod 级排查
kubectl describe pod <pod> -n <ns>   # Pod 详情（含事件）
kubectl logs <pod> -n <ns> --previous  # 上次崩溃日志
kubectl top pod <pod> -n <ns>        # 资源使用

# 命令示例：服务级排查
kubectl get svc -n <ns>              # 服务列表
kubectl get endpoints -n <ns>        # 端点（后端 Pod）
kubectl get ingress -n <ns>          # Ingress
```

### 4.2 常见故障场景

#### 4.2.1 场景 1：控制台 502

**现象**：访问控制台返回 502。

**排查步骤**：

1. `kubectl get pods -n dataengine-system | grep console`：检查控制台 Pod。
2. `kubectl logs <console-pod> -n dataengine-system --tail=50`：查看日志。
3. `kubectl get ingress -n dataengine-system`：检查 Ingress。
4. `kubectl get svc -n dataengine-system | grep console`：检查 Service。
5. `kubectl get endpoints -n dataengine-system | grep console`：检查 Endpoints。

**常见根因与处置**：

| 根因 | 处置 |
| --- | --- |
| 控制台 Pod 崩溃 | `kubectl delete pod <pod>` 触发重启 |
| Ingress 配置错 | 修正 Ingress 配置 |
| Service 无 Endpoints | 检查 Pod 标签与 Service selector |
| 后端 Pod 资源不足 | 扩容控制台副本数 |

#### 4.2.2 场景 2：Spark 作业全部失败

**现象**：所有 Spark 作业提交后立即失败。

**排查步骤**：

1. `kubectl get pods -n dataengine-system | grep spark-operator`：检查 Operator。
2. `kubectl logs <spark-operator-pod> -n dataengine-system --tail=50`：查看日志。
3. `kubectl get pods -n tenant-<id> | grep spark`：检查引擎 Pod。
4. 查看 Grafana Spark 大盘：是否有资源不足或队列满。

**常见根因与处置**：

| 根因 | 处置 |
| --- | --- |
| Spark Operator 异常 | 重启 Operator Pod |
| 资源队列满 | 扩容集群或调整队列 |
| 镜像拉取失败 | 检查镜像仓库与网络 |
| 配置错误 | 检查最近配置变更并回滚 |

#### 4.2.3 场景 3：某租户无法登录

**现象**：某租户所有用户无法登录控制台。

**排查步骤**：

1. 检查租户状态：`管理 → 租户管理`，是否被冻结。
2. 检查租户命名空间：`kubectl get ns tenant-<id>`。
3. 检查认证服务：`kubectl get pods -n dataengine-system | grep auth`。
4. 查看认证服务日志：是否有该租户错误。

**常见根因与处置**：

| 根因 | 处置 |
| --- | --- |
| 租户被冻结 | 解冻租户 |
| 命名空间异常 | 重建命名空间 |
| 认证服务异常 | 重启认证服务 |
| LDAP/IdP 不通 | 检查外部 IdP 连通性 |

#### 4.2.4 场景 4：Flink 作业 Checkpoint 失败

**现象**：Flink 作业 Checkpoint 持续失败，最终作业失败。

**排查步骤**：

1. 查看 Flink 作业 WebUI：Checkpoint 失败原因。
2. 检查 Checkpoint 存储：`kubectl get pv` / 对象存储连通性。
3. 检查状态大小：是否状态过大导致超时。
4. 查看 Flink TaskManager 日志：是否有 OOM 或反压。

**常见根因与处置**：

| 根因 | 处置 |
| --- | --- |
| Checkpoint 存储异常 | 修复存储 / 切换存储 |
| 状态过大 | 增大 Checkpoint 超时 / 清理过期状态 |
| TaskManager OOM | 增大 TM 内存 / 优化作业 |
| 反压 | 优化作业逻辑 / 增加并行度 |

#### 4.2.5 场景 5：磁盘空间不足

**现象**：节点磁盘使用率 > 90%，Pod 无法写入。

**排查步骤**：

1. `kubectl describe node <node>`：查看节点磁盘。
2. `df -h` 登录节点查看具体路径。
3. 找出大文件：`du -sh /* 2>/dev/null | sort -h | tail`。
4. 检查日志/镜像/中间数据是否堆积。

**常见根因与处置**：

| 根因 | 处置 |
| --- | --- |
| 日志堆积 | 清理旧日志 / 调整保留策略 |
| 镜像堆积 | `crictl rmi --prune` 清理未用镜像 |
| 中间数据 | 清理已完成作业的中间数据 |
| 数据湖膨胀 | 扩容存储 / 数据归档冷存储 |

> 更多故障场景见 `design/运维/故障排查手册.md`。

### 4.3 故障复盘

故障恢复后 24 小时内完成复盘报告：

| 项 | 内容 |
| --- | --- |
| 故障编号 | INC-YYYYMMDD-NN |
| 发生时间 | yyyy-MM-dd HH:mm |
| 检测时间 | 告警触发时间 |
| 恢复时间 | 业务恢复时间 |
| 影响面 | 受影响租户/作业/用户数 |
| 根因 | 技术根因 + 管理根因 |
| 处置过程 | 时间线 + 操作 |
| 改进项 | 短期/中期/长期改进 |

## 第5章 备份恢复

### 5.1 备份策略

#### 5.1.1 备份对象与频率

| 对象 | 频率 | 保留 | 目标 | RPO |
| --- | --- | --- | --- | --- |
| 元数据库 | 每日全量 + 每小时增量 | 7 日 + 4 周 + 12 月 | 对象存储（跨区域） | 1 小时 |
| 配置（Git） | 实时（Git push） | 永久 | Git 仓库 + 镜像 | 0 |
| 数据湖 | 每日增量 | 7 日 + 4 周 | 对象存储（跨区域） | 24 小时 |
| 作业状态 | Checkpoint/Savepoint | 按需 | 对象存储 | 按作业 |
| 审计日志 | 实时同步 | 7 年 | 对象存储 + 冷归档 | 0 |

#### 5.1.2 备份目标

- 主备份：同区域对象存储（低延迟）。
- 跨区域备份：异地对象存储（容灾）。
- 冷归档：低成本存储（长期保留）。

### 5.2 恢复操作

#### 5.2.1 元数据库恢复

场景：元数据库误删表，须恢复到 1 小时前。

```bash
# 命令示例：元数据库 PITR 恢复
# 1. 停止平台服务
kubectl scale deploy platform-console -n dataengine-system --replicas=0

# 2. 恢复元数据库到指定时间点
debdp db restore --target-time "2026-08-18 13:00:00"

# 3. 校验数据
debdp db verify --table <table>

# 4. 恢复平台服务
kubectl scale deploy platform-console -n dataengine-system --replicas=1
```

#### 5.2.2 数据湖恢复

场景：某张 Iceberg 表被误删，须恢复。

```sql
-- SQL功能名：Iceberg time travel 恢复
-- 1. 查看表历史快照
SELECT snapshot_id, committed_at FROM iceberg.table_history('db.dwd_order');

-- 2. 回滚到指定快照
CALL iceberg.rollback_to_snapshot('db.dwd_order', <snapshot_id>);

-- 3. 校验数据
SELECT count(*) FROM db.dwd_order;
```

#### 5.2.3 作业状态恢复

场景：Flink 作业失败，须从 Savepoint 恢复。

```bash
# 命令示例：Flink 从 Savepoint 启动
flink run -s hdfs:///savepoints/flink-job-xxx -d -p 4 my-job.jar
```

### 5.3 灾备切换

#### 5.3.1 灾备架构

- 主集群：日常承载业务。
- 灾备集群：异地部署，元数据与数据异步复制。
- DNS：主集群域名解析到主集群 IP，切换时改解析。

#### 5.3.2 切换前提

- 主集群不可恢复（如机房故障）。
- 灾备集群数据已达 RPO（核心数据 < 1 小时延迟）。
- 经应急决策委员会批准。

#### 5.3.3 切换步骤

1. 确认主集群不可恢复。
2. 校验灾备集群数据完整性。
3. DNS 切换：主域名解析到灾备集群 IP。
4. 灾备集群提升为主：开启写入、启动调度。
5. 通知租户与用户。
6. 验证业务功能正常。
7. 故障恢复后，反向同步再回切。

#### 5.3.4 切换演练

- 每年一次全量灾备切换演练。
- 演练记录 RTO 实测值，目标 < 4 小时。
- 演练后复盘改进。

> 详细灾备方案见 `design/运维/灾备方案.md`。

#### 6.1.1 升级前准备

1. 阅读 Release Notes，了解变更内容与兼容性。

#### 6.2.3 数据回滚

- 元数据库：PITR 恢复到升级前时间点。
- 配置：Git 回滚到升级前 commit。

#### 6.2.4 回滚条件

- 升级后出现 P0 故障。

### 6.3 灰度发布

#### 6.3.1 灰度策略

## 第7章 安全运维

### 7.1 证书管理

#### 7.1.1 证书对象

| 证书 | 用途 | 签发 | 续期 |
| --- | --- | --- | --- |
| Ingress TLS | 控制台 HTTPS | cert-manager / 国密 CA | 自动 / 30 天前告警 |
| 引擎 mTLS | 引擎内部通信 | cert-manager | 自动 90 天轮转 |
| API Server | K8s API | K8s CA | 自动 |
| 国密证书 | 信创 TLS / 登录 | 国密 CA | 手动续期 |

#### 7.1.2 证书查看

```bash
# 命令示例：查看证书
kubectl get certificate -A
kubectl describe certificate <cert> -n <ns>

# 检查证书到期
openssl s_client -connect console.example.com:443 -showcerts < /dev/null 2>/dev/null | openssl x509 -noout -dates
```

#### 7.1.3 证书续期

- cert-manager 自动续期：到期前 30 天自动续。
- 国密证书手动续期：联系 CA 续期，更新 K8s Secret。
- 续期后须重启使用该证书的 Pod。

#### 7.1.4 证书撤销

密钥泄露时：

1. 撤销证书（联系 CA）。
2. 全量轮转相关证书。
3. 重启所有使用该证书的 Pod。
4. 审计泄露期间访问记录。

### 7.2 密钥轮转

#### 7.2.1 密钥对象

| 密钥 | 用途 | 轮转周期 |
| --- | --- | --- |
| 数据库密码 | 元数据库 / 引擎数据库 | 90 天 |
| API Token | 平台 API Token | 180 天 |
| 加密密钥 | 数据加密密钥（DEK/KEK） | 365 天 |
| SSH 密钥 | 节点 SSH 访问 | 180 天 |

#### 7.2.2 轮转方式

- **K8s Secret + External Secrets Operator**：从 Vault/AWS Secrets Manager 拉取，轮转源端即可。
- **Vault**：集中式密钥管理，自动轮转插件。
- **手动轮转**：生成新密钥 → 更新 K8s Secret → 重启 Pod → 验证。

#### 7.2.3 轮转流程

```bash
# 命令示例：数据库密码轮转
# 1. 生成新密码
NEW_PASSWORD=$(openssl rand -base64 24)

# 2. 更新数据库密码
mysql -u root -p -e "ALTER USER 'debdp'@'%' IDENTIFIED BY '$NEW_PASSWORD';"

# 3. 更新 K8s Secret
kubectl create secret generic db-secret \
  --from-literal=password=$NEW_PASSWORD \
  -n dataengine-system --dry-run=client -o yaml | kubectl apply -f -

# 4. 重启使用该 Secret 的 Pod
kubectl rollout restart deploy platform-console -n dataengine-system

# 5. 验证
kubectl logs deploy/platform-console -n dataengine-system --tail=10
```

### 7.3 安全扫描

#### 7.3.1 镜像扫描

工具：Trivy

```bash
# 命令示例：Trivy 镜像扫描
trivy image <image-name>:<tag>

# 扫描所有平台镜像
for img in $(kubectl get pods -A -o jsonpath='{..imageID}' | sort -u); do
  trivy image "$img" --severity HIGH,CRITICAL
done
```

扫描频率：每日 + 每次发布前。

#### 7.3.2 CIS 基准扫描

工具：kube-bench

```bash
# 命令示例：kube-bench CIS 扫描
kube-bench run --config-dir=/etc/kube-bench/
```

检查项：K8s 主节点与工作节点 CIS 安全基准。

#### 7.3.3 网络扫描

- 端口扫描：nmap 扫描集群节点，确认仅暴露必要端口。
- 网络策略审计：`kubectl get networkpolicy -A` 检查隔离策略。
- 入向流量：确认 Ingress 仅暴露 443（HTTPS）。

#### 7.3.4 漏洞处置

| 严重度 | 处置时效 | 方式 |
| --- | --- | --- |
| Critical | 24 小时 | 升级镜像 / 打补丁 |
| High | 7 天 | 升级镜像 / 打补丁 |
| Medium | 30 天 | 评估后处置 |
| Low | 季度 | 评估后处置 |

无法立即修复的可临时加白名单（须评审）。

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 证书到期告警 | 即将到期 | 续期证书 |

| 网络策略误拒 | 策略过严 | 调整策略并测试 |

## 第8章 运维常见问题 FAQ

### 8.1 通用问题

**Q1：kubectl 命令不可用怎么办？**
A：1) 检查 kubeconfig 是否过期；2) 联系平台管理员重新发放 kubeconfig；3) 检查网络到 API Server 连通性。

**Q2：Pod 一直 Pending 怎么办？**
A：`kubectl describe pod <pod>` 查看 Events，常见原因：资源不足 / 镜像拉取失败 / PVC 未绑定 / 节点污点。

**Q3：Pod 一直 CrashLoopBackOff 怎么办？**
A：`kubectl logs <pod> --previous` 查看上次崩溃日志，常见原因：配置错误 / 依赖服务不通 / OOM / 启动命令错。

**Q4：节点 NotReady 怎么办？**
A：1) SSH 登录节点检查 kubelet/容器运行时；2) 检查节点资源（磁盘/内存）；3) 重启 kubelet；4) 仍不行则驱逐 Pod 后重启节点。

### 8.2 升级问题

**Q5：升级后 Pod 不起怎么办？**
A：1) `kubectl describe pod` 看事件；2) 检查镜像版本与兼容性；3) 检查配置变更；4) 必要时回滚。

**Q6：升级后数据不一致怎么办？**
A：1) 检查数据迁移脚本是否执行成功；2) Iceberg time travel 校验；3) 必要时回滚到升级前。

### 8.3 监控问题

**Q7：Prometheus 数据丢失怎么办？**
A：1) 检查 Prometheus Pod 状态与存储；2) 检查采集 Target 是否 up；3) 短期数据丢失可接受，长期须排查根因。

**Q8：Grafana 大盘加载慢怎么办？**
A：1) 检查查询时间范围（缩短）；2) 检查数据源查询性能；3) 优化面板查询语句；4) 增加缓存。

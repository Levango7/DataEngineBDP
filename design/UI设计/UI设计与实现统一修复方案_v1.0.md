## 问题 1：文档与实现矛盾 — 深色 vs 浅蓝侧边栏

### 问题描述
设计系统规范 §2.4 明确要求"侧边栏采用深蓝黑垂直渐变"（`#0f172a → #1e293b`），但 `design-tokens.css` L126-128 实际定义浅蓝渐变（`#cbe2f8 → #b8d4f5 → #a6c8f0`），且 L124 注释自承认"浅蓝科技风侧边栏渐变"。文档与实现存在直接矛盾，破坏设计契约。

### 修复方案
1. **修改 `frontend/src/styles/design-tokens.css`**：
   - L126 `--ds-color-sidebar-bg-1: #cbe2f8` → `#0f172a`
   - L127 `--ds-color-sidebar-bg-2: #b8d4f5` → `#162238`（中间过渡色）
   - L128 `--ds-color-sidebar-bg-3: #a6c8f0` → `#1e293b`
   - L129 `--ds-color-sidebar-muted: #3b5a92` → `#94a3b8`（slate-400，与规范 §2.4 一致）
   - L124 注释改为"深色科技风侧边栏渐变 + 浅色次要文字"
2. **验证 `main.css` 中侧边栏样式**：确认 `.side` / `.sidebar` 背景引用 `--ds-color-sidebar-bg-*` 变量，无需额外改动
3. **视觉回归**：侧边栏文字色、hover 态、激活态在深色背景下的对比度

### 五维评审
- **成本性**：5/5 — 改 4 个变量值 + 1 行注释，< 1 人时
- **风险性**：2/5 — 侧边栏配色从浅蓝翻转为深色，子元素（文字、图标、hover）可见性需全量回归，存在中等破坏风险
- **收益性**：5/5 — 消除文档实现矛盾，恢复设计契约权威性，同时顺带解决对比度问题（深色背景上浅色文字对比度更高）
- **兼容性**：3/5 — 暗色模式已有深色定义（L272-283），亮色模式切换会显著改变视觉，需验证所有侧边栏子组件
- **可持续性**：5/5 — 变量驱动，后续主题切换零改动

**GAP = 20  → ✅ 推荐做**

## 问题 2：导航项膨胀 19 → 52

### 问题描述
IA 文档定义 19 项导航，`useNavGroups.ts` 实际定义 7 组 52 项（infra:7 + engine:8 + governance:7 + devtools:9 + tenant:5 + intelligent:6 + operations:10），膨胀 2.7 倍。导航项过多导致侧边栏滚动、认知负荷高、折叠模式下图标难辨识。

### 修复方案
1. **核对 IA 文档**：逐项比对 `design/详细设计/多平台多租户大数据平台_控制台信息架构_v0.1.md` 中定义的 19 项
2. **分类处理 52 项**：
   - **保留**：与 IA 文档对齐的核心项（约 19 项）
   - **合并**：相近功能合并（如 `/data-lineage` 合并入 `/lineage`，`/sql-workbench` 合并入 `/sql`）
   - **降级**：次要项移入二级菜单或"更多"抽屉（如 `/dev-tag`、`/ops-tpl`、`/ops-api`）
   - **移除**：未实现或废弃路由（需确认 router 中无对应路由）
3. **修改 `useNavGroups.ts`**：按上述分类重构 groups 数组，目标收敛至 19-25 项
4. **更新 i18n**：移除未使用导航项的翻译 key
5. **路由回归**：确认被合并/降级项的旧路径有重定向

### 五维评审
- **成本性**：2/5 — 需逐项核对 IA 文档 + 路由 + 权限 + 用户使用数据，1 人周+
- **风险性**：2/5 — 移除/合并导航项可能影响用户已有操作习惯，需确认每项的用户依赖度
- **收益性**：4/5 — 降低认知负荷，恢复 IA 契约，侧边栏不再滚动
- **兼容性**：2/5 — 移除项需重定向，合并项需更新书签/外链，存在兼容风险
- **可持续性**：4/5 — 收敛后更易维护，但需建立"新增导航项需 IA 评审"的流程

**GAP = 14  → ⚠️ 需讨论**（建议分阶段：先合并明显重复项，再评估降级/移除）

## 问题 3：Login.vue 13 处硬编码颜色

### 问题描述
`Login.vue` 中 13 处硬编码十六进制颜色（如 `#3b82f6`、`#ffffff`、`#1e293b` 等），未走 `--ds-*` token，导致主题切换时登录页不跟随，且违背规范 §2.5"禁止自定义灰度"。

### 修复方案
1. **grep 定位 13 处**：`rg "#[0-9a-fA-F]{3,6}" src/views/Login.vue`
2. **逐处替换为 token**：
   - `#3b82f6` → `var(--ds-color-primary-500)`
   - `#ffffff` / `#fff` → `var(--ds-text-inverse)` 或 `var(--ds-bg-surface)`（视语义）
   - `#1e293b` → `var(--ds-color-gray-800)`
   - `#0f172a` → `var(--ds-color-gray-900)`
   - 其他按 `design-tokens.css` 映射
3. **验证**：亮色/暗色模式下登录页视觉一致

### 五维评审
- **成本性**：5/5 — 13 处替换，< 1 人时
- **风险性**：4/5 — Login 页面独立性强，不影响主应用；仅需验证登录页两主题
- **收益性**：4/5 — 消除硬编码，支持主题切换，符合规范
- **兼容性**：5/5 — token 已在 design-tokens.css 定义，完全兼容
- **可持续性**：5/5 — 变量驱动，后续主题切换零改动

**GAP = 23  → ✅ 推荐做**

## 问题 4：main.css 50 处 #fff 硬编码

### 问题描述
`main.css` L2118 注释自承认"多个视图 scoped 样式写死 #fff 且未配暗色覆盖（扫描结果 50 处）"，导致暗色模式下白底卡片不反色，需用 184 处 `!important` 补丁集中反色（问题 6 的根因）。

### 修复方案
1. **grep 定位 50 处**：`rg "#fff\b|#ffffff\b" src/views/ src/components/ --include="*.vue"`
2. **按语义分类替换**：
   - 卡片/面板背景 `background: #fff` → `var(--ds-bg-surface)`
   - 文字色 `color: #fff` → `var(--ds-text-inverse)`
   - 边框 `border-color: #fff` → `var(--ds-bg-surface)`（视语境）
3. **逐文件替换并视觉回归**：每文件改后跑亮色/暗色回归
4. **验证暗色覆盖**：替换后暗色模式自动通过 token 切换生效，可逐步移除 `!important` 补丁

### 五维评审
- **成本性**：3/5 — 50 处分散在多文件，需逐文件替换 + 回归，1 人天+
- **风险性**：3/5 — 替换可能影响暗色模式覆盖层级，需逐视图验证
- **收益性**：4/5 — 消除暗色补丁根因，主题切换自动生效
- **兼容性**：4/5 — token 已定义，但 scoped 优先级可能变化
- **可持续性**：5/5 — 变量驱动，消除补丁依赖

**GAP = 19  → ✅ 推荐做**

## 问题 5：45 处硬编码 font-size（main.css）

### 问题描述
`main.css` 中 45 处 `font-size` 直接写像素值（如 `12px`、`14px`、`18px`、`24px`），未走 `--ds-font-size-*` token，违背规范 §4.4.4 字号阶梯。Vue 文件中另有 359 处（本方案暂不处理，列入后续迭代）。

### 修复方案
1. **按 §4.4.4 字号阶梯映射表替换**：
   - `12px` → `var(--ds-font-size-xs)`
   - `13px` → `var(--ds-font-size-sm)`
   - `14px` → `var(--ds-font-size-base)`
   - `16px` → `var(--ds-font-size-lg)`
   - `18px` → `var(--ds-font-size-xl)`
   - `20px` → `var(--ds-font-size-2xl)`
   - `24px` → `var(--ds-font-size-3xl)`
   - `10px` / `11px` → `var(--ds-font-size-xs)`（向上靠档）
2. **批量替换**：用 `replaceAll` 按值分批替换
3. **视觉回归**：确认字号无视觉差异（token 值与原值一致）

### 五维评审
- **成本性**：4/5 — 45 处批量替换，1 人天
- **风险性**：3/5 — 字号 token 值与原值一致，风险低；但 10px→12px、11px→12px 有视觉变化
- **收益性**：3/5 — 统一字号管理，但仅 main.css，Vue 文件 359 处未处理
- **兼容性**：4/5 — token 已定义，值基本一致
- **可持续性**：5/5 — 变量驱动，后续字号调整改 token 即可

**GAP = 19  → ✅ 推荐做**

## 问题 6：暗色模式 480 行 !important 补丁

### 问题描述
`main.css` L1160-2385 暗色块共 1226 行，含 184 处 `!important`，用于突破 scoped 优先级强制反色。根因是各视图 scoped 样式写死 `#fff`（问题 4），暗色模式无法通过变量切换自动生效，需 `!important` 补丁。非变量驱动式实现，违背规范 §8.1"主题切换仅需替换变量值"。

### 修复方案
1. **前置依赖**：先完成问题 4（50 处 #fff → token 替换），使暗色模式通过变量切换自动生效
2. **逐块移除 !important**：
   - L2120-2139 el-card 暗色覆盖：替换 token 后 el-card 自动反色，移除 `!important`
   - L2130-2139 各类 .card/.stat/.comp-card 暗色覆盖：同理
   - 逐块验证：每移除一块 `!important`，跑暗色模式回归
3. **保留必要 !important**：Element Plus 组件样式覆盖可能仍需少量 `!important`（EP 默认优先级高），但应从 184 处降至 < 20 处
4. **长期目标**：scoped 样式全部走 token 后，暗色块仅保留 `:root[data-theme='dark']` 变量定义，无组件级覆盖

### 五维评审
- **成本性**：1/5 — 涉及 1226 行重构，需逐处验证暗色覆盖，依赖问题 4 完成，> 1 人月
- **风险性**：1/5 — 大规模重构暗色模式，移除 !important 可能导致暗色模式局部失效，极高风险
- **收益性**：4/5 — 消除补丁，恢复变量驱动，符合规范 §8.1
- **兼容性**：2/5 — 重构期间暗色模式可能局部失效，需灰度
- **可持续性**：5/5 — 变量驱动，长期零维护

**成本性 = 1  → ❌ 不通过（成本性不可行，> 1 人月）**
**GAP = 13  → 即使忽略成本性否决，也仅"需讨论"**

> **建议**：不单独做，作为问题 4 的后续自然消解。问题 4 替换 #fff → token 后，暗色覆盖自动生效，可逐步移除 !important。本问题不单独立项。

- **可持续性**：5/5 — 变量驱动

> **依赖**：若问题 1 先做（侧边栏改深色），本问题需同步调整 muted 为浅色。建议问题 1 + 7 合并实施。

## 问题 8：响应式仅 1024px 一档

### 问题描述
`main.css` 仅 L654 一个 `@media (max-width: 1024px)`，规范 §9 要求 4 档断点（xs <640px 抽屉化 / sm 640-1024px 折叠 / lg 1024-1440px 标准 / xl >1440px 居中）。缺 640px 抽屉化和 1440px 居中。（Vue 文件中有 30 处 640px 断点，但 main.css 全局缺失）

### 修复方案
1. **在 `main.css` 添加 640px 断点**：
   ```css
   @media (max-width: 640px) {
     .app { grid-template-columns: 1fr; }  /* 侧边栏抽屉化 */
     .side { position: fixed; transform: translateX(-100%); z-index: 100; }
     .side.open { transform: translateX(0); }
     /* 添加汉堡菜单触发 */
   }
   ```
2. **添加 1440px 断点**：
   ```css
   @media (min-width: 1440px) {
     .main { max-width: 1600px; margin: 0 auto; }  /* 内容区居中 */
   }
   ```
3. **实现抽屉化交互**：在 `Sidebar.vue` 添加 `open` 状态，640px 下汉堡菜单触发
4. **多分辨率回归**：375px / 640px / 1024px / 1440px / 1920px

### 五维评审
- **成本性**：3/5 — 需实现抽屉化交互 + 多断点样式，1 人周
- **风险性**：3/5 — 响应式变更需多分辨率回归，可能影响现有布局
- **收益性**：4/5 — 满足多端适配，平板/移动端可用
- **兼容性**：4/5 — 增量添加断点，不影响现有桌面布局
- **可持续性**：4/5 — 符合规范 §9，但抽屉化需维护交互逻辑

**GAP = 18  → ✅ 推荐做**

## 问题 10：间距非 4 倍数 22px/26px/18px/10px

## 五维评审方法论说明

> 来源：2026-09-12-5d-review-pass-fail-cost-veto-decision-rule

### 评分标准（1-5 分）
- **成本性**：5=极低(<1人时) ｜ 4=低(1人天) ｜ 3=中(1人周) ｜ 2=高(1人周-1人月) ｜ 1=极高(>1人月)
- **风险性**：5=无风险 ｜ 4=低风险 ｜ 3=中风险 ｜ 2=高风险 ｜ 1=极高风险
- **收益性**：5=极高收益 ｜ 4=高 ｜ 3=中 ｜ 2=低 ｜ 1=极低
- **兼容性**：5=完全兼容 ｜ 4=基本兼容 ｜ 3=部分兼容 ｜ 2=少量不兼容 ｜ 1=不兼容
- **可持续性**：5=长期友好 ｜ 4=较好 ｜ 3=一般 ｜ 2=较差 ｜ 1=不可持续

### 判定规则
- **GAP > 17**：✅ 推荐做
- **GAP 13-17**：⚠️ 需讨论
- **GAP < 13**：❌ 不推荐做
- **成本性 = 1**：❌ 直接否决（成本性不可行，> 1 人月）

### 成本性否决案例
问题 6（暗色模式 !important 补丁）成本性 = 1（涉及 1226 行重构，> 1 人月），直接判定不通过，否决理由"成本性不可行"。建议作为问题 4 的后续自然消解，不单独立项。

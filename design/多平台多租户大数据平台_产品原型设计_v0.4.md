## 1. 产品定位与目标

### 1.1 背景

企业数据散落在多个业务线、多种存储中，缺乏统一治理与复用；同时面向外部客户需要提供可交付、可计费的大数据能力。在信创要求下，底层软硬件需国产化替代，传统闭源商业发行版难以满足自主可控诉求。

### 1.2 产品愿景

构建一套**运行在客户机器上自建 Kubernetes 集群之上的多租户湖仓集一体大数据平台（信创优先）**，K8s 作为高度封装的隐形底座对客户完全透明，对内沉淀为"数据能力中台"供各业务线复用，对外封装为标准化的"数据产品"按租户交付——客户只见大数据平台、不见容器与编排，实现"一套主代码、多形态环境、两类客户、统一治理、K8s 不可见"。

### 1.3 目标用户与价值

- 对内（业务线 / 数据团队）：开箱即用的数据集成、开发、治理、分析能力，降低重复建设成本。
- 对外（行业客户 / 生态伙伴）：私有化或订阅式交付标准化大数据能力，含租户隔离与计量计费。
- 平台运营方：统一的租户、资源、计量、运营后台，支撑商业化运转。

### 1.4 对内 + 对外兼顾的设计含义

- 同一套平台底座同时承载内部租户与外部租户，通过租户类型（内部 / 外部）区分 SLA、计费策略与合规要求。
- 内部业务线以"组织-项目"粒度共享资源池；外部客户以"租户"粒度独占或共享资源，按套餐计费。
- 控制面（运营后台、控制台）统一，数据面（计算/存储）按隔离级别弹性分配。

## 2. 设计原则

1. 信创自主可控：全栈优先选用支持国产芯片/OS、可源码构建、社区活跃的组件；关键控制面自研。
2. 私有化自建底座：Kubernetes 一律在客户自有机器上自建标准发行版（kubeadm / KubeSphere / Rancher RKE2 等），**不依赖任何云厂商托管 K8s 服务**（ACK / EKS / TKE / CCE 等），平台完全自持自运维，与云厂商解耦，利于私有化售卖。
3. 云原生优先：所有大数据组件容器化、声明式部署、弹性伸缩、故障自愈，自建 K8s 为唯一资源底座。
4. 湖仓集一体：以 Iceberg 表格式统一流批存储，计算引擎插拔，避免数据多份冗余。
5. 多租户隔离：命名空间 + 配额 + 网络策略 + 存储隔离 + 行级权限，租户间安全与性能互不影响。
6. 可运营可计量：资源、作业、存储均可观测、可计量、可计费，支撑商业化闭环。
7. 多环境可移植：一套主代码 + 环境适配驱动，业务与编排逻辑与环境解耦，支持信创 / 本地数据中心 / 公有云 / 私有云四类机器资源上一套底座多形态交付。
8. K8s 透明封装（客户无感知）：K8s 的 Namespace / Quota / Pod / Operator 等内部复杂度由封装层吸收，客户视角只见"工作空间 / 数据项目 / 计算任务 / 数据资产"等业务概念，不接触 kubectl、不感知容器与调度，最大化商用可交付性。

## 3. 总体架构（分层）

### 3.1 架构总览

平台采用自底向上的四层主架构（L0 基础设施层、L2 引擎层、L3 治理层、L4 工具链层、L5 产品层）+ L4.5 智能数据层，叠加四条横切能力带。

```text
┌────────────────────────────────────────────────────────────────────────┐
│                       L5  多租户产品层（数据云 SaaS）                    │
│   统一控制台 │ 运营后台 │ 行业应用 │ 对内业务线门户 │ 开放 API/服务目录   │
│   数据资产流通(Navier对标,可选)                                          │
├────────────────────────────────────────────────────────────────────────┤
│               L4.5  智能数据层（数据 + AI 一站式）★新增                  │
│   向量库 │ 知识工程(RAG/图谱) │ LLMOps(训练/部署/Agent) │ 领域大模型接口  │
├────────────────────────────────────────────────────────────────────────┤
│                   L4  数据开发与分析层（PaaS）                          │
│   数据集成 │ 调度编排 │ 数据开发IDE │ BI可视化 │ 即席查询 │ 标签画像 │ ML │
├────────────────────────────────────────────────────────────────────────┤
│                      L3  数据治理层（中台核心）                         │
│   元数据 │ 数据标准 │ 数据质量 │ 血缘 │ 资产目录 │ 主数据 │ 安全脱敏      │
├────────────────────────────────────────────────────────────────────────┤
│        L2  大数据引擎层（湖仓集一体 · 统一 SQL 网关）★升级               │
│   统一SQL网关(Quark对标): 单一入口跨引擎关联                             │
│   湖(原始, Iceberg) → 仓(主题, Doris/Trino) → 集(实时在线服务)          │
│   批(Spark) │ 流(Flink) │ 交互(Trino) │ OLAP(Doris) │ 消息(Kafka/IoTDB)│
│   多模型选配: 图/向量/搜索/时序/键值(按需)                              │
├────────────────────────────────────────────────────────────────────────┤
│           L0  基础设施层（机器供应 + 自建 K8s 底座，客户不可见）           │
│   机器供应: 信创(鲲鹏/海光/飞腾+麒麟/openEuler) ｜ 本地(x86裸金属/虚机) ｜ 云(客户VM) │
│   自建K8s(SKE发行版) │ 多可用区 │ 网络(Cilium) │ 存储(CSI/JuiceFS) │ 监控 │
│   └─ K8s 产品化封装层：Namespace/Quota/Pod/Operator → 工作空间/数据项目/计算任务 │
├────────────────────────────────────────────────────────────────────────┤
│        环境适配框架（多平台）：Profile + 驱动插件 + 多 Arch 镜像          │
│   抽象: 算力/OS/存储/网络/LB/KMS/身份/弹性 ｜ 按 Profile 加载驱动,主代码零改 │
├────────────────────────────────────────────────────────────────────────┤
        横切：统一身份与权限(国密) │ 安全合规(等保/密评) │ 统一运维观测 │ API网关
```

### 3.2 层级职责

| 层 | 职责 | 关键产出 |
| --- | --- | --- |
| L0 | 提供客户自有机器资源（信创/本地/云 VM）并在其上自建 K8s，提供容器编排、网络、存储、可观测性，且对外透明封装；不托管任何云厂商 K8s | 机器供应层基线 + 稳定弹性、客户不可见的 K8s 运行环境，差异由适配框架屏蔽 |
| L2 | 提供流批计算、湖仓集一体存储、统一 SQL 网关、消息、多模型引擎 | 数据加工、存储与统一查询能力 |
| L3 | 提供元数据、质量、血缘、资产、安全治理 | 可信、可管、可追溯的数据资产 |
| L4 | 提供集成、调度、开发、分析、BI 工具链 | 数据价值生产流水线 |
| L4.5 | 提供向量库、知识工程、LLMOps、领域大模型接口，打通数据→AI | 数据 + AI 一站式能力（★新增） |
| L5 | 提供多租户数据云控制台、运营、行业应用、资产流通 | 对内对外可消费的数据产品 |

## 4. L0 基础设施层 · 机器供应（L0.1–L0.5，客户自有资源，多形态）

目标：为不同环境提供算力、网络、存储资源。四类环境均指**客户自有的机器资源**（无论物理机还是 VM），其上由本平台统一**自建标准 Kubernetes 集群**；**绝不启用任何云厂商托管的 K8s 服务（ACK / EKS / TKE / CCE 等）**，以保证平台自持、私有化可交付、与云厂商解耦。

- 信创环境：鲲鹏 920（ARM64）/ 海光（x86）/ 飞腾 服务器 + openEuler / 麒麟 V10 / 统信 UOS；国产交换机与分布式存储；国密 SM2/3/4 加速卡；裸金属或国产虚拟化（OpenStack 信创版）。
- 本地数据中心：x86 服务器（裸金属或本地虚机）+ CentOS / RHEL / Ubuntu；标准交换机 + Ceph / 本地存储；硬件 LB。
- 公有云（客户自购 VM）：客户在公有云购买的虚拟机（如 ECS / CVM / EC2），**平台在其上自建 K8s**，仅把云当"裸算力 + 块存储 + 网络"用，不启用云托管 K8s、不绑定云原生数据库/消息等托管服务，保持可迁移。
- 私有云（客户自有虚拟化）：客户既有私有云（OpenStack / 华为云栈 / 国产化云）提供的 VM，平台同样自建 K8s，云只作为资源供给方。
- 共性：所有环境节点按 `arch` / `region` 打标签调度；控制面建议 3 节点 HA；存储按"对象存储优先、本地盘加速"原则。无论底层是哪种机器来源，K8s 形态、API、封装层完全一致。

## 5. L0 基础设施层 · 自建 K8s 底座（L0.6–L0.12，原 L1 云原生底座层）

目标：在信创 OS 之上提供稳定的容器平台，作为唯一资源底座。

### 5.1 核心组件（一律自建，非云托管）

- Kubernetes：v1.30+，多可用区部署，控制面 HA（3+ 节点，etcd 独立部署）。**由平台交付时自动在客户机器上 bootstrap，不依赖云厂商托管控制面。**
- 发行版封装：**自研 SKE（Shuqing Kubernetes Engine）发行版**——基于上游 K8s 二进制 + 深度调优与封装层，**非 KubeSphere/RKE2/k3s/kind 原样**。SKE 以一组静态 Pod + 自研 installer 交付，升级原子化；**对客户不暴露** K8s 控制台，仅平台运维与运营后台可见。详见 `ske/README.md`。
- 容器网络：Cilium（eBPF，取代 kube-proxy，支持 ARM，提供 NetworkPolicy 与可观测）。
- 容器存储：CSI 插件对接国产/本地存储；存算分离场景用 JuiceFS 提供 POSIX/HDFS 兼容接口。
- 可观测：Prometheus + Grafana（指标）、Loki（日志）、Tempo/自研（链路），全部部署于自建 K8s，但客户看板只呈现"服务健康 / 资源水位"等封装后视图。

#### 5.1.1 SKE 七大性能支柱（自研发行版核心差异化）

SKE 不是 vanilla kubeadm/k3s/kind 出厂即用，而是在保留上游 K8s 兼容性与生态前提下，做成"出厂即高性能、出厂即封装好"的发行版。七大支柱逐项有基准对照（见 `ske/tuning/` 脚本内注释基准）：

| 支柱 | 调优内容 | 落地脚本/配置 |
| --- | --- | --- |
| ① 内核调优 | 大页(2MB/1GB) + NUMA 绑核 + CPU 隔离(isolcpus+static) + 网络栈 sysctl | `ske/tuning/kernel.sh` |
| ② 网络 eBPF | Cilium 取代 kube-proxy，绕过 iptables/netfilter 慢路径，延迟降一个数量级 | `ske/manifests/cilium-values.yaml` |
| ③ 存储 IO | NVMe 直通 + IO_uring + LocalPV；etcd 专属 NVMe 独占 | `ske/tuning/storage.sh` |
| ④ 拓扑感知调度 | topologyKey=numa + single-numa-node + 自研数据本地性扩展器 | `ske/manifests/scheduler-policy.yaml` |
| ⑤ 控制面隔离 | etcd 独立部署独占 NVMe+CPU；apiserver max-inflight=3000/2000 | `ske/tuning/controlplane.sh` |
| ⑥ 组件精简 | 移除 cloud-provider、非必要 addon、关闭未用特性门；单发行版打包 | `ske/manifests/kubelet-config.yaml` |
| ⑦ 封装收敛 | SKE 不直接暴露给客户；由封装层(L0.11)翻译成工作空间/项目/任务；客户不持 kubeconfig | 见 §5.4 |

两种运行模式：`dev`（笔记本 kind + 自定义节点镜像，尽力调优）与 `prod`（客户交付 VM/裸金属 kubeadm，全量调优生效）。

### 5.2 大数据专属能力

- Spark / Flink 通过 Operator（Spark Operator / Flink Kubernetes Operator）原生提交到 K8s。
- 动态资源配额（ResourceQuota + LimitRange）按命名空间约束租户资源。
- 节点标签 + 污点容忍，区分控制面、计算、IO 密集、GPU 节点。
- 弹性：Cluster Autoscaler / KEDA 按作业队列与资源水位自动扩缩。

### 5.3 环境适配框架（多平台可移植）

目标：一套主代码（业务与编排逻辑），通过"环境抽象 + 驱动插件 + 部署 Profile"在信创、本地数据中心、公有云、私有云四种环境上运行，业务代码零改动。

#### 5.3.1 抽象维度

| 维度 | 信创 | 本地数据中心 | 公有云 | 私有云 |
| --- | --- | --- | --- | --- |
| 算力架构 | 鲲鹏(ARM64)/海光(x86) | x86 为主 | 云实例(多 arch) | 厂商 x86/ARM |
| OS | 麒麟/统信/openEuler | CentOS/RHEL/Ubuntu | 云定制内核 OS | 厂商 OS |
| 存储后端 | 国产对象存储/MinIO/Ceph | Ceph/MinIO | S3/OBS/OSS | 厂商对象存储 |
| 网络/LB | Cilium + MetalLB | Cilium + 硬件 LB | 云 CNI + 云 LB | 厂商 CNI + HAProxy |
| KMS/加密 | 国密卡(SM2/3/4)+国产KMS | Vault/自研 KMS | 自托管 KMS(可选云KMS,弱绑定) | 自托管/厂商 KMS |
| 身份 | Keycloak + LDAP | Keycloak/LDAP | Keycloak(优先自托管,可选云SSO) | Keycloak/厂商 IAM |
| 弹性 | 固定节点池 | 固定+Cluster Autoscaler | 自建节点池(可选调云API扩VM) | 自建节点池(可选调云API) |
| 可观测 | 自托管 Prometheus | 自托管 | 自托管/云监控 | 自托管 |

#### 5.3.2 实现机制

1. 主代码与配置分离：业务/编排代码（Spark/Flink 作业、调度、控制台）与环境无关，环境差异全部外置为配置。
2. 部署 Profile：采用 Helm values overlay 或 Kustomize overlay，每环境一个 profile（`profiles/xinchuang.yaml`、`onprem.yaml`、`aws.yaml`、`privatecloud.yaml`），含镜像仓库、arch 列表、storage/kms/lb/ingress/autoscaling 驱动选择、OS 基础镜像。
3. 驱动插件化：定义 `StorageDriver`、`CryptoDriver`、`AuthDriver`、`LBAdapter`、`CloudProvider` 等接口，各环境实现对应驱动，主流程仅依赖接口，运行时按 Profile 加载。
4. 多 Arch 镜像：统一 base image（含国密库的信创 base + 标准 base），CI 用 buildx 产出 multi-arch manifest（amd64 + arm64）；信创额外产出国产 OS 基础镜像变体。
5. 能力探测：部署前 preflight 检查 arch/OS/存储可达性/KMS/LB/国密支持，输出环境能力矩阵，决定启用国密等特性。
6. 统一抽象约定：存储统一走 S3 兼容 API；身份统一 OIDC；加密默认标准算法、信创按 Profile 切国密；镜像统一推送到各环境 registry（Harbor/云 ACR），内容一致。

#### 5.3.3 关键决策

- 以 Kubernetes 为不变底座，且一律自建：无论机器来自信创/本地/公有云/私有云，K8s 都是平台自建的标准发行版，云厂商仅作为"裸算力/块存储/网络"供给方，**绝不调用云托管 K8s 服务**；环境差异收敛到 K8s 之下的"机器供应层"与 K8s 之上的"适配驱动"，业务代码不改。
- 国密可插拔：默认标准算法，信创环境按 Profile 切换到国密驱动，不污染主流程。
- 一套交付物多形态：同一 Helm Chart / Kustomize 基线，按 Profile 生成环境专属清单，运维与审计一致。

### 5.4 K8s 产品化封装层（客户无感知）★ 本次核心

目标：把 Kubernetes 内部的 Namespace / ResourceQuota / Deployment / StatefulSet / Operator / Pod / HPA / 节点池等概念全部吸收进封装层，对外只暴露**业务语义**。客户（及外部租户）自始至终只与"大数据平台"交互，不接触 kubectl、不感知容器、不感知调度与故障自愈——这是商用可交付、能卖钱的关键。

#### 5.4.1 概念映射（内部 K8s → 客户视角）

| 客户 / 业务视角 | 内部 K8s 实现 |
| --- | --- |
| 租户工作空间（Workspace） | K8s Namespace + ResourceQuota + LimitRange + NetworkPolicy |
| 数据项目（Project） | Namespace 内的一组 Deployment/StatefulSet + 存储桶前缀 + 角色绑定 |
| 计算任务 / 作业 | Spark/Flink CR（Operator 托管）或 Job/CronJob，提交即运行，无 Pod 概念 |
| 数据资产 / 表 | 对象存储 + Iceberg 元数据，与 K8s 解耦 |
| 套餐 / 容量 | ResourceQuota + 节点池租约 + 存储配额 |
| 自动扩容 | HPA / KEDA，客户仅见"任务自动变快 / 并发提升" |
| 高可用 / 自愈 | 多副本 + 反亲和 + 重启策略，客户仅见"服务持续可用" |
| 运维告警 | 平台内部 Prometheus 告警；客户看板只显"服务健康"状态 |

#### 5.4.2 封装层职责

1. 抽象门面：控制台 / 运营后台 / 网关的全部请求经封装层转译为 K8s 操作，业务侧零 K8s 概念。
2. 资源翻译：把"套餐 / 项目 / 任务"翻译为 Namespace/Quota/Deployment/Operator CR，反向把 Pod 状态归纳为"任务运行中 / 成功 / 失败"。
3. 黑盒运维：节点故障、Pod 漂移、镜像拉取等由平台自动处理，仅在影响 SLA 时以"服务降级"等业务语言通知。
4. 安全收敛：客户无 K8s API 权限，所有操作走平台鉴权与审计，杜绝越权与误删。
5. 可移植保证：因上层不依赖 K8s 细节，封装层可在信创/本地/云 VM 上保持一致行为，是"一套主代码多环境"的落点。

#### 5.4.3 商用卖点

- 客户采购的是"大数据平台"，不是"K8s 集群"，部署与运维由我方全包，降低客户技术门槛与决策顾虑。
- 私有化交付时，K8s 作为内部底座可被信创/本地/云 VM 承载，但交付界面统一，销售话术统一（"一套平台、四类环境、同一体验"）。
- 不绑云厂商，避免客户担心锁定，也避免云账单不可控，利于按我方套餐定价。

## 6. L2 大数据引擎层（湖仓集一体）

以对象存储 + Iceberg 表格式为统一存储底座，计算引擎插拔；在存算之上增设**统一 SQL 网关**，并把"湖仓一体"升级为"湖仓集一体"（增加实时在线服务维度）。

### 6.1 计算引擎

| 引擎 | 用途 | 信创适配 |
| --- | --- | --- |
| Apache Spark 3.5 | 批处理、ETL、ML | Java 生态，ARM/x86 原生支持 |
| Apache Flink 1.18 | 流处理、实时数仓 | Java 生态，信创友好 |
| Trino 438 | 交互式即席查询 | Java 生态，ARM 支持 |
| Apache Doris 2.1 | 实时 OLAP、报表 | 国产开源，ARM 构建成熟，信创生态完善 |
| StarRocks（可选） | 高并发 OLAP | 国产开源，信创友好 |
| Apache IoTDB 2.0 | 时序 / 工业数据 | 国产开源（清华），信创适配好 |

### 6.2 存储与消息

- 表格式：Apache Iceberg，统一流批存储，支持 schema 演进、时间旅行、ACID。
- 对象存储：国产对象存储（MinIO 信创版 / 华为 OBS / 自建 Ceph），作为数据湖底座。
- HDFS：可选，仅在强兼容 Hadoop 生态的老作业保留，逐步迁移到对象存储。
- 消息：Apache Kafka（Java，ARM 可用），承担实时接入与解耦（§5.5 拍板）。

### 6.3 湖仓集一体（Lakehouse + Real-time Serving）

把"湖仓一体"升级为**湖仓集一体**，在湖（原始）、仓（主题）之上增加"集"——实时在线服务层，让同一份数据既能做离线分析，也能直接服务业务查询：

- **湖（Lake）**：对象存储 + Iceberg 承载原始贴源与明细，流批统一写入。
- **仓（Warehouse）**：Doris/Trino 承载主题建模、即席分析与报表，通过 External Catalog 直查 Iceberg，避免冗余拷贝。
- **集（Serving）**：Doris 物化视图 + 实时入湖（Flink CDC）承载高并发点查/接口查询，直接对业务系统/控制台提供服务，无需再走报表。
- 流批一体：Flink 写 Iceberg，Spark/Trino 读，Doris 同步建集，统一语义、统一治理。

### 6.4 统一 SQL 网关（对标星环 Quark）★ 新增

在 L2 之上设单一 SQL 入口，屏蔽引擎方言差异，强化"客户无感知"：

- 入口：用户只写标准 SQL，网关路由到 Trino（即席）/ Doris（OLAP/集）/ Spark（重批）。
- 联邦查询：跨 Iceberg / Doris / 外部库关联，用户无需关心数据落在哪。
- 管控：统一鉴权（接 X1）、限流、审计、查询剖析与熔断。
- 兼容：内置方言映射（Hive/Spark/MySQL/Oracle 兼容度），降低老作业迁移成本。

## 7. L3 数据治理层（中台核心）

目标：让数据"可信、可管、可追溯、可复用"。

### 7.1 核心模块

- 元数据管理：自研轻量 Catalog（Java/Go，§5.5 拍板），纳管库表、字段、作业、指标元数据。
- 数据标准：标准字典、码值、命名规范，落地到建模与校验。
- 数据质量：自研规则引擎（Java，集成进治理中台，§5.5 拍板；Griffin 已 Apache 停孵不可选），内置空值、唯一、波动、对账规则，质量分量化。
- 数据血缘：解析 Spark/Flink SQL 与调度 DAG，构建表级/字段级血缘，支持影响分析。
- 资产目录：面向业务的数据资产地图、标签、检索、申请审批，连接消费方与提供方。
- 主数据管理（MDM）：统一客户、组织、物料等核心实体。
- 数据安全：列/行级权限、动态脱敏、加密（国密）、分级分类、审计日志。

### 7.2 治理闭环

```text
采集元数据和血缘 → 定标准 → 检质量 → 评资产 → 授权消费 → 监控反馈 → 持续治理
```

治理结果（质量分、分级、owner）反馈到资产目录与权限系统，形成闭环。

## 11. 多租户与多层业务模型

> 说明：以下"租户 / 组织 / 项目 / 用户"为客户与运营视角的业务模型。其背后的 K8s 资源（Namespace / Quota / Pod）由 §5.4 封装层自动管理，客户与租户管理员均不可见、不可直接操作，确保商用交付的透明性与安全性。

### 11.1 租户分层（四层）

```text
平台运营方 (Platform)
  └─ 租户 Tenant (内部业务线 / 外部客户)
       └─ 组织 Organization (部门/子公司)
            └─ 项目 Project (数据源+作业+资产集合)
                 └─ 用户 User / 角色 Role
```

- 内部业务线映射为"内部租户"，共享平台资源池，内部结算或不计费。
- 外部客户映射为"外部租户"，按套餐独占或共享资源，按量/包年计费。

### 11.2 资源隔离与配额

| 维度 | 机制 |
| --- | --- |
| 计算 | K8s Namespace + ResourceQuota + 节点池隔离 |
| 网络 | NetworkPolicy + 服务网格 mTLS |
| 存储 | 对象存储桶前缀隔离 / 独立 PVC，加密密钥按租户 |
| 元数据 | Catalog 租户维度逻辑隔离 + 行级权限 |
| 权限 | 租户管理员自治，平台超管兜底 |

### 11.3 对内 + 对外兼顾部署模型

- 共享控制面（运营后台、网关、认证、监控）。
- 数据面可选：外部高合规租户走"独占节点池 + 独立存储桶"；内部租户走"共享资源池 + 配额约束"。
- 通过租户标签（type=internal/external）驱动差异化 SLA 与计费策略。

### 11.4 计量计费模型

- 计量项：CPU·内存·GPU 使用时长、存储容量·天数、作业次数、API 调用次数、网络流量。
- 计费：外部租户按套餐（基础/标准/旗舰）+ 超量计费；内部租户按成本中心内部结算（可选）。
- 实现：采集 K8s / 对象存储 / 网关指标 → 计量聚合 → 账单引擎 → 运营后台展示。

#### 11.5.5 内部租户结算策略

- 内部业务线映射为"内部租户"，**不走套餐**，按成本中心结算。
- 结算价 = 实际资源消耗 × 成本系数（默认 **0.3**，即按成本价内部结算，不含利润）。
- 可配置为**不计费**（纯共享，仅做资源水位监控）。
- 内部租户无工作空间数限制，受 ResourceQuota 约束。
- 结算报表按月出账，推送至财务系统（对接 L5.4 对内业务线门户）。

#### 11.5.6 多租户隔离级别判定

| 条件 | 隔离级别 | 成本承担 |
| --- | --- | --- |
| 外部租户 + 数据量 < 10TB | 共享节点池 + 配额隔离 | 平台承担 |
| 外部租户 + 数据量 ≥ 10TB 或等保三级以上 | 独占节点池 + 独立存储桶 | 租户加购独占费（节点数 × 1.5 万/年） |
| 内部租户 | 共享资源池 + 配额约束 | 平台承担 |

> 独占判定由平台自动检测（数据量 + 合规标签），运营后台可手动调整。独占费在套餐外单独计费。

## 14. 部署拓扑与高可用

- 控制面：3 节点 etcd + 多副本 K8s 控制组件，**由平台在客户机器上自建并托管**，跨可用区反亲和，不依赖云托管控制面。
- 计算：按 arch/负载类型分组节点池（批/流/IO/GPU），HPA + KEDA 弹性。
- 存储：对象存储 3 副本 + 跨区复制；关键元数据库（openGauss）主备或集群。
- 网络：Ingress 多副本 + 负载均衡，Cilium 提供策略与可观测。
- 容灾：核心组件多副本；数据湖副本与备份；RTO/RPO 按租户套餐分级。
- 多环境一致性：同一套 Helm/Kustomize 基线按 Profile 渲染，四种环境的控制面拓扑与租户模型保持一致，降低运维与审计成本。

## 18. 附录：术语表

- 信创：信息技术应用创新，软硬件国产化替代。
- 湖仓集一体：Lakehouse + Real-time Serving，数据湖的灵活性与数据仓库的管理能力结合，并增加实时在线服务层。
- 多租户：单一平台实例服务多个隔离客户/组织。
- Iceberg：开放表格式，支持 ACID 与 schema 演进。
- K8s 透明封装：把 Kubernetes 内部资源（Namespace/Quota/Pod/Operator）吸收进封装层，对外仅暴露业务语义，客户无感知。
- 自建 K8s（非云托管）：在客户机器上自建标准 Kubernetes 集群，不启用 ACK/EKS/TKE/CCE 等云厂商托管服务。
- 等保/密评：网络安全等级保护 / 商用密码应用安全性评估。
- 多模型数据库：单一平台内置关系、宽表、图、时序、键值、事件、文档、搜索、时空、向量等多种存储引擎，统一 SQL/计算/存储。
- 湖仓集一体：星环提出的架构范式——数据湖（湖）+ 数据仓库（仓）+ 实时数据集/在线服务（集）三者统一，由 ArgoDB 落地。
- TCOS：星环自研云原生操作系统，容器化编排、统一调度计算/存储/网络，可类比本平台的"自建 K8s + 封装层"。
- 数据云（TDC）：以多租户方式将大数据能力作为云服务交付，可类比本平台的 L5 多租户产品层。

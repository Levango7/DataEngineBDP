# 错误码定义

> 归属：数据引擎大数据平台 · 接口规范
> 关联文档：`统一API规范.md`、`openapi.yaml`
> 版本：v1.0  日期：2026-08-17

## 第1章 错误码编码规则

### 1.1 编码结构

平台错误码采用 **5 位整数** 编码，由"HTTP 状态码前三位 + 业务序号两位"或"模块段前缀 + 模块内序号"两种模式组成。统一通过 `ApiResponse.code` 字段返回，HTTP 状态码作为协议层兜底。

```text
错误码 = [HTTP状态码前3位] × 100 + [业务序号2位]
或
错误码 = [模块段前缀] × 1000 + [模块内序号3位]
```

- `0`：成功
- `40001`–`40999`：客户端错误（HTTP 4xx 语义）
- `50001`–`50999`：服务端错误（HTTP 5xx 语义）
- `10000`–`29999`：业务错误，按模块分段

### 1.2 设计原则

1. **唯一性**：每个错误码全局唯一，禁止跨模块复用。
2. **可读性**：错误码与 HTTP 状态码前三位对齐，肉眼可推断类别。
3. **可扩展性**：每个模块预留 999 个槽位，模块内序号按子功能再分段。
4. **稳定性**：错误码一经发布不可改含义，仅可弃用（标记 deprecated）并新增替代码。
5. **国际化友好**：`message` 字段为可读中文，未来通过 `Accept-Language` 头切换 i18n 资源，错误码本身不变。

### 1.3 错误响应统一格式

所有错误响应必须符合 `ApiResponse<T>` 结构：

```json
{
  "code": 40101,
  "message": "登录已过期，请重新登录",
  "data": null,
  "traceId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "timestamp": 1723891234567
}
```

`data` 字段在错误响应中恒为 `null`。如需返回错误详情（如字段级校验错误），使用 `details` 扩展字段（非标准 `ApiResponse` 字段，由各错误码自行约定）：

```json
{
  "code": 40001,
  "message": "参数校验失败",
  "data": null,
  "details": [
    { "field": "username", "reason": "不能为空" },
    { "field": "password", "reason": "长度需 8-32" }
  ],
  "traceId": "...",
  "timestamp": 1723891234567
}
```

## 第4章 错误码使用示例

### 4.1 后端抛错示例

```java
// 代码示例：业务异常抛出（Java）
public Tenant create(Tenant tenant) {
    if (repository.existsByName(tenant.getName())) {
        throw new BizException(10001, 409, "租户 " + tenant.getName() + " 已存在");
    }
    if (quotaService.userCount(tenant.getId()) >= tenant.getQuota()) {
        throw new BizException(10002, 400, "租户 " + tenant.getId() + " 用户数已达上限 " + tenant.getQuota());
    }
    return repository.save(tenant);
}
```

`BizException` 携带业务码、HTTP 状态、消息三要素，由全局异常处理器统一转 `ApiResponse`。

### 4.2 前端处理示例

```typescript
// 代码示例：前端错误处理（TypeScript）
import { ApiError, get } from '@/api/client'

try {
  const tenant = await get<Tenant>('/tenants/1001')
} catch (e) {
  if (e instanceof ApiError) {
    switch (e.code) {
      case 40401:
        router.push('/404')
        break
      case 40101:
        // 拦截器已自动跳登录页，此处兜底
        break
      case 10001:
        toast.error('租户已存在，请改名')
        break
      default:
        toast.error(e.message)
    }
  }
}
```

## 第5章 错误码与前端拦截器协同

### 5.1 前端拦截器逻辑

`frontend/src/api/client.ts` 响应拦截器核心逻辑：

```typescript
const body = response.data as ApiResponse<unknown>
if (body && typeof body === 'object' && 'code' in body) {
  if (body.code !== 0) {
    const msg = body.message || '业务处理失败'
    errorNotifier?.(msg)
    return Promise.reject(new ApiError(msg, body.code, response.status))
  }
  response.data = body.data  // 拆包
}
```

- `code === 0`：拆包，业务层直接拿到 `T`。
- `code !== 0`：reject `ApiError`，业务层 catch 后按 `e.code` 分支处理。
- 响应体无 `code` 字段（后端未包装）：拦截器不拆包，业务层拿到整个响应体，**这是当前 bug 状态**。

### 5.2 HTTP 状态码兜底

当响应体不是合法 JSON 或无 `code` 字段时，拦截器走 HTTP 状态码兜底分支：

```typescript
if (status === 401) {
  msg = '登录已过期，请重新登录'
  unauthorizedHandler?.()
} else if (status === 403) {
  msg = '无权限访问该资源'
} else if (status === 500) {
  msg = '服务器内部错误，请联系管理员'
} else if (status === 404) {
  msg = '请求的资源不存在'
}
```

此分支仅作为后端未按规范包装时的兜底，正常情况下不应触发。

## 第6章 错误码治理流程

### 6.1 新增错误码流程

1. **申请**：开发者在模块 PR 中提出新增错误码需求，注明含义、HTTP 状态、触发场景。
2. **审阅**：接口规范师审阅是否与现有码冲突、是否落入正确模块段。
3. **登记**：在本文件 §3 对应模块表中追加条目。
4. **同步**：同步更新 `openapi.yaml` 中对应接口的 `responses` 段。
5. **发布**：合并 PR 后错误码即生效，禁止后续修改含义。

### 6.2 弃用错误码流程

1. 错误码含义需变更时，**不改原码**，而是新增一个新码承载新含义。
2. 原码标记 `deprecated: true` 并在文档中注明替代码。
3. 至少保留 6 个月兼容期，期间后端可同时返回新码或原码。
4. 兼容期结束后，后端只返回新码，前端移除对原码的分支处理。

### 6.3 错误码与日志关联

每个错误响应的 `traceId` 必须与后端日志链路 ID 一致。后端通过 `MDC.put("traceId", ...)` 注入日志上下文，所有日志行含 `traceId` 字段，便于前端报错时一键搜索后端日志。

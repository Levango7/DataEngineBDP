### 3.2 详细发现

#### 3.2.1 网关统一入口与各引擎路由关系（✅ 通过）

L2.7 §4.1 定义统一入口 `POST /api/sql/v1/query`，§2 架构图明确"客户视角（控制台 / API）→ 统一 SQL 网关 → 各引擎"。L2.2 §5 注明"重批 SQL 经 L2.7 网关路由"；L2.3 §6 注明"Stream SQL 或 Jar 经 L2.7/L0.11 进入封装层"；L2.4 §5 注明"客户不直连 Trino，统一经 L2.7 SQL 网关路由"；L2.5 §5 注明"所有查询经 L2.7 统一 SQL 网关统一鉴权、路由、限流"。各引擎均承认网关为唯一入口，契约方向一致。

#### 3.2.2 网关路由目标不完整（❌ P1，问题 #2）

L2.7 §1 定位："跨 Iceberg（湖）/ Doris（仓·集）/ Trino / Kafka（流）/ 外部 JDBC 做联邦查询"；§2 架构图路由目标为 `[Doris] [Trino] [Iceberg] [Kafka/其他]`。但：

- L2.2 批计算明确"重批 SQL 经 L2.7 网关路由 Spark 执行"——Spark 未列入 L2.7 路由目标。
- L2.9 时序引擎明确"经 L2.7 统一 SQL 网关以 IoTDB 方言查询"——IoTDB 未列入 L2.7 路由目标。
- L2.10 多模型引擎明确"经 L2.7 统一 SQL 网关统一入口，多模型 SQL 方言映射"——多模型未列入 L2.7 路由目标。

**影响**：L2.7 网关接口契约与下游引擎声明不闭环，开发实现时网关 Executor Adapter 缺少 Spark/IoTDB/NebulaGraph/Milvus/ES 适配，将导致这三类引擎无法真正经网关统一入口访问，与"唯一查询入口"定位矛盾。

**建议**：L2.7 §1 定位与 §2 架构图补全路由目标为 `[Spark(重批)] [Flink(Stream SQL)] [Trino(交互/联邦)] [Doris(仓·集)] [Iceberg(湖)] [Kafka(流)] [IoTDB(时序)] [多模型(图/向量/搜索/键值)]`，并在 §6 方言适配表补对应 Adapter。

#### 3.2.3 L2.1 存储接口为各引擎提供 catalog 读写（✅ 通过）

L2.1 §2 架构图"计算引擎（读写，均经 catalog）→ 表格式层（Iceberg）→ StorageDriver"。L2.2 §4 "spark.sql.catalog.lake = org.apache.iceberg.spark.SparkCatalog, type=rest, 指向 L2.1 RestCatalog"；L2.3 §7 "状态后端统一到 L2.1 对象存储"；L2.4 §3 "Iceberg Connector 直查 L2.1 统一存储"；L2.5 §3 "Doris External Catalog 直读 L2.1 Iceberg 表"。存储接口契约一致。

#### 3.2.4 L2.6 整合与 L2.8 流源（✅ 通过）

L2.6 §2 三级架构整合 L2.1（底座）+ L2.2（仓建模）+ L2.3（实时入湖）+ L2.4（即席）+ L2.5（集层在线）+ L2.7（统一入口）；L2.8 §1 "下游 Flink/数据集成按订阅消费"，L2.3 §4 "Kafka(L2.8) ─stream──▶ Flink Source"。整合与流源契约一致。

### 4.2 详细发现

#### 4.2.1 L2.7 网关关联声明严重不完整（❌ P1，问题 #3）

L2.7 文档头部"关联"仅写"L0.11 封装层（网关本身以逻辑服务形态运行）"。但正文实际涉及：

- §2 架构图路由到 Doris/Trino/Iceberg/Kafka → 应关联 L2.1（Iceberg）、L2.4（Trino）、L2.5（Doris）、L2.8（Kafka）。
- §7 "权限与脱敏下推复用 L3" → 应关联 L3.7 数据安全。
- §3 "Catalog Service 与 L3.5 资产目录同源" → 应关联 L3.5。
- 按 3.2.2 发现，还应关联 L2.2（Spark）、L2.9（IoTDB）、L2.10（多模型）。

**影响**：关联声明是模块间依赖的契约，缺失会导致依赖梳理遗漏、影响分析断链、构建顺序错误。

**建议**：L2.7 头部"关联"补全为 `L0.11 封装层；L2.1 统一存储(Iceberg catalog)；L2.2 Spark(重批路由)；L2.4 Trino(交互路由)；L2.5 Doris(OLAP路由)；L2.8 Kafka(流路由)；L2.9 IoTDB(时序路由)；L2.10 多模型(方言路由)；L3.5 资产目录(元数据同源)；L3.7 数据安全(权限/脱敏下推)`。

#### 4.2.2 L2.9 时序引擎关联声明遗漏 L2.1（❌ P1，问题 #6）

L2.9 头部"关联"写"L2.7 统一 SQL 网关；L4.1 数据集成；L0.11 封装层"，但正文 §2 架构图明确"冷数据归档 → L2.1 统一存储（Iceberg 湖）"，§5 流程"定时降采样任务：IoTDB(热/温) → Iceberg(冷)"。

**影响**：L2.9 对 L2.1 存在数据写入依赖（降采样归档），关联声明缺失会导致部署时 L2.9 先于 L2.1 就绪、归档链路断裂。

**建议**：L2.9 头部"关联"补充 `L2.1 统一存储（冷数据降采样归档 Iceberg 湖）`。

#### 4.2.3 其余 8 份文档关联引用（✅ 通过）

L2.1–L2.6、L2.8、L2.10 关联声明引用的模块编号（L0.11、L2.1–L2.8、L3.5、L3.7、L4.1、L4.2、L4.5.3、L4.5.4）均与 §3.3 模块状态表一致，无错误编号、无幽灵引用。

### 6.2 详细发现

#### 6.2.1 引擎名称与存储格式术语（✅ 通过）

10 份文档的引擎名称与 §3.3 模块名一致：L2.2"批计算"（非"批处理"）、L2.3"流计算"（非"流处理"）、L2.4"交互查询"、L2.5"OLAP"、L2.6"湖仓集一体"、L2.7"统一 SQL 网关"、L2.8"消息与流接入"、L2.9"时序引擎"、L2.10"多模型选配引擎"。存储格式统一为 Apache Iceberg，Hudi 未作为选型出现，Delta Lake 仅在 L2.1 对标行出现（非选型）。

#### 6.2.2 Catalog 类型术语割裂（❌ P0，问题 #1）

这是本次评审最严重的问题，涉及术语与部署配置双重不一致：

- L2.1 统一存储 §2 架构图：计算引擎经 catalog 读写，StorageDriver 屏蔽后端——隐含 RestCatalog。
- L2.2 批计算 §4：`spark.sql.catalog.lake = org.apache.iceberg.spark.SparkCatalog, type=rest`——**RestCatalog**。
- L2.4 交互查询 §3：`connector.name=iceberg, iceberg.catalog.type=hive, hive.metastore.uri=thrift://hms:9083`——**Hive Metastore**。
- L2.5 OLAP §3：`CREATE CATALOG iceberg_catalog ... 'iceberg.catalog.type'='rest', 'iceberg.catalog.uri'='http://iceberg-rest:8181'`——**RestCatalog**。
- L2.6 湖仓集一体 §7："三级共用一套 catalog（Hive Metastore / Iceberg REST Catalog / Doris Catalog 联邦）"——混合表述。
- trino-values.yaml：`catalogs.iceberg.connector: "iceberg", catalogUri: "http://iceberg-catalog:8181"`——**REST Catalog**。

**结论**：L2.4 文档使用 Hive Metastore（`iceberg.catalog.type=hive`），而 L2.1/L2.2/L2.5 及 trino-values.yaml 均使用 REST Catalog（`type=rest` / `catalogUri=http://...`）。Catalog 类型割裂会导致：

1. Trino 与 Spark/Doris 看到不同的元数据视图，联邦查询表对不上。
2. 部署时需额外维护一套 Hive Metastore 服务，与 values 中 `iceberg-catalog:8181` 的 REST Catalog 端点重复。
3. 湖仓集一体"统一 catalog"契约破裂。

**建议**：L2.4 §3 Iceberg Connector 配置改为 REST Catalog：

```properties
connector.name=iceberg
iceberg.catalog.type=rest
iceberg.catalog.uri=http://iceberg-catalog:8181
iceberg.file-format=PARQUET
```

并同步 L2.6 §7 表述为"三级共用 Iceberg REST Catalog + Doris Catalog 联邦"（移除 Hive Metastore 作为主 catalog 的表述，仅作可选兼容）。

#### 6.2.3 "交互查询"与"即席查询"混用（⚠️ P3，问题 #16）

L2.4 模块名为"交互查询"（与 §3.3 一致），但正文 §1"即席/联邦查询引擎"、"即席查询（Ad-hoc）"频繁使用"即席查询"。两者语义相近但非完全等同（交互查询含即席+联邦），建议统一为"交互查询（即席/联邦）"或在 §1 首句明确"交互查询即即席查询与联邦查询的合称"。

见 6.2.2，此处从部署配置维度复述：trino-values.yaml `catalogs.iceberg.catalogUri: "http://iceberg-catalog:8181"` 为 REST Catalog 端点，L2.4 §3 配置 `iceberg.catalog.type=hive, hive.metastore.uri=thrift://hms:9083` 为 Hive Metastore。部署时按 values 起的是 iceberg-catalog:8181（REST），而文档指导的配置连的是 hms:9083（HMS），两者不可互通。

#### 7.2.3 Flink / Doris / Kafka / IoTDB 配置一致（✅ 通过）

- Flink：L2.3 §7"RocksDB 增量 Checkpoint，周期 60s" ↔ flink-values.yaml `stateBackend.type: rocksdb, incremental: true, checkpoint.interval: "60s"`，一致。
- Doris：L2.5 §2"FE 3 节点 HA + BE StatefulSet NVMe" ↔ doris-values.yaml `fe.replicas: 3, be.persistence.data.storageClass: "fast-nvme"`，一致。
- Kafka：L2.8 §3"KRaft + replicas=3 + RF=3 + min.isr=2" ↔ kafka-values.yaml `metadata.mode: "kraft", broker.replicas: 3, defaultReplicationFactor: 3, minInSyncReplicas: 2`，一致。
- IoTDB：L2.9 §2"ConfigNode 奇数 + DataNode NVMe" ↔ iotdb-values.yaml `configNode.replicas: 3, dataNode.persistence.sequence.storageClass: "fast-nvme"`，一致。

#### 7.2.4 Kafka 基础版副本因子降级（⚠️ P2，问题 #13）

kafka-values.yaml `tierProfiles.base.replicationFactor: 1`，而 L2.8 §7 推荐"default.replication.factor: 3"。基础版 RF=1 意味着无副本容错，与 L2.8 §7"容忍 1 副本宕"的表述矛盾。

**影响**：基础版 Kafka 单副本无高可用，与文档"故障切换不丢不重"承诺不符。

**建议**：L2.8 §7 补充"基础版 RF=1（无副本容错，仅演示/小规模）；标准版/旗舰版 RF=3"的套餐分档说明；或 values 基础版 RF 改为 2（最低容错）。

## 第10章 评审结论

### 10.1 总体评价

10 份 L2 引擎层详细设计文档整体质量**良好**，框架完整、职责清晰、跨引擎协同关系基本对齐。主要优点：

- **选型对齐 §5.5 拍板**：L2.8 Kafka、L2.10 NebulaGraph+Milvus 正确遵循 §5.5 决策，未沿用基准文档 §3.3/§13 中遗留的"或"表述。
- **湖仓集范式自洽**：L2.6 定义湖→仓→集三级流转，L2.1–L2.5 各司其职，L2.2 Spark 写 Iceberg、L2.3 Flink CDC 入湖、L2.4 Trino 即席、L2.5 Doris 集层物化，分工与 §6.3 一致。
- **封装层收敛一致**：10 份文档均声明客户不直连 K8s/CR/Operator，经 L0.11 封装层翻译，与 §5.4"K8s 透明封装"原则一致。
- **多环境适配统一**：四环境（信创/本地/公有云/私有云）均声明"自建 K8s + 裸对象存储，不启云托管服务"，与 §5.3 环境适配框架一致。

### 10.2 主要风险

1. **Catalog 割裂（P0，#1）**：L2.4 Trino 用 Hive Metastore 而其余用 REST Catalog，是唯一阻断性问题，直接威胁湖仓集一体"统一 catalog"契约，必须首批修复。
2. **网关契约不闭环（P1，#2/#3）**：L2.7 网关作为"唯一查询入口"，但路由目标与关联声明均不完整，下游 8 个引擎中仅 4 个被网关显式覆盖，"一个入口查全部"承诺存在落地缺口。
3. **套餐矩阵冲突（P1，#4）**：L2.10 标准版 ES/Redis 可选与 §11.5.1 矩阵矛盾，且 ES 牵连 L3.5 资产目录搜索能力，需基准侧决策。

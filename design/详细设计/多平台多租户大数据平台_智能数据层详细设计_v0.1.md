# L4.5 智能数据层 · 详细设计（v0.1）

> 归属：多平台多租户大数据平台 · L4（数据开发与分析）与 L5（产品层）之间的智能数据层
> 对标：星环 Hippo（向量）/ 无涯问知（知识工程）/ LLMOps（微调运营）/ SoLar（大模型网关）
> 关联：L0.11 封装层（所有服务 Pod 由 Operator 托管）；L2.7 统一 SQL 网关（embedding/生成可作为查询能力）；L3.5 资产目录（知识库可登记为资产）；L4.5.2 机器学习（MLflow 底座复用，详见 L4.5.5 LLMOps）
> 适用版本：仅旗舰版（基础版❌ / 标准版❌ / 旗舰版✅，对照 §11.5 套餐模块矩阵）

智能数据层把"数据分析"升级为"数据 + AI 一站式"，是差异化卖点。其下四个组件共用同一封装哲学：**客户只见能力，不见 Pod/模型服务/显卡**。

---

## L4.5.3 向量库（Vector Store）

### 定位与价值
统一管理 embedding 集合（维度/索引/检索），支撑语义检索与 RAG。对标星环 Hippo / Milvus / pgvector。

### 架构
向量服务（集合管理 + 检索路由） + 底层向量引擎（Milvus / 自研，StatefulSet + PVC 持久化）。集合 = 一组 Pod + 持久卷，受工作空间配额约束。

### 接口契约
```
POST /api/vector/v1/collections                 { name, dim, indexType(HNSW|IVF_PQ), metric(L2|IP|COSINE), kb? }
GET  /api/vector/v1/collections                 → [{name,dim,count,index,linkedKb}]
POST /api/vector/v1/collections/{c}/upsert       { vectors:[[...]], payloads:[{id,text,meta}] }
POST /api/vector/v1/collections/{c}/search       { vector?|text?, topK, filter? } → [{id,score,payload}]
DELETE /api/vector/v1/collections/{c}
```
> `text` 检索时由 L4.5.6 网关 embedding 模型转为向量，客户不感知 embedding 过程。

### 关键流程
建集合 → 文本经 embedding 写入（upsert 含 payload）→ 检索返回 topK + payload（关联原文/元数据）。底层引擎故障由封装层重建 Pod，客户无感。

## L4.5.4 知识工程（Knowledge Engineering / RAG）

### 定位与价值
文档入库 → 切片 → 向量化 → RAG 策略配置，构建企业级知识底座。对标星环无涯问知 / 阿里百炼知识库。

### 架构
文档解析 → 切片(Chunker) → 向量化(调 embedding) → 写 L4.5.3 向量集合 → 检索(混合 向量+关键词) → 重排(Reranker) → 引用溯源。**知识库底层直接复用向量库**，不重复造存储。

> 图数据库选型：知识图谱（NebulaGraph，§5.5 拍板）——国产开源、C++ 高性能、信创适配好，用于实体/关系存储与图谱推理，不使用 Neo4j 或其他图库。

### 接口契约
```
POST /api/kb/v1/knowledge-bases                 { name, chunkStrategy{type,size}, retriever{type,topK,threshold}, reranker }
POST /api/kb/v1/knowledge-bases/{id}/documents   { source(file|url|text), parse:true } → 触发解析+切片+向量化
POST /api/kb/v1/knowledge-bases/{id}/query       { question, topK, threshold } → { answer?, chunks:[{text,score,ref}] }
GET  /api/kb/v1/knowledge-bases                  → [{name,docs,chunk,retriever,status}]
```

### RAG 策略
TopK、分数阈值、重排模型（如 bge-reranker 自托管）、引用溯源开关。策略变更即时生效，无需重建索引。

### 关键流程
上传文档 → 解析为块 → embedding 写向量集合 → 查询时向量+关键词混合召回 → 重排 → 返回带引用的片段（可接大模型生成答案）。

## L4.5.5 LLMOps（微调 · 评估 · 部署）

### 定位与价值
从微调、评估到部署的一体化大模型运营；基座模型与领域模型统一纳管。对标星环 LLMOps / 阿里 PAI。

### 架构
模型注册表（Registry） + 微调训练（Fine-tune，封装层调度 GPU Pod） + 评估（Eval） + 部署端点（Endpoint/Serving，注册到 L4.5.6 网关）。

> 关联：复用 L4.5.2 机器学习 MLflow Tracking/Registry 底座——微调训练的运行追踪（metrics/params/artifacts）、模型版本注册与 L4.5.2 共用同一 MLflow 服务，避免重复建设。LLMOps 在 MLflow 之上扩展大模型特有的评估指标（幻觉率、对比基座提升等）与端点生命周期管理。
>
> 训练数据预处理：不复用 L2.2 Spark ETL，由 LLMOps 内置轻量预处理流水线（tokenization / packing / chat template 渲染）完成；当训练数据规模超过单机处理能力（>1TB）时，可经 L2.2 Spark ETL 做分布式预处理后导入 LLMOps，此场景在关联行已声明 L2.2 可选依赖。

### 接口契约
```
POST /api/llmops/v1/models                       { name, type(base|ft), base?, params } → 注册
POST /api/llmops/v1/fine-tunes                   { baseModel, dataset, epochs, gpu, lr } → 训练任务
GET  /api/llmops/v1/fine-tunes/{id}/eval         → { accuracy, hallucinationRate, upliftVsBase }
POST /api/llmops/v1/endpoints                    { model, replica, gpu } → 部署端点(路由到大模型网关)
GET  /api/llmops/v1/endpoints                    → [{model,url,status}]
```

### 评估指标
准确率、幻觉率、对比基座提升（如 +11.3pt）；支持发起人工评估任务。

### 关键流程
选基座 → 准备训练数据 → 提交微调（封装层拉起 GPU Pod，客户无感） → 评估 → 部署端点 → 注册到 L4.5.6 网关 → 业务经网关调用。

## L4.5.6 领域大模型接口（含大模型网关）

> 术语说明：本节模块名为「领域大模型接口」（对齐 §3.3 模块状态表），「大模型网关（LLM Gateway）」为其内部核心组件名，负责路由/限流/计费/审计的执行面。

### 定位与价值
统一 API 入口，路由多模型、限流、计费、审计，屏蔽底层部署差异。对标星环 SoLar / 通用 LLM Gateway。OpenAI 兼容协议，便于存量应用接入。

### 架构
网关（路由 / 限流 / 计费 / 审计） + 后端模型服务（由各 LLMOps 端点提供）。**网关只做治理，不直接持有模型**——与封装层"客户只见能力不见底座"思想一致。

### 接口契约
```
POST /api/gateway/v1/chat/completions            OpenAI 兼容 { model, messages } → 流式/非流式
POST /api/gateway/v1/embeddings                  { model, input } → { vectors }
GET  /api/gateway/v1/models                       → 可路由模型列表
POST /api/gateway/v1/keys                         { name, routeModel, rpm, tpm } → API Key
GET  /api/gateway/v1/keys                         → [{name,routeModel,rpm,status}]
GET  /api/gateway/v1/stats                        → { calls, latencyP95, successRate, activeKeys }
```

### 路由与治理
- **路由**：Key → model 映射；支持按权重/健康度多副本。
- **限流**：rpm（请求/分）/ tpm（token/分），超额返回 429。
- **计费**：按 token / 调用量计量，账单接入 L5 计量。
- **审计**：记录调用方 / 模型 / token 量 / 耗时，供合规与回溯。

### 计量链路
大模型网关 → X4 APISIX（prometheus 插件采集调用量/token 指标）→ L5.2 运营后台账单引擎（按套餐计费规则出账）。网关自身不做账单存储，仅产生指标，由 X4 APISIX 统一采集后汇入 L5.2 计量链路，与平台其他 API 计量链路一致。

### 关键流程
应用持 Key 调 `/chat/completions` → 网关校验 Key+限流 → 路由到对应 LLMOps 端点 → 返回结果 → 写审计与计量。后端模型服务扩缩容由封装层 HPA 托管。

## 跨组件一致性

| 维度 | 约定 |
| --- | --- |
| 封装 | 四个组件服务均为无状态/有状态 Pod，由 L0.11 Operator 托管；客户不持 K8s 权限 |
| 配额 | 向量集合、GPU 端点、网关 QPS 均计入工作空间 ResourceQuota |
| 多环境 | 逻辑一致；底层引擎/基座模型按 Profile（信创可选国产基座 qiong 系列） |
| 资产化 | 知识库、微调模型可登记为 L3.5 资产，纳入统一目录与权限 |

对照 §8.5.1 智能层三阶段演进，本详细设计 v0.1 覆盖 v0.1 阶段全部能力，v0.2/v0.3 为后续迭代：

| 阶段 | 范围 | 本文档覆盖情况 |
| --- | --- | --- |
| v0.1（当前） | 向量检索 + 知识图谱 + RAG + MLflow + 模型网关 | ✅ 全覆盖（L4.5.3 向量库 / L4.5.4 知识工程含 NebulaGraph 知识图谱 / L4.5.5 LLMOps 含 MLflow 底座 / L4.5.6 领域大模型接口含大模型网关） |
| v0.2 | Agent 编排 + 多模态 + AutoML | ⏳ 待 v0.2 迭代（本 v0.1 不含） |
| v0.3 | 领域大模型微调 + 联邦学习 + 模型市场 | ⏳ 待 v0.3 迭代（本 v0.1 不含；控制台 v0.3 已落地示例数据，详见「与 UI 的对应」节） |

## 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 向量检索精度不足 | RAG 答非所问 | 混合检索 + 重排 + 阈值过滤 + 引用溯源 |
| GPU 资源争抢 | 微调/推理互饿 | 节点池租约隔离 + 配额上限 + 队列优先级 |
| 模型幻觉 | 误导性输出 | 评估门禁（幻觉率阈值）+ 人工评估 + 引用可查 |
| 网关单点 | 调用中断 | 多副本 + 限流保护 + 后端健康检查 |

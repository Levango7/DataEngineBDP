﻿# L3.5 资产目录（数据地图）· 详细设计（v0.1）

> 归属：多平台多租户大数据平台 · L3 数据治理层
> 套餐：基础版起含（§11.5.1）
> 对标：阿里 DataWorks 数据地图 / Cloudera Atlas（元数据+血缘+分类）
> 关联：L3.1 元数据 · L3.2 数据标准 · L3.3 数据质量 · L3.4 血缘 · L3.7 安全脱敏；L0.11 封装层；L2.7 统一 SQL 网关（共享元模型）；L4.3 数据开发 IDE（消费 `/api/catalog/v1/assets` 做表名补全）；L4.4 BI 可视化（消费 `/api/catalog/v1/assets/{id}` 获取数据集元模型）

## 1. 定位与价值

资产目录是平台的**统一数据地图**：客户在一个入口检索、预览、申请、订阅全部数据资产（表/主题/标签/API/文件/模型），血缘、质量、脱敏策略随资产沉淀，无需切换多个引擎控制台。

客户价值：
- "找数快"——全文 + 标签 + 分层 + 敏感级别多维检索。
- "用数合规"——资产可见性受行级权限过滤；敏感资产走审批流才能用。
- "资产可运营"——订阅变更通知、质量分透明、血缘可追溯。

平台价值：
- 与 L2.7 统一 SQL 网关**共享同一元模型**：网关的 `catalogs` 接口直接读资产目录，客户只见资产名。
- 与 L3.7 安全联动：资产的敏感级别驱动统一 SQL 的脱敏下推。
- 权限最终收敛到 L0.11 封装层的 K8s RBAC / 引擎授权，客户无感知。

## 2. 资产元模型

```text
Asset {
  id, name,
  type:        table | theme | tag | api | file | model
  layer:       ODS | DWD | DWS | ADS        // 数仓分层
  domain:      核心 | 增长 | 安全 | 财经 …   // 业务域
  owner, team,
  engine:      iceberg | doris | trino | kafka   // 技术归属
  storageRef:  { catalog, db, table }            // 物理定位（客户不可见细节可折叠）
  schema:      [ { field, type, sensitive } ]    // 字段级
  sensitiveLevel: none | restricted | PII        // 联动 L3.7
  qualityScore: 0-100,                            // 联动 L3.3
  tags:        [ ... ],                           // 业务标签
  lineageRef:  assetId[],                         // 联动 L3.4
  updateFreq:  realtime | hourly | daily | …,
  description, createdAt, updatedAt
}
```

- **技术元数据**（schema/统计/血缘）：自动采集，客户只读。
- **业务元数据**（分层/域/标签/描述/敏感定级）：人工补全或标准自动落标。
- 资产支持"注册"（人工登记）与"自动发现"（采集器从引擎拉取）两种方式，以 `source=manual|discovered` 区分。

## 3. 总体架构

```text
┌──────────── 客户视角（控制台 资产目录 / 统一SQL catalogs） ────────────┐
└──────────────────────────┬──────────────────────────────────────────┘
                            ▼
┌──────────── 资产服务（逻辑服务，Pod 由封装层 Operator 托管） ──────────┐
│  检索 ─ 详情(元数据/Schema/质量/权限) ─ 登记 ─ 申请 ─ 订阅            │
└──────┬───────────────────────────────────────┬──────────────────────┘
       ▼                                       ▼
  元数据存储(图库+关系库)              权限申请 ──→ L3.7 安全工作流(审批)
       ▲                                       │
       │ 采集                                  ▼
  采集器(引擎 Hook / 定时抽取)             封装层 RBAC / 引擎级授权(最终落地)
```

资产服务无状态，多副本；**资产服务基于自研轻量 Catalog（Java/Go）实现**（对齐 §5.5 #2 决策），与 L3.1 元数据、L2.7 统一 SQL 网关共享同一元模型与 Catalog 实现，避免引入 DataHub 等 Python 栈组件。元数据存储按环境选图库（信创环境用国产图库或关系库+ES，不绑单一图库）。

## 4. 接口契约（REST）

### 4.1 检索
```
GET /api/catalog/v1/assets?q=order&layer=DWD&domain=&sensitive=&page=1&size=20
→ { total, items:[ {id,name,layer,owner,qualityScore,sensitiveLevel} ], facets:{layer,domain,sensitive} }
```
> 结果按 workspaceId + 行级权限过滤，客户只看得到有权限的资产。

### 4.2 详情
```
GET /api/catalog/v1/assets/{id}
→ { meta, schema:[{field,type,sensitive}], quality:{rules,passRate}, permissions:{current,applyUrl} }
```

### 4.3 登记 / 申请 / 订阅
```
POST /api/catalog/v1/assets                      { name,type,layer,storageRef,... } → 资产
POST /api/catalog/v1/assets/{id}/subscribe       → 订阅(变更通知)
POST /api/catalog/v1/assets/{id}/permissions     { action:read|write, reason } → 进入 L3.7 审批流
```

### 4.4 血缘 / 统计
```
GET /api/catalog/v1/lineage/{id}        → { upstream:[], downstream:[] }
GET /api/catalog/v1/stats               → { total, byLayer, byQuality, bySensitive }
```

## 5. 关键流程

- **采集**：引擎 Hook / 定时抽取 schema 与统计 → 自动建/更新资产 → 触发标准落标与质量评分；血缘由 L3.4 采集回填 `lineageRef`。
- **检索**：q 走全文索引 + 标签 + 分层 + 敏感过滤；返回前再过行级权限，越权资产不出现。
- **申请权限**：点"申请读权限" → 生成 L3.7 审批单 → 审批通过 → 封装层授予 K8s RBAC / 引擎授权 → 客户可在统一 SQL 查询该资产。
- **订阅**：订阅后资产 schema/质量/敏感级别变更，事件通知订阅者（不推送原始数据）。

## 6. 与封装层（L0.11）/ 统一 SQL（L2.7）的关系

- 资产目录的 `storageRef` 是技术定位；客户视角由封装层翻译为"工作空间/项目/资产名"，不暴露 catalog/db/table 物理细节。
- `sensitiveLevel` 直接驱动 L2.7 的脱敏下推函数选择（掩码/哈希/仅授权可见），国密 SM3 在信创按 Profile 启用。
- `catalogs` 接口（L2.7 §4.3）读资产目录元模型，保证"一个元模型、两处消费"。

## 7. 多环境一致性

- 资产元模型四环境完全一致；采集器作为"适配驱动"按 Profile 对接不同引擎（信创/本地/云VM/私有云）。
- 权限落地的 RBAC/引擎授权在四环境行为一致，差异只在底层授权后端（K8s RBAC 通用，引擎授权按驱动）。

## 8. 部署配置

部署参数落地于 `design/deploy/values/catalog-values.yaml`，由封装层 Helm Operator 渲染。关键配置块：

```yaml
# catalog-values.yaml
catalog:
  image: sq-catalog:0.1.0          # 自研轻量 Catalog（Java/Go）
  replicas: 2
  resources:
    requests: { cpu: "0.5", memory: "1Gi" }
    limits:   { cpu: "1",   memory: "2Gi" }
  storage:
    graph: { type: "nebula", profile: "default" }   # 信创 Profile 切国产图库
    relational: { type: "postgresql" }
    search: { type: "elasticsearch" }               # 全文检索
  tierProfiles:
    base:      { replicas: 1, resources: "small" }
    standard:  { replicas: 2, resources: "medium" }
    flagship:  { replicas: 3, resources: "large" }
```

> 资源配额说明：`resources` 中 quota 为单组件上限，平台总额度见 §11.5.2，由封装层 ResourceQuota 在租户级聚合约束（非所有组件同时满载，故单组件配额之和可略超平台总额度）。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 元数据滞后/不一致 | 找数不准、血缘断点 | 采集频率可调 + 血缘校验 + 人工补录入口 |
| 权限蔓延 | 越权/合规事故 | 定期权限回收 + 审批流 + 审计留痕 |
| 敏感定级遗漏 | 脱敏失效 | 自动识别模板 + 强制定级才能发布资产 |
| 图库在信创缺失 | 检索性能差 | 关系库 + ES 兜底，不绑单一图库 |

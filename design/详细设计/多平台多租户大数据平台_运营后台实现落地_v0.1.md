> 版本：v0.1 ｜ 日期：2026-08-01 ｜ 状态：实现落地稿
> 依赖：运营后台详细设计 v0.1（接口契约 / 套餐档位 / 流程）、封装层 v0.1（套餐→ResourceQuota 翻译）、部署清单 v0.1（deploy/ 体系）
> 目标：把运营后台从「设计」变成「可部署的真实服务」——套餐管理、计量采集、账单计费、运营看板真实跑起来，对接 Prometheus 与封装层。

## 1. 服务架构

```text
┌──────────────────────────────────────────────────────────┐
│  operations-api (Deployment, 无状态)                       │
│   /api/v1/admin/tenants  packages  metering  bills  dashboard│
└───────────┬───────────────────────────┬────────────────────┘
            │ 查指标                     │ 设套餐 / 查租户
            ▼                            ▼
      Prometheus             封装层 API (L0.11)
      (kube-state-metrics     POST /api/v1/workspaces (配额)
       + cAdvisor)            GET tenant→ws 映射
            │
            ▼
      按 namespace=ws-<name> 聚合
      (tenant 标签由封装层打在 Namespace 上)
```

**组件**：
- `operations-api`：FastAPI 服务，提供全部 `/api/v1/admin/*` 端点；套餐配置内置；计量实时查 Prometheus 聚合；账单实时计算；看板聚合。
  - **FastAPI 选型理由**：运营后台属 L5 控制面（非 BI/ML 范畴），选 Python/FastAPI 因：(1) 快速迭代——运营后台需求多变，FastAPI 自动生成 OpenAPI 文档、Pydantic 校验，迭代效率高于 Java/Spring；(2) 与 Prometheus/封装层 API 集成简洁——httpx + prometheus-client 生态成熟，无需 JVM 启动开销；(3) 与 L4.5.2 机器学习 Python 生态共享运维栈。对照 §5.5 语言栈收敛为「Java（主）+ Python（BI/ML）+ Go（向量/Catalog）+ TS（前端/IDE）」，运营后台 Python/FastAPI 纳入「Python（控制面）」补充声明。
- `Prometheus`：复用 L0 可观测栈（部署清单 v0.1），提供 `container_cpu_usage_seconds_total` / `container_memory_usage_bytes` / PVC 等。
- `封装层`：租户→工作空间映射、套餐→ResourceQuota 落地（已有，本服务调用其 API）。

## 2. 计量采集逻辑（metering）

不独立跑 collector，改为 operations-api 在 `GET /metering` 时**实时聚合 Prometheus**，降低组件数、避免中间存储：

| 指标 | PromQL | 聚合维度 |
| --- | --- | --- |
| CPU 小时 | `sum(increase(container_cpu_usage_seconds_total{namespace=~"ws-$ws"}[30d]))` | tenant→ws |
| 内存 GB 小时 | `sum(increase(container_memory_usage_bytes{namespace=~"ws-$ws"}[30d]))/1e9` | tenant→ws |
| 存储 GB 天 | `sum(kube_persistentvolumeclaim_resource_requests_storage_bytes{namespace=~"ws-$ws"})/1e9` | tenant→ws |
| 作业数 | 封装层 `GET /api/v1/jobs?workspace=$ws` 计数 | ws |
| 查询数 | 统一 SQL 网关指标 `sql_gateway_query_total{ws=$ws}` | ws |

tenant→ws 映射：封装层在 Namespace 打 `tenant=<tid>` 标签，operations-api 经封装层 API 获取；Prometheus 按 namespace 查，再映射回 tenant。

## 3. 账单计算（billing）

`GET /api/v1/admin/bills?tenant=T&month=2026-08`：
```
pkg      = TENANTS[T].package            # 套餐档位
base     = PACKAGES[pkg].price           # 套餐基线价
meter    = metering(T, month_start, month_end)
overflow = 0
if meter.cpuHours  > PACKAGES[pkg].cpu*720:    # 720h/月基线
    overflow += (meter.cpuHours - baseline) * CPU_UNIT_PRICE
if meter.storageGBDays > PACKAGES[pkg].storage*30:
    overflow += (meter.storageGBDays - baseline) * STORAGE_UNIT_PRICE
total = base + overflow
```
单价（`CPU_UNIT_PRICE` / `STORAGE_UNIT_PRICE`）为运营配置，四环境一致。账单不读任何云账单（铁律）。

## 4. 套餐→封装层对接

`POST /api/v1/admin/tenants` 创建租户后，operations-api 调用封装层：
```
POST /api/v1/workspaces  {name: "<tid>-default", quota: PACKAGES[pkg].{cpu,mem,storage}}
```
封装层翻译为 Namespace + ResourceQuota（见封装层 v0.1 R1）。套餐变更同理调封装层更新 Quota。

**SLA 档位**（与运营后台 v0.1 §4.2 一致）：

| 套餐 | CPU | 内存 | 存储 | 节点池 |
| --- | --- | --- | --- | --- |
| base | 8 | 32Gi | 200Gi | 共享 |
| standard | 32 | 128Gi | 1Ti | 共享优先 |
| flagship | 128 | 512Gi | 5Ti | 独占租约 |

## 5. 与现有 deploy/ 的集成

- 部署文件：`deploy/services/operations/k8s.yaml`（Deployment + Service + ServiceMonitor）
- 镜像：`deploy/services/operations/Dockerfile` → 推各环境 registry（复用 build-images.yaml）
- 配置：套餐档位与单价经 ConfigMap / 环境变量注入，四环境一致
- 权限：operations-api 持封装层 admin token，不暴露给客户（L5 平台侧隔离）

---

## 6. 多环境一致性

- 计量 PromQL 四环境相同（kube-state-metrics / cAdvisor 通用）。
- 套餐档位、单价、账单公式四环境一致；公有云环境客户 VM 成本不计入（仅平台内资源）。
- operations-api 本身无状态，四环境同镜像同配置。

---

## 7. 风险与对策（实现层面）

| 风险 | 对策 |
| --- | --- |
| PromQL 在不同 K8s 发行版指标名差异 | 指标名走配置项，Profile 可覆盖 |
| 实时聚合性能（大租户量） | 月度账单改定时预聚合落库；实时仅看板用 |
| tenant 标签缺失 | 封装层强约束 Namespace 打 tenant 标签，preflight 校验 |
| 账单争议 | 计量原始点可回溯（Prometheus 保留期 + 导出） |

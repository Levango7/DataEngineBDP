﻿# L3.1~L3.4 数据治理层（细项）· 详细设计（v0.1）

> 归属：多平台多租户大数据平台 · L3 数据治理层
> 套餐：基础版起含（§11.5.1）
> 对标：阿里 DataWorks 数据治理（标准/质量/血缘/数据地图）/ Cloudera Atlas（元数据+血缘）
> 关联：L3.5 资产目录（元数据/质量/血缘的"展示面"）；L3.7 安全脱敏（敏感定级与审批）；L0.11 封装层；L2.1 统一存储（被治理对象）；L4.1 数据集成 / L4.2 调度编排 / L4.3 数据开发 IDE / L4.4 BI 可视化（消费治理 API）

L3 数据治理层由七个子模块组成，其中 **L3.5 资产目录**、**L3.7 安全脱敏** 已单独成文。本文档细化其余四项：**L3.1 元数据 · L3.2 数据标准 · L3.3 数据质量 · L3.4 血缘**，统一遵循"客户只见治理结果、治理动作经封装层落地"的封装哲学。

---

## L3.1 元数据（Metadata）

### 定位与价值
统一管理技术元数据（schema/统计/血缘）与业务元数据（分层/域/标签/描述/敏感定级），是资产目录（L3.5）与统一 SQL（L2.7）的元数据来源。

### 架构
采集器（引擎 Hook / 定时抽取 / SQL 解析） → 元数据存储（图库 + 关系库） → 元数据服务（注册/更新/查询）。

### 接口契约
```
POST /api/meta/v1/collectors          { engine, ds }            // 注册采集源
POST /api/meta/v1/scan                { scope }                 // 触发扫描
POST /api/meta/v1/entities            { name, type, schema, businessMeta }  // 注册/补全
PUT  /api/meta/v1/entities/{id}       { businessMeta }          // 人工补全
GET  /api/meta/v1/entities/{id}       → 技术+业务元数据
```

### 关键流程
引擎抽取 → 自动建实体 → 人工补业务元数据/标准/脱敏 → 推送到 L3.5 资产目录与 L2.7 catalog。

## L3.2 数据标准（Data Standard）

### 定位与价值
统一字段命名、类型、码值、规则，治理前置，避免"同义不同名"。对标 DataWorks 数据标准。

### 架构
标准项库（Standard Registry） + 落标校验（比对资产字段是否符标）。

### 接口契约
```
POST /api/std/v1/standards            { item, type(主键|枚举|字典|金额), rule, codeValues? }
GET  /api/std/v1/standards            → 标准项列表
POST /api/std/v1/check                { assetId }               // 落标检查
GET  /api/std/v1/compliance           → { rate, byDomain }      // 落标率
```

### 关键流程
定义标准项（如 `user_id: bigint 非空`、`order_status: 待支付/已支付/...`）→ 落标检查比对资产字段 → 不达标资产打标/告警 → 落标率纳入治理看板。

## L3.3 数据质量（Data Quality）

### 定位与价值
规则即校验，异常自动阻断下游并告警，保障湖仓集数据可信。对标 DataWorks 数据质量。

### 架构
规则引擎（非空/唯一/范围/波动/自定义表达式） + 校验调度（嵌入 DAG 或独立定时） + 处置（告警/阻断下游）。

### 接口契约
```
POST /api/dq/v1/rules                 { table, field, checkType, threshold, onFail(告警|阻断下游) }
POST /api/dq/v1/rules/{id}/run        → { pass, rows, detail }
GET  /api/dq/v1/stats                 → { passRate, byRule }
```

### 关键流程
建规则 → 随 DAG 调度或定时运行 → 通过则继续、失败则按 `onFail` 告警或阻断下游 → 质量分回写 L3.5 资产目录。

## L3.4 血缘（Data Lineage）

### 定位与价值
端到端自动采集字段级血缘，影响分析一键追溯。对标 Atlas / DataWorks 血缘。

### 架构
血缘采集器（SQL 解析 / Spark/Flink Lineage Listener / ETL 元数据采集） → 血缘图（有向图，字段级） → 血缘服务（上下游/影响分析）。

### 接口契约
```
POST /api/lineage/v1/collect          { jobId | sql }            // 解析并写入
GET  /api/lineage/v1/{assetId}/upstream    → [ {assetId, level} ]
GET  /api/lineage/v1/{assetId}/downstream  → [ {assetId, level} ]
POST /api/lineage/v1/impact           { assetId }               // 影响分析
```

### 关键流程
作业提交时解析 SQL / 监听引擎执行计划 → 抽取字段级依赖 → 写血缘图 → 资产目录展示上下游、支持影响分析（改上游字段影响哪些下游）。

## 跨组件一致性

| 维度 | 约定 |
| --- | --- |
| 元模型 | L3.1 实体 = L3.5 资产 = L2.7 catalog 条目，单一元模型三处消费 |
| 敏感定级 | L3.1 业务元数据中的 `sensitiveLevel` 驱动 L3.7 脱敏与 L2.7 下推 |
| 质量分 | L3.3 输出 → L3.5 资产质量分 → 客户在目录可见 |
| 血缘 | L3.4 图 → L3.5 资产 `lineageRef` → 影响分析 |
| 封装 | 治理动作（采集/校验/落标）由封装层调度 Pod，客户只见治理结果面板 |
| L4 层消费 | L4.1 调 `/api/meta/v1/entities` 获取 schema；L4.2 调 `/api/dq/v1/rules/{id}/run` 作为 DAG 质量校验节点；L4.3 调 `/api/catalog/v1/assets` 做表名/字段补全；L4.4 调 `/api/catalog/v1/assets/{id}` 获取数据集元模型与敏感级别 |

## L4 层消费治理 API 契约

L3 数据治理层暴露的 REST API 是 L4 数据开发与分析层的一站式治理依赖来源，避免 L4 各租户自写治理逻辑导致规则不可复用。

| L4 模块 | 调用的 L3 API | 用途 | 调用时机 |
| --- | --- | --- | --- |
| L4.1 数据集成 | `GET /api/meta/v1/entities/{id}` | 获取源/目标 schema，自动填充字段映射，避免手工填写易错 | 配置同步任务 Source/Sink 时 |
| L4.1 数据集成 | `POST /api/lineage/v1/collect` | 同步作业提交后回写字段级血缘 | 作业执行成功后 |
| L4.2 调度编排 | `POST /api/dq/v1/rules/{id}/run` | DAG 中"SQL 质量校验"节点调用，规则统一在 L3.3 维护 | DAG 质量校验节点执行时 |
| L4.2 调度编排 | `GET /api/std/v1/check` | 调度前对产出资产做落标检查 | 任务成功后可选 |
| L4.3 数据开发 IDE | `GET /api/catalog/v1/assets?q=` | SQL 编辑器内表名/字段自动补全 | 用户编辑 SQL 时 |
| L4.3 数据开发 IDE | `GET /api/meta/v1/entities/{id}` | IDE 内展示资产 schema 与敏感级别 | 用户查看表结构时 |
| L4.4 BI 可视化 | `GET /api/catalog/v1/assets/{id}` | 建数据集时获取已发布视图与字段敏感级别，避免绕过脱敏 | 建数据集、选字段时 |
| L4.4 BI 可视化 | `GET /api/lineage/v1/{assetId}/downstream` | 数据集影响分析（改字段影响哪些下游仪表盘） | 数据集变更前 |

> 所有调用经 L0.11 封装层鉴权与租户上下文注入；L4 不直连治理服务 Pod，统一经封装层 REST 转发。

## 落地选型

为对齐产品基准 §5.5"12 项选型全部拍板、Java 生态优先、减少语言栈数量"决策，L3.1–L3.4 落地选型如下：

| 子模块 | 选型 | 技术栈 | 决策依据 |
| --- | --- | --- | --- |
| L3.1 元数据 | 自研轻量 Catalog | Java/Go（与封装层/治理层同栈） | §5.5 #2，避免引入 DataHub（Python/Java 双栈，运维重） |
| L3.2 数据标准 | 自研标准项库 + 落标校验引擎 | Java | 与 L3.1 同栈，规则 DSL 化 |
| L3.3 数据质量 | 自研规则引擎 | Java（规则 DSL 化，集成进治理层） | §5.5 #3，Griffin 已 Apache 停孵不可选，Great Expectations 为 Python 栈不纳入 |
| L3.4 血缘 | 自研 SQL 解析 + 引擎 Listener | Java（ANTLR 解析 SQL；Spark/Flink Lineage Listener 走 JVM 侧） | 与 Spark/Flink 同 JVM 生态，Listener 注入无额外语言 |

> 元数据存储：图库 + 关系库（信创环境用国产图库或关系库+ES，不绑单一图库）。
> 所有治理服务以 Java 为主、Go 为辅（Catalog 高并发查询路径可 Go 实现），统一镜像基础，信创 JDK/麒麟/统信适配。

## 部署配置

L3.1–L3.4 治理服务部署参数落地于 `design/deploy/values/governance-values.yaml`，由封装层 Helm Operator 渲染。关键配置块：

```yaml
# governance-values.yaml（节选）
governance:
  catalog:                # L3.1 元数据（自研轻量 Catalog）
    image: sq-governance-catalog:0.1.0
    replicas: 2
    resources:
      requests: { cpu: "1", memory: "2Gi" }
      limits:   { cpu: "2", memory: "4Gi" }
  standard:               # L3.2 数据标准
    image: sq-governance-standard:0.1.0
    replicas: 2
  quality:                # L3.3 数据质量
    image: sq-governance-quality:0.1.0
    replicas: 2
    ruleEngine: { dsl: "java", maxParallel: 8 }
  lineage:                # L3.4 血缘
    image: sq-governance-lineage:0.1.0
    replicas: 2
    parser: { sql: "antlr", listeners: ["spark","flink"] }
  storage:
    graph: { type: "nebula", profile: "default" }   # 信创 Profile 切国产图库
    relational: { type: "postgresql" }
  tierProfiles:
    base:      { replicas: 1, resources: "small" }
    standard:  { replicas: 2, resources: "medium" }
    flagship:  { replicas: 3, resources: "large" }
```

> 资源配额说明：`resources` 中 quota 为单组件上限，平台总额度见 §11.5.2，由封装层 ResourceQuota 在租户级聚合约束（非所有组件同时满载，故单组件配额之和可略超平台总额度）。

## 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 元数据滞后 | 目录不准 | 采集频率可调 + 血缘校验 |
| 落标率虚高 | 治理走过场 | 标准项强制引用 + 抽样审计 |
| 质量规则误杀 | 正常数据被阻断 | `onFail` 分级 + 人工复核通道 |
| 血缘断点 | 影响分析不全 | 增强 SQL 解析 + 引擎 Listener + 缺失提示 |

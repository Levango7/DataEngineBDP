# L0.11 K8s 产品化封装层 · 详细设计（v0.1）

> 所属：多平台多租户大数据平台 · 产品原型设计 v0.5 → 详细设计首项
> 归属：L0 云原生底座层
> 套餐：基础版（三档全含）
> 定位：L0 自建云原生底座之上的"翻译与黑盒"层，是平台知识产权核心
> 目标：把客户视角的「工作空间 / 数据项目 / 计算任务 / 套餐配额」翻译成 Kubernetes 资源，并对客户完全隐藏容器、Pod、编排概念。
> 关联：L0.6 SKE 控制面（封装其 K8s API）；L0.8 容器存储（PVC 翻译）；L0.9 可观测基座（看板视图封装）；L0.12 弹性调度（HPA/KEDA/配额翻译）；L2.* 引擎层（业务 API 消费方）；L5.* 控制台（RBAC 与视图入口）

---

## 1. 定位与职责

封装层（Encapsulation Layer）位于 **L0 自研 SKE（K8s 发行版）** 与 **L2~L5 业务层** 之间，承担四类职责：

| 职责 | 说明 |
| --- | --- |
| 抽象门面 | 对上暴露业务语义 API（Workspace / Project / Task / Quota），对下只调用 SKE K8s API / Operator。业务层绝不直连 K8s。 |
| 资源翻译 | 将客户概念 1:N 映射为 Namespace / Quota / Deployment / Operator CR 等，规则集中可审计。 |
| 黑盒运维 | 自愈、扩容、调度、滚动升级由封装层自动完成，客户只见「变快 / 持续可用」。 |
| 安全收敛 | 客户无 K8s API / kubeconfig 权限，仅有控制台 RBAC 内的业务操作权限。 |

**设计铁律**：业务层与适配驱动都只依赖封装层接口，永不感知 Pod、容器、节点、etcd。这保证「SKE 透明封装、客户无感知」与「一套主代码多环境交付」同时成立。

## 2. 客户概念 ↔ Kubernetes 资源映射总表

| 客户概念 | K8s / 平台资源 | 关键约束 |
| --- | --- | --- |
| 工作空间 Workspace | `Namespace` + `ResourceQuota` + `LimitRange` + `NetworkPolicy` + 标签 `tenant-id` / `ws-id` | 租户间网络隔离；配额硬上限 |
| 套餐 / 容量 | `ResourceQuota` + 节点池租约 `NodePoolLease`(CRD) + `HPASpec` | 超额自动扩容或升级套餐，不超租约 |
| 数据项目 Project | `Label ws-id` 下的 `Deployment`/`StatefulSet`/`Job` + 存储前缀 `bucket/<ws>/<proj>/` + `RoleBinding` | 项目级 RBAC；存储逻辑隔离 |
| 计算任务 Task（批） | `SparkApplication`(Spark Operator CR) 或 `CronJob` + `Job` | 客户只见「任务」，不见 Pod |
| 计算任务 Task（流） | `FlinkDeployment`(Flink Operator CR) | 持续运行，封装层保活 |
| 数据集 / 表 | 对象存储前缀 + `Iceberg` 元数据（`Catalog`） | 经统一存储抽象，不暴露桶细节 |
| 作业调度 | `Workflow`(Argo/DolphinScheduler 适配) / `CronJob` | 封装为「调度计划」 |
| 监控 / 告警 | `Prometheus` `ServiceMonitor` + 封装层指标导出 | 客户只见业务指标，不见 K8s 指标名 |
| 扩容 / 高可用 | `HPA` / `KEDA` + 多副本 + 反亲和 | 全自动，客户无感知 |

## 3. 核心接口契约（业务语义 API）

封装层作为对上暴露业务语义 API 的门面，统一 REST 路径前缀为 **`/api/encaps/v1/`**；下游子模块接口（L0.8 `/api/storage/v1/`、L0.12 `/api/elastic/v1/` 等）均经封装层翻译后挂入门面之下，业务层不直连子模块路径。以下为封装层对业务层暴露的契约草案（以 OpenAPI 风格描述，实现可用 Go/Java）：

| 业务对象 | REST 端点（门面前缀 `/api/encaps/v1/`） | 说明 |
| --- | --- | --- |
| Workspace | `POST/GET/DELETE /api/encaps/v1/workspaces[/{id}]` | 工作空间 CRUD |
| Project | `POST/GET/DELETE /api/encaps/v1/workspaces/{wsId}/projects[/{id}]` | 数据项目 CRUD |
| Task | `POST/GET /api/encaps/v1/projects/{projId}/tasks[/{id}]` | 计算任务提交与查询 |
| Quota | `GET/PUT /api/encaps/v1/workspaces/{id}/quota` | 套餐配额查询与调整 |
| Storage（翻译 L0.8） | `POST/GET /api/encaps/v1/workspaces/{id}/volumes[/{vid}]` | 经封装层翻译为 L0.8 `/api/storage/v1/volumes` |
| Elastic（翻译 L0.12） | `POST/GET /api/encaps/v1/workspaces/{id}/policies` | 经封装层翻译为 L0.12 `/api/elastic/v1/policies` |

### 3.1 Workspace（工作空间）
```yaml
Workspace:
  id:            string            # 平台生成，全局唯一
  name:          string            # 客户命名，如「华东生产集群」
  tenantId:      string            # 所属租户（内部/外部）
  tier:          enum              # 套餐: internal | standard | enterprise | flagship
  quota:         QuotaSpec         # 容量边界
  networkPolicy: enum              # isolated(默认) | peering(跨 ws 互通,需审批)
  status:        enum              # provisioning | running | suspended | error
  createdAt:     datetime

QuotaSpec:
  cpuCores:      int               # 如 800
  memoryGB:      int               # 如 3072
  storageGB:     int               # 如 1048576 (1PB)
  maxProjects:   int               # 项目数上限
  autoScaleOut:  bool              # 超额自动扩容(计费另计) 或 拒绝
```

### 3.2 Project（数据项目）
```yaml
Project:
  id:            string
  workspaceId:   string            # 所属工作空间
  name:          string
  domain:        string            # 业务域，如 交易/营销/风控
  rbac:          list<RoleBinding> # 项目内角色: owner/dev/reader
  storagePrefix: string            # bucket/<ws>/<proj>/
  status:        enum              # active | paused | archived
```

### 3.3 Task（计算任务）
```yaml
Task:
  id:            string
  projectId:     string
  type:          enum              # batch | stream
  engine:        enum              # spark | flink | trino
  specRef:       string            # 指向作业定义(SQL/DAG)的存储引用
  schedule:      string            # cron(可选)；流任务为空
  resources:     TaskResource       # 该任务的算力请求(受 Quota 约束)
  status:        enum              # pending | running | success | failed | suspended

TaskResource:
  cpuCores:      int
  memoryGB:      int
  parallelism:   int               # 流任务并发度
```

### 3.4 平台内部 CRD（客户不可见）
```yaml
NodePoolLease:                   # 节点池租约，保障套餐容量
  wsId:          string
  guaranteedCpu: int
  guaranteedMem: int
  burstAllowed:   bool

WorkspaceRuntime:                # 封装层内部状态机，驱动翻译
  wsId:          string
  phase:         enum            # 对应 Workspace.status
  translated:    list<K8sObjectRef>
```

## 4. 翻译规则（Translation Rules）

翻译是封装层的核心算法，集中实现、可单测、可审计。规则摘要：

| 规则 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| R1 建空间 | `CreateWorkspace` | `Namespace` + `ResourceQuota` + `NetworkPolicy`(deny-all) + 标签 | 命名 `ws-<hash>`；配额按 `QuotaSpec` 设硬上限 |
| R2 建项目 | `CreateProject` | 打 `ws-id`/`proj-id` 标签 + 建存储前缀 + `RoleBinding` | 不新建 NS，复用工作空间 NS，靠标签隔离 |
| R3 提批作业 | `SubmitTask(batch)` | `SparkApplication` CR（Spark Operator 接管 Pod 生命周期） | 客户只见 Task 状态，Pod 由 Operator 管 |
| R4 提流作业 | `SubmitTask(stream)` | `FlinkDeployment` CR + 保活探针 | 失败由封装层重启，状态回写 Task |
| R5 调度 | `Schedule(cron)` | `CronJob` 包装 `SparkApplication` / `Workflow` | 封装为「调度计划」 |
| R6 扩容 | `Quota > 80%` 或 `autoScaleOut` | 调 `NodePoolLease` 扩容 + 更新 `ResourceQuota` | 客户只见「容量增加」，无操作感 |
| R7 隔离 | `NetworkPolicy` | 默认 deny-all，仅放行同 NS + 必要出口 | 租户间零互通，满足合规 |
| R8 计量 | 周期采集 `ResourceQuota` 用量 + 作业时长 | 账单事件 | 与 K8s 解耦，按套餐核算 |

**一致性保证**：同一 `Workspace` 在信创/本地/云 VM 四环境下，翻译出的 K8s 对象集合与标签约定**完全一致**，差异仅在 L0 供应层与 L0 适配驱动（镜像 arch、存储后端、KMS）。

## 5. 关键流程

### 5.1 创建工作空间
```
客户(控制台) → POST /workspaces
  → 封装层校验租户套餐/配额余量
  → R1: 创建 Namespace + ResourceQuota + NetworkPolicy
  → 预留 NodePoolLease(若套餐含保底)
  → 回写 Workspace.status=running
客户只见：「华东生产集群 已就绪」
```

### 5.2 创建数据项目
```
POST /workspaces/{id}/projects
  → R2: 打标签 + 建存储前缀 + RoleBinding
  → 注册到 Catalog(资产目录)
客户只见：「交易域 项目已创建，可建数据集/作业」
```

### 5.3 提交计算任务
```
POST /projects/{id}/tasks  (type=batch, engine=spark, specRef=...)
  → 校验 TaskResource ≤ 剩余 Quota
  → R3: 创建 SparkApplication CR
  → Operator 拉起 Pod(客户不可见)
  → 轮询 CR 状态 → 回写 Task.status
客户只见：「作业 运行中 / 成功 / 失败」
```

### 5.4 自动扩容（客户无感知）
```
监控检测到 CPU 78% → 触发 R6
  → 调 NodePoolLease 扩容(云VM: 加节点; 本地: 释放预留; 信创: 启用备用节点)
  → 更新 ResourceQuota
  → 仅平台运维视图可见「扩容中」，客户控制台无提示或仅「容量已优化」
```

### 5.5 故障自愈（客户无感知）
```
Pod 崩溃 / 节点宕机
  → K8s 调度器 + Operator 重建
  → 封装层将结果归一为 Task.status
  → 若持续失败则升级为 Task.status=failed 并告警(客户可见)
```

## 6. 安全收敛（客户无 K8s API）

- 客户**不持有 kubeconfig**，无 `kubectl`、无 Dashboard 直连。
- 唯一入口为封装层业务 API + 控制台 RBAC；所有写操作经封装层翻译，受 `Quota` 与 `NetworkPolicy` 双重约束。
- 平台运维持有 K8s 权限，但仅通过运营后台(§admin 视图)操作，且操作留痕审计。
- 多租户加密：存储/传输加密按环境 Profile 选国密或标准算法，对客户透明。

---

## 7. 多环境一致性

封装层是「一套主代码多环境」的关键枢纽：

- **业务 API 不变**：四环境下 Workspace/Project/Task/Quota 契约完全一致。
- **翻译输出不变**：R1~R8 规则四环境同构，仅底层驱动不同（见 v0.5 §5.3 环境适配框架）。
- **差异收敛点**：镜像 arch（amd64/arm64/国产 OS 变体）、存储后端（国产对象存储/S3/MinIO）、KMS（国密卡/Vault）、弹性（节点池实现）。这些由适配驱动在 R1/R6 内部按 Profile 选择，不污染翻译逻辑。
- **部署形态**：封装层本身以 Deployment 部署于每个 SKE K8s 集群，由 SKE installer（基于 kubeadm 二次封装，非 KubeSphere/RKE2 原样）统一拉起，对齐 §5.5 决策1 自研 SKE 路线与 `ske/manifests/kubeadm-config.yaml` 实际实现。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 翻译层黑盒导致排障难 | 客户/运维定位慢 | 封装层输出结构化翻译日志 + WorkspaceRuntime 状态机可追溯 |
| 配额超卖导致租户争抢 | 性能互扰 | NodePoolLease 保底 + ResourceQuota 硬限 + 调度优先级 |
| Operator 版本与 K8s 不兼容 | 作业起不来 | 锁定 Operator 版本矩阵，CI 多环境冒烟 |
| 国密/标准切换出错 | 合规失败 | preflight 能力探测 + Profile 强校验，禁用混用 |
| 封装层自身故障 | 全平台不可控 | 封装层多副本 + 自愈 + 与业务 API 解耦，故障不影响已运行作业 |

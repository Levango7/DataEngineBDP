# L2.8 消息与流接入（Kafka）· 详细设计（v0.1）

> 归属：多平台多租户大数据平台 · L2 大数据引擎层
> 适用套餐：标准版、旗舰版（基础版不含，对齐 §11.5.1 套餐矩阵）
> 对标：Apache Kafka 3.x（KRaft 模式）/ Confluent Platform / 阿里云 MQ for Kafka
> 关联：L0.11 封装层（Strimzi Operator 部署/配额/隔离）；L2.3 Flink（消费 Kafka 做流算/CDC）；L4.1 数据集成（Kafka 作源/汇）

## 1. 定位与价值

消息与流接入是平台的**实时解耦枢纽**：以 Apache Kafka 承载系统间异步解耦、削峰填谷与 CDC 缓冲，上游生产者写 Topic，下游 Flink/数据集成按订阅消费，流批一体不丢不重。

客户价值：
- "实时入湖"——业务库 CDC 先入 Kafka 缓冲，Flink 消费写 Iceberg，源端零侵入。
- "削峰填谷"——秒级峰值先落 Kafka 分区，下游按自身节奏消费，保护计算与存储。
- "解耦演进"——上下游各自扩缩容、Schema 演进，互不阻塞。

平台价值：
- Kafka 集群经 **Strimzi Kafka Operator** 部署到自研 SKE K8s，客户无感知 K8s。
- **KRaft 模式去 ZooKeeper**，组件数减一，运维与启动链路更短，ARM/x86 同构。
- 多租户隔离收敛到封装层，客户只见"Topic / 消息用量 / 消费延迟"。

## 2. 总体架构

```text
┌──────── 上游生产者（写 Topic） ────────┐
│  业务库 CDC(Debezium)   业务事件   IoT 边端   日志 Agent  │
└──────────────────────┬──────────────────────────┘
                        ▼
┌──────── Kafka 集群（KRaft on K8s，Strimzi 管理） ────────┐
│  Broker(含 Controller) × N   分区/副本/ISR   日志存 SKE NVMe │
│  Topic: tenant.app.topic.vN   Schema Registry(Avro)         │
└──────────────────────┬──────────────────────────┘
                        ▼
┌──────── 下游消费者（按订阅） ────────┐
│  Flink(流算/CDC→Iceberg)   数据集成(Kafka→Doris/数仓)   │
└──────────────────────────────────────────────────────────┘
        ▲ 统一经封装层 REST/CR 管理，客户不直连 K8s/Kafka 原生端口
```

## 3. K8s 集成（Strimzi + KRaft）

Kafka 集群以 Strimzi `Kafka` CR 声明式部署到 SKE K8s，控制面由封装层下发，客户不直接操作 CR。

```yaml
# deployment.yaml：Strimzi Kafka CR（KRaft，去 ZooKeeper）
apiVersion: kafka.strimzi.io/v1beta2
kind: Kafka
metadata: { name: sq-kafka, namespace: sq-msg }
spec:
  kafka:
    replicas: 3
    storage: { type: jbod, volumes: [{ id: 0, type: persistent-claim, size: 200Gi, class: ske-nvme }] }
    authorization: { type: simple }            # ACL 多租户
    listeners:
      - name: plain, port: 9092, type: internal, tls: false
      - name: tls,  port: 9093, type: internal, tls: true
    config:
      process.roles: broker,controller          # KRaft 合并角色
      default.replication.factor: 3
      min.insync.replicas: 2
      auto.create.topics.enable: false          # 经封装层白名单创建
  entityOperator: { topicOperator: {}, userOperator: {} }   # Topic/User CR 自动同步
```

- **KRaft 去 ZooKeeper**：元数据写入 Kafka 内部 Topic，无 ZK 集群，启动与升级链路更短。
- **Topic 自动创建**：禁用 Broker 自动建 Topic，由封装层下发 `KafkaTopic` CR 白名单创建，命名/分区/副本受租户配额约束。
- **Schema Registry**：旁路部署 Avro Schema Registry，生产/消费按 subject 注册演进，避免脏数据反序列化失败。

## 4. 多租户隔离

- **Topic 命名规范**：`<tenant>.<app>.<topic>.vN`，前缀即租户边界，跨租户不可见、不可订阅。
- **ACL（SimpleAclAuthorizer）**：经 `KafkaUser` CR 为每租户颁发 SCRAM/TLS 用户，仅授权本租户前缀 Topic 的读/写/Describe。
- **配额**：按 user 维度设 `producer_byte_rate` / `consumer_byte_rate` / `request_percentage`，超额限流不阻断，受工作空间 ResourceQuota 上限约束。
- **NetworkPolicy**：Broker Pod 入向只放行本租户命名空间与下游 Flink/数据集成命名空间，跨租户网络层隔离。

| 隔离维度 | 机制 | 粒度 |
| --- | --- | --- |
| Topic 可见性 | 命名前缀 + ACL | 租户 |
| 流量 | user 配额 | 租户/应用 |
| 网络 | NetworkPolicy | 命名空间 |
| 资源 | ResourceQuota/CPU/存储 | 工作空间 |

## 5. 接口契约（经封装层 REST）

```
POST /api/msg/v1/topics                 { name, partitions, replicas, retentionMs } → 建 Topic
GET  /api/msg/v1/topics                 ?tenant=&prefix= → [{name, partitions, lag}]
POST /api/msg/v1/topics/{t}/produce     { records[] }                  → {offsets[]}
POST /api/msg/v1/topics/{t}/consume     { groupId, maxRecords }        → {records[]}
GET  /api/msg/v1/topics/{t}/lag         ?groupId= → { partitionLag[] }
POST /api/msg/v1/users                  { tenant, auth:scram|tls }     → {user, secretRef }
```

> 原生 Kafka 端口不直接暴露给客户；生产/消费可走封装层 REST（轻量）或经鉴权后直连 Broker（高吞吐，Flink/数据集成场景）。

## 6. 关键流程

1. **生产**：生产者按 `acks=all` 写 Leader 副本，Broker 追加到分区日志（SKE NVMe 顺序写）。
2. **复制**：Follower 从 Leader 拉取日志，落 ISR 集合；`min.insync.replicas=2` 保证写入多数派持久。
3. **存储**：分区日志分段落盘，按 `retention.ms`/`segment.bytes` 滚动删除，无 TTL 误删。
4. **消费**：消费者组按分区拉取、提交 offset；封装层暴露 lag 监控，下游 Flink/数据集成按订阅消费。
5. **故障切换**：Leader 宕 Controller 触发重选举，ISR 内副本升 Leader，客户端重连续传，不丢不重。

## 7. 资源与调优

| 参数 | 推荐值 | 说明 |
| --- | --- | --- |
| 分区数 | 按吞吐 ≈ 生产者数 × 2~3 | 过多增开销，过少限并发 |
| `default.replication.factor` | 基础版=1 / 标准版以上=3 | 套餐分档：基础版 RF=1（无副本容错，仅演示/小规模）；标准版/旗舰版 RF=3（容忍 1 副本宕，故障切换不丢不重） |
| `min.insync.replicas` | 基础版=1 / 标准版以上=2 | `acks=all` 下持久多数派；基础版 RF=1 时 min.isr=1 仅持久单副本 |
| `log.flush.interval.messages` | 默认（依赖 OS page cache） | NVMe 下不必强刷 |
| `retention.ms` | 按业务 24h~7d | CDC 缓冲可短，事件流可长 |

> 套餐分档说明：基础版 Kafka RF=1（单副本无容错，仅用于演示/小规模场景，不承诺"故障切换不丢不重"）；标准版/旗舰版 RF=3 + min.isr=2（多副本高可用，满足故障切换不丢不重承诺）。对应 kafka-values.yaml `tierProfiles.base.replicationFactor: 1` / `tierProfiles.standard.replicationFactor: 3`。

- **SKE NVMe 加速**：Broker 日志目录挂 `ske-nvme` StorageClass，顺序写延迟 <1ms，副本同步快、ISR 稳。
- **JBOD 多盘**：多分区跨盘打散，单盘故障只丢部分分区，副本自动重建。

## 8. 多环境适配

- 四环境（信创/本地/公有云/私有云）Kafka 集群均由 Strimzi 部署到 SKE K8s，CR 与配置同构。
- 信创环境优先国产 ARM 节点 + 国产 NVMe；公有云 VM 上不启用云托管 Kafka（保持可迁移、不锁云）。
- 跨环境迁移走 Topic 镜像（MirrorMaker2，Strimzi 内置），按租户前缀粒度复制，RPO 可控。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 分区不均/热点 | 部分副本过载、lag 倾斜 | 按 key hash 分区 + 监控 lag，必要时 Reassign Partitions |
| 消息积压 | 下游追不上、延迟升高 | lag 告警 + 下游 Flink/集成自动扩并发，必要时临时扩分区 |
| Schema 演进冲突 | 消费反序列化失败 | Schema Registry 强校验 + BACKWARD 兼容策略 |
| KRaft 元数据丢失 | 集群不可用 | Controller 副本 ≥3 + 元数据快照定期备份到对象存储 |
| 跨租户越权 | 数据泄露 | 命名前缀 + ACL + NetworkPolicy 三重隔离，定期审计 |

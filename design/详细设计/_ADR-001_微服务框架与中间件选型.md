## 1. 背景

DataEngineBDP 为多语言微服务平台：41 个独立部署单元（口径定义见 [docs/模块数口径定义.md](../../docs/模块数口径定义.md)；Java×24 pom 工程 / Go×9 / Python×12），
统一部署于自研 SKE(K8s) 集群，Helm Chart + ArgoCD GitOps 交付。服务间调用为 REST over K8s Service DNS
（如 `http://trino-service:8080`），认证走 Keycloak OIDC/JWT，观测栈 Prometheus/Loki/Grafana/OTEL 就绪。

本 ADR 回答三个悬而未决的选型问题：

1. Java 微服务体系走 SCA(Spring Cloud Alibaba)、Dubbo 还是维持现状？
2. 配置中心选 Apollo 还是 Nacos？（原 §3 决策维持 Apollo，已据主流优先原则改选 Nacos，详见 §3）
3. 熔断器如何补齐？（当前仅 llm-gateway 对 LLM 上游有局部熔断实现）

## 2. 决策一：微服务框架路线 —— 维持「K8s 原生微服务 + REST」主线

### 2.1 候选项

| 项 | 内容 |
|----|------|
| A | SCA 全家桶（Nacos 注册配置 + Sentinel + Seata + Gateway + OpenFeign） |
| B | Dubbo 3 全局化（应用级服务发现 + Triple/gRPC 协议） |
| C | **K8s 原生主线 + Java 侧轻量吸收（选定）** |

### 2.2 对比要点

| 维度 | A · SCA | B · Dubbo 3 | C · K8s 原生 |
|------|---------|-------------|--------------|
| 多语言覆盖 | 仅 Java（19 个 Go/Python 服务不适用） | Triple 协议跨语言叙事较好，但 Go/Python SDK 生态弱于 gRPC 主线 | 天然全语言（HTTP 是共同语言） |
| 与现有 K8s 体系关系 | Nacos 与 Service/CoreDNS **职责重叠，双注册中心并存** | 应用级发现仍需与 Service 协调 | 零冲突 |
| 改造成本 | 20+ 服务接口层重写（REST→Feign） | 同左，另加 IDL 定义 | 零 |
| 性能收益依据 | 无瓶颈证据 | 无瓶颈证据 | — |
| 信创叙事 | 阿里系组件常见于信创项目 | Apache 顶级项目，叙事略优 | 中立 |

### 2.3 决策与理由

**选 C**。理由：

1. **多语言占比否决 Java 系统一方案**：非 Java 服务占约 46%，任何 Java 框架都只能覆盖一半体系，
   强行统一将产生两套异构运维模式。
2. **K8s 已提供注册发现/负载均衡**：引入 Nacos/Dubbo 注册中心属于重复建设，并新增有状态故障域。
3. **成本收益倒挂**：当前无性能瓶颈证据、无跨库强事务需求（SQLite/PG 单库+最终一致满足 MVP），
   全量接口层改造的收益无法成立。

### 2.4 后果与配套约定

- 正向：避免双注册中心、避免 20+ 服务重写、保留未来按服务粒度引入 RPC 的自由度。
- 代价：放弃 SCA/Dubbo 的声明式编程便利，Java 间调用继续手写 HTTP 客户端样板。
- 缓解：Spring 6 自带 `@HttpExchange` + `RestClient` 提供声明式体验，零新依赖零生态绑定；
  若个别热点链路实测需要 RPC，允许**单点**引入 gRPC（Protobuf 契约先行），不允许框架级全局化。

## 3. 决策二：配置中心 —— 选 Nacos，替换 Apollo

### 3.1 能力对比（分维度）

| 维度 | Apollo | Nacos |
|------|:---:|:---:|
| 发布审批流 / 权限 / 审计日志 | ✅ 企业级内置 | ❌ 无内置审批 |
| 灰度发布 / 版本回滚 | ✅ 成熟精细 | ⚠️ Beta 发布可用 |
| 多环境多集群模型 | ✅ App-Cluster-Namespace 三级 | ⚠️ Namespace 单层 |
| 注册中心 | ❌ 不具备 | ✅ 核心强项 |
| 多语言客户端生态 | ⚠️ 一般 | ✅ 较好 |
| 生产部署形态 | 三件套(Portal/Admin/Config)+MySQL | ≥3 节点集群+MySQL（**两者都依赖 MySQL**） |
| 资源基线 | ≈0.6C/1.5Gi 起 | ≈0.5C×3/1Gi 起 |
| 信创叙事 | 携程系，信创项目常见 | 阿里系 + Apache 顶级，略优 |

> 「哪个能力强就用哪个」的答案必须分维度：**配置中心本体能力 Apollo 强**（治理/审计/灰度）；
> **Nacos 的强项是注册中心，而本项目该职责已由 K8s 承担**。

### 3.2 本项目语境加权

- 配置消费方现状：**19 个 Go/Python 服务全部 ENV 注入（Helm values → Deployment env），零直连配置中心**；
  22 个 pom.xml 中 `apollo-client`/`nacos-client` 依赖均为零 —— 配置中心目前是纯设计资产，代码侧零绑定。
- 因此 Nacos 的差异化优势（注册中心、多语言 SDK）在本项目**注册中心职责无用武之地**（已由 K8s 承担）；
  但其作为 SCA 生态入口 + Apache 顶级项目的主流度、以及多语言 ENV 注入零绑定的兼容性，恰与平台多语言（Java/Go/Python）演进方向匹配。

### 3.3 切换成本评估（已执行：Apollo → Nacos）

现状投入盘点：原 charts/apollo 一个经两轮安全审核的 chart + 11 个文件引用；本地/GitOps 链路均未启用。

表：Apollo→Nacos 切换工作项与实际成本

| 工作项 | 估算 |
|--------|------|
| 归档 apollo chart + 新建 nacos StatefulSet chart（含探针/资源/安全上下文，达现行 chart 标准） | 2–4h |
| umbrella Chart.yaml/values + env{dev,staging,prod} + local values 引用更新 | 1h |
| 11 个设计文档引用修订 | 1h |
| Java 接入（22 个 pom + bootstrap.yml，每服务 10–20 行；可先核心链路） | 2–3h |
| **合计** | **≈1 人日，低风险（无数据迁移）** |

结论：切换便宜且主流度收益成立。Nacos 作为 SCA 生态入口 + Apache 顶级项目更主流；兼容性全绿（Spring Boot 3.2 / Java 17 / K8s 原生 / 多语言 ENV 注入均兼容）。判定为正收益，已执行切换。

### 3.4 决策与复审触发

**选 Nacos**（chart 已新建：standalone 模式 Derby 内嵌 DB 零外部依赖；鉴权 fail-fast 强制注入 tokenSecretKey，非 root 运行 + 资源配额 + 探针齐备，达现行 chart 质量标准）。

决策理由（主流优先原则）：
1. Nacos 作为 SCA 生态入口 + Apache 顶级项目，社区活跃度与主流度高于 Apollo；
2. 兼容性全绿（Spring Boot 3.2 / Java 17 / K8s 原生 / 多语言 ENV 注入均兼容）；
3. 切换成本约 1 人日，已执行（apollo chart 归档 + nacos chart 新建 + 引用修订）。

重新评估触发条件（满足任一即重开本决策）：
1. Nacos 鉴权/治理能力无法支撑平台企业交付（多租户计费、运营后台的审批/审计需求）；
2. 出现 ≥3 个 Go/Python 服务需要运行时动态配置且 Nacos SDK 不满足；
3. Nacos 运维成本实际超出预期（如 cluster 模式 MySQL 依赖成为负担）。

## 4. 决策三：熔断器 —— Resilience4j（应用内）+ APISIX api-breaker（网关层）双层

| 层 | 组件 | 说明 |
|----|------|------|
| 南北向（外部流量） | APISIX `api-breaker` 插件 | 启用 APISIX 时一并配置，纯配置零代码 |
| 东西向（服务互调，Java） | **Resilience4j** | 纯库、无中心依赖；不用 Sentinel（其 Dashboard/规则推送体系超出当前团队规模） |
| 东西向（Go） | gobreaker（按需） | 仅对已知不稳定依赖引入 |
| 已有 | llm-gateway provider 熔断 | 保留 |

分布式事务：暂不引入 Seata。触发重评条件同 §8：出现真实跨库强一致场景。

## 5. 三语言选型原则

DataEngineBDP 采用 Java 17 / Go 1.22+ / Python 3.11 三语言栈，各语言有明确职责边界与选型依据，新组件语言选择须遵循本节决策树。

### 5.1 语言职责定义

| 语言 | 职责边界 | 选型依据 | 代表组件 |
| --- | --- | --- | --- |
| **Java 17** | 主服务 / 治理 / 封装层 | Spring Boot 3.2.x 生态成熟（JPA / Security / WebFlux / OpenTelemetry），企业级治理能力完备（事务 / 审计 / 租户隔离），K8s client（fabric8）与国密（BouncyCastle）支持完善 | encaps-layer、sql-gateway、rule-engine、governance、tag-engine、infra-orchestrator、finops |
| **Go 1.22+** | CLI 工具 / 网关 / 轻量服务 | 编译单二进制（无 JVM 开销，启动毫秒级），交叉编译便利（信创 ARM64 一键构建），Gin 框架轻量高效，GORM 提供类型安全 ORM | catalog、llm-gateway、vector-engine、dqctl、ai-assistant、observability、karmada-api |
| **Python 3.11** | AI / 数据 / 模板 / 运营 | FastAPI + Pydantic 异步高性能且类型安全，ML 生态丰富（sklearn / MLflow / LLaMA-Factory），数据科学工具链完备（pandas / pydantic 模型校验），行业模板 DDL/DAG 自然表达 | knowledge-engine、nl2sql、batch-pipeline、llmops、ml-platform、model-finetuning、operations-api、industry-templates |

### 5.3 语言选型决策树（新组件）

```
新组件需要选择语言？
│
├── 是否为 ML / AI / 数据科学 / 模板资产业务？
│   └── 是 → Python 3.11（FastAPI + Pydantic）
│
├── 是否为 CLI 工具 / 网关 / 极低延迟轻量服务？
│   └── 是 → Go 1.22+（Gin / cobra，单二进制）
│
├── 是否需要 K8s 资源翻译 / JPA 事务 / Spring Security 鉴权 / 云 SDK？
│   └── 是 → Java 17（Spring Boot 3.2.x）
│
└── 混合场景？
    ├── 计算密集 + 低延迟 → Go
    ├── 企业治理 + 事务 → Java
    └── ML / 数据 → Python
```

- **禁止**：同一组件混用多语言（除 governance/finops/karmada 子模块按职责拆分外）。
- **禁止**：引入 Java 17 / Go 1.22+ / Python 3.11 以外的后端语言（TS 仅限前端/IDE）。

## 6. 六件套盘点结论（速查表）

| 组件 | 结论 | 承载方 |
|------|------|--------|
| API 网关 | ✅ 已就绪待启用 | APISIX（X4 设计 + chart），umbrella 默认关闭 |
| 服务注册 | ✅ K8s 白送 | Service 即注册表 |
| 服务发现 | ✅ K8s 白送 | CoreDNS 解析 service DNS |
| 配置中心 | ✅ 已就绪待启用 | **Nacos**（本 ADR §3 决策选 Nacos，已替换 Apollo） |
| 负载均衡 | ✅ 双层齐备 | 东西向 kube-proxy / 南北向 APISIX Ingress |
| 熔断器 | ⚠️ 唯一缺口 | 按 §4 双层方案补齐 |

## 7. 执行路径

1. 现在：本 ADR 归档；熔断方案写入各服务 backlog（Resilience4j 引入随真实联调启动）。
2. 联调期：启用 Nacos（tokenSecretKey Secret 注入，fail-fast 强制）+ APISIX（含 api-breaker），均为 umbrella values 开关级操作。
3. 流量期：按不稳定依赖清单选择性加 gobreaker；出现性能瓶颈再评估单点 gRPC。

## 8. 本 ADR 整体重评触发条件

- 任一服务出现实测性能瓶颈且定位为 REST 序列化开销；
- 组织强制统一 SCA/Dubbo 技术栈；
- 放弃 K8s 自管集群转向托管非 K8s 平台；
- §3.4 所列任一条件成立。

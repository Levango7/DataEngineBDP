## 第1章 等保三级标准解读（GB/T 22239-2019）

### 1.0 标准概述

GB/T 22239-2019《信息安全等级保护基本要求》将等级保护对象由低到高分为五级，第三级适用于"受到破坏会对社会秩序和公共利益造成严重损害，或者对国家安全造成损害的公民、法人和其他组织的合法权益"的系统。第三级要求在二级基础上增加"安全标记""剩余信息保护""抗抵赖""软件容错""资源控制""代码安全"等增强项，并要求"应能够检测到对物理边界、网络边界、主机边界、应用边界、数据边界的入侵行为，并能及时报警"。

数据引擎大数据平台作为面向政企客户提供数据采集、治理、分析、流通全链路能力的数据操作系统，承载客户核心数据资产，按第三级要求进行合规建设。本章按 GB/T 22239-2019 第三级要求的 6 类控制项（物理安全、网络安全、主机安全、应用安全、数据安全、管理安全）逐条解读，并给出平台适用性分析。

> 解读体例：每条控制项按"标准要求 → 平台适用性分析"两段式描述。标准要求引用 GB/T 22239-2019 原文要点；平台适用性分析结合数据引擎大数据平台 V2.0 架构（L0-L5 五层 + X 横切层）、四环境交付形态（信创/本地/公有云/私有云）、组件技术栈给出落地判断。

### 1.1 物理安全

#### 1.1.1 物理访问控制

- **标准要求**：机房应划分区域进行管理，重要区域应设置电子门禁、视频监控，进入机房的人员应经过审批并记录；机房出入口应配置控制装置，对人员进出进行登记。
- **平台适用性分析**：数据引擎大数据平台为软件平台，不自带机房。物理访问控制由部署环境方负责：信创环境由客户机房物理安全体系承担；本地数据中心由客户数据中心承担；公有云 VM 由云厂商数据中心承担（如华为云 T3+ 机房、阿里云五星级机房）；私有云由客户私有云机房承担。平台侧不直接落地物理访问控制，但通过 L0.1-L0.4 资源供应模块在纳管机器时要求客户声明机房合规等级，并在运营后台（L5.2）记录机房合规信息作为测评材料输入。

#### 1.1.2 防盗窃和防破坏

- **标准要求**：主要设备的摆放应固定，并设置明显的不易除去的标记；媒体（磁盘/磁带）应分类标识、存储在安全环境，并定期检查；应对重要设备进行备份，并异地存放。
- **平台适用性分析**：物理设备防盗窃防破坏由部署环境方负责。平台侧通过 L2.1 统一存储底座（对象存储 + Iceberg 表格式）实现数据级防破坏：对象存储启用多副本（Ceph RGW 三副本 / 云对象存储跨 AZ 复制）；Iceberg 表启用快照与版本化，支持数据误删恢复；L3.7 数据安全模块对核心数据启用 WORM（一次写入不可修改）存储，防篡改。备份异地存放由 L3.7 数据备份恢复策略落地（详见 1.5.3）。

#### 1.1.3 防雷击

- **标准要求**：机房建筑应设置避雷装置；机房内应设置等电位连接地；应采用浪涌保护器防止雷击过电压。
- **平台适用性分析**：由机房方负责，平台不直接落地。公有云/私有云环境由云厂商机房防雷体系承担；信创/本地环境由客户机房防雷设施承担。平台侧不涉及。

#### 1.1.4 防火

- **标准要求**：机房应设置火灾自动消防系统，能自动检测火情、自动报警、自动灭火；机房内的材料应采用阻燃材料。
- **平台适用性分析**：由机房方负责，平台不直接落地。同 1.1.3，由部署环境方机房消防体系承担。

#### 1.1.5 防水

- **标准要求**：机房应设置防水设施，防止水浸；机房应安装对水敏感的检测报警装置，并能在水浸时及时报警。
- **平台适用性分析**：由机房方负责，平台不直接落地。同 1.1.3。

#### 1.1.6 防静电

- **标准要求**：机房应采用防静电地板；机房内应采取防静电措施，如接地、温湿度控制等。
- **平台适用性分析**：由机房方负责，平台不直接落地。同 1.1.3。

#### 1.1.7 温湿度控制

- **标准要求**：机房应配备精密空调，温度保持在 18℃-28℃，相对湿度保持在 40%-70%。
- **平台适用性分析**：由机房方负责，平台不直接落地。同 1.1.3。平台侧通过 L0.9 可观测基座（Prometheus + Node Exporter）采集节点机箱内温度指标，作为机房环境合规的辅助监控信号，异常时告警通知运维方。

#### 1.1.8 电力供应

- **标准要求**：机房应提供可靠的电力供应，配备 UPS 和备用发电机；应设置冗余或并路电力线路。
- **平台适用性分析**：由机房方负责，平台不直接落地。同 1.1.3。平台侧通过 L0.9 可观测基座采集节点 UPS 状态、市电状态指标（如 IPMI 传感器），作为机房电力合规的辅助监控信号。

### 1.2 网络安全

#### 1.2.1 网络结构安全

- **标准要求**：应划分网络区域，重要区域与其他区域隔离；应采用 VLAN、防火墙等技术进行区域隔离；网络边界应配置访问控制设备；应避免将重要网段暴露在边界外。
- **平台适用性分析**：平台通过 L0.7 容器网络（Cilium 1.15 + NetworkPolicy）实现 K8s 集群内网络区域隔离：系统 Namespace（kube-system / sq-system / sq-monitor）与租户 Namespace（sq-tenant-*）通过 NetworkPolicy 默认拒绝跨域访问；租户间通过 Cilium NetworkPolicy 强隔离，仅允许经 X4 APISIX 网关的南北向流量；对外仅暴露 APISIX 入口（80/443），其余端口默认不对外。跨集群通信经 L0.16 多集群联邦控制面（Karmada）建立加密隧道。网络结构安全由 L0.7 + L0.11 封装层 + X4 APISIX 共同落地。

#### 1.2.2 网络访问控制

- **标准要求**：应在网络边界部署访问控制设备，启用访问控制策略；应对进出网络的数据流进行过滤；应对源地址、目的地址、源端口、目的端口、协议进行检查；应禁止远程拨号访问。
- **平台适用性分析**：平台通过 X4 APISIX 3.9 网关在网络边界落地访问控制：APISIX 启用 jwt-auth 插件校验请求 JWT Token，未通过鉴权的请求拒绝；启用 ip-restriction 插件配置租户 IP 白名单；启用 cors 插件限制跨域来源；启用 ua-restriction 插件过滤恶意 User-Agent。L0.7 Cilium 在集群内落地 NetworkPolicy，按 Namespace/Selector 限制 Pod 间访问。出口流量经 L0.11 封装层出口白名单控制，默认仅允许访问必要的外部依赖（如镜像仓库、客户 IdP）。远程拨号访问在平台架构中不存在。

#### 1.2.3 网络入侵防范

- **标准要求**：应在网络边界处监视网络攻击行为，能检测到端口扫描、强力攻击、网络蠕虫、网络僵尸网络、缓冲区溢出、恶意代码等攻击；应能及时告警并自动采取阻断措施。
- **平台适用性分析**：平台通过 X2 安全合规模块落地入侵防范：信创环境部署国产 HIDS Agent（如青藤云 HIDS）+ 国产 WAF；非信创环境部署 Falco（容器行为监控）+ Suricata（网络 IDS）+ 可选 WAF。APISIX 网关启用 limit-req 插件防暴力破解（按 IP + URI 限速）、limit-count 插件防端口扫描。检测到入侵行为后告警接入 L0.9 可观测基座（Alertmanager），并联动 APISIX 动态封禁源 IP。入侵特征规则定期更新。

#### 1.2.4 恶意代码防范

- **标准要求**：应在网络边界处对恶意代码进行检测和清除；应支持恶意代码库的统一管理和自动更新。
- **平台适用性分析**：平台通过 L0.11 封装层 + X2 安全合规落地恶意代码防范：所有容器镜像经 Trivy（非信创）/ 国产镜像扫描（信创，如 Anchore 国产替代）扫描后才允许准入（L0.11 启用镜像签名准入，cosign / 国密签名）；APISIX 网关对接病毒墙对上传文件扫描；恶意代码特征库统一管理并定期自动更新。检测到恶意代码的镜像/文件拒绝准入并告警。

#### 1.2.5 安全审计

- **标准要求**：应对网络访问、网络流量、网络攻击等行为进行审计记录；审计记录应包含事件日期、时间、发起者、事件类型、事件结果等；审计记录应保存至少 6 个月；应保护审计记录，避免受到未预期的删除、修改或覆盖。
- **平台适用性分析**：平台通过 X2 安全合规模块的统一审计中心落地网络审计：APISIX access log + Cilium flow log + Falco 告警事件经 FluentBit 采集 → Kafka 缓冲 → 安全合规专用 Elasticsearch（非信创）/ 国产日志存储（信创）存储。审计记录包含时间戳、源/目的 IP、端口、协议、用户、动作、结果等字段，保留 180 天（≥ 6 个月）。审计日志写入 WORM（一次写入不可修改）存储，防篡改。审计查询经 `/api/compliance/v1/audit/logs` 接口，需鉴权 + 审批。

#### 1.2.6 边界完整性检查

- **标准要求**：应保证网络边界的完整性，能够检测到非授权设备私自接入网络的行为；应能够自动阻断非授权设备的接入。
- **平台适用性分析**：平台通过 L0.7 Cilium + L0.6 SKE 控制面落地边界完整性：K8s 集群启用节点准入控制（TLS Bootstrap + CSR 审批），非授权节点无法加入集群；Cilium 配置 host-firewall 规则，检测非授权 Pod/进程对外访问；APISIX 网关作为唯一南北向入口，非经网关的对外流量被 NetworkPolicy 默认拒绝。检测到非授权接入时告警接入 Alertmanager，并联动 Cilium 动态阻断。

#### 1.2.7 网络设备防护

- **标准要求**：应对网络设备的管理员登录进行身份鉴别；应限制网络设备的管理方式（如仅允许 SSH/HTTPS）；应记录网络设备的管理操作；应定期备份网络设备配置。
- **平台适用性分析**：平台网络设备主要是 K8s 控制面（L0.6 SKE）+ Cilium（L0.7）+ APISIX（X4）。管理操作经 X1 Keycloak 统一鉴权（OIDC Token + RBAC），管理员身份经多 IdP 联邦登录（信创统一身份 / LDAP / 账号密码）；管理通道强制 HTTPS/TLCP（信创）/ HTTPS（非信创），禁用 HTTP/Telnet；管理操作经 X2 审计中心留痕；网络设备配置经 L0.15 GitOps 控制器（ArgoCD）版本化在 Git 仓库，配置变更自动同步 + 漂移检测 + 回滚，等效"定期备份配置"。

### 1.3 主机安全

#### 1.3.1 身份鉴别

- **标准要求**：应对登录操作系统的用户进行身份鉴别；应对用户标识唯一；应对用户身份鉴别的信息进行保护；应提供双因素认证；应对登录失败进行处理（如限制登录次数、结束会话）。
- **平台适用性分析**：平台主机主要是 K8s 节点（L0.6 SKE 节点）。节点 SSH 登录经 X1 Keycloak 颁发的证书或 LDAP 账号鉴别；信创环境对接信创统一身份认证（含 SM2 证书登录，等效双因素）；非信创环境对接 LDAP/AD + 可选 OTP 双因素。登录失败次数经 SSH 配置（MaxAuthTries=3）+ fail2ban 限制并封禁源 IP。K8s API Server 访问经 X1 OIDC Token 鉴权，Token 短 TTL + 滚动 refresh + 撤销列表。用户标识唯一性由 Keycloak Realm 保证。

#### 1.3.2 自主访问控制

- **标准要求**：应实现操作系统自主访问控制，对文件、数据库表等客体进行权限管理；应限制用户对敏感客体的访问权限。
- **平台适用性分析**：K8s 节点操作系统经硬化脚本配置：文件权限按最小权限原则设置（如 /etc/shadow 0600 root）；SELinux/AppArmor（非信创）/ 国产 MAC（信创，如麒麟 SELinux 等效）启用强制访问控制。K8s 层 RBAC 控制 Pod/Service/ConfigMap 等资源访问，权限粒度到 Namespace + Resource + Verb。容器内文件权限经 PodSecurity Standards（Restricted 策略）约束，禁止以 root 运行、禁止特权模式。

#### 1.3.3 安全标记

- **标准要求**：应对重要信息资源设置安全标记；应根据安全标记控制主体对客体的访问。
- **平台适用性分析**：平台通过 L3.7 数据安全模块落地安全标记：数据资产按公开/内部/敏感/核心四级标注，标注作为安全标记存储在 L3.1 元数据管理（Catalog）中；X1 ABAC 层在运行时根据 Token claim（租户/项目/角色）+ 资源安全标记做访问判定，如"仅本部门 + 非密级数据"才允许访问。K8s 层通过 Namespace label + Pod label 作为安全标记，NetworkPolicy 据此控制 Pod 间访问。

#### 1.3.4 剩余信息保护

- **标准要求**：应保证操作系统和数据库系统用户的鉴别信息所在的存储空间（如硬盘、内存）被释放或再分配前得到完全清除；应保证存有敏感数据的存储空间被释放或再分配前得到完全清除。
- **平台适用性分析**：K8s Pod 销毁时，容器存储层（L0.8 CSI）的临时卷（emptyDir）随 Pod 删除自动清理；持久卷（PVC）按租户配置决定是否清理，敏感租户启用 PVC 删除时 shred（多次覆写）。内存敏感数据（如 Keycloak Token、KMS 密钥）在进程退出时由操作系统回收，关键凭据经 KMS 临时密钥加密使用，使用完即销毁。节点下线时经 L0.6 SKE 节点池管理执行磁盘擦除脚本（dd / shred）。

#### 1.3.5 入侵防范

- **标准要求**：应能够检测到对主机的入侵行为（如端口扫描、强力攻击、恶意代码、缓冲区溢出等）；应能及时告警；应能自动采取阻断措施（如封禁源 IP）。
- **平台适用性分析**：平台通过 X2 安全合规模块落地主机入侵防范：信创环境部署国产 HIDS Agent（如青藤云 HIDS），非信创环境部署 Falco（容器行为监控）+ Wazuh（主机 IDS）。HIDS/Falco 检测异常进程、异常文件变更、异常网络连接、提权行为等，告警接入 Alertmanager，并联动 APISIX/Cilium 动态阻断。入侵特征规则定期更新。

#### 1.3.6 恶意代码防范

- **标准要求**：应对主机进行恶意代码检测和清除；应支持恶意代码库的统一管理和自动更新；应对主机恶意代码检测策略进行统一管理。
- **平台适用性分析**：K8s 节点经 L0.6 SKE 节点镜像硬化（最小化基础镜像 + 安全补丁定期更新）；容器镜像经 Trivy/国产扫描在准入前检测恶意代码（详见 1.2.4）；节点 HIDS Agent 含恶意代码检测能力（如 rootkit 检测、可疑进程检测）。恶意代码库统一管理并定期自动更新。

#### 1.3.7 安全审计

- **标准要求**：应对主机登录、主机配置变更、主机进程启动、主机文件访问等行为进行审计记录；审计记录应保存至少 6 个月；应保护审计记录。
- **平台适用性分析**：K8s 节点经 auditd（Linux 内核审计）记录登录、配置变更、进程启动、文件访问等事件；K8s 控制面经 kube-apiserver audit log 记录 API 调用；审计日志经 FluentBit 采集到 X2 统一审计中心，保留 180 天（≥ 6 个月），WORM 存储防篡改。

#### 1.3.8 资源控制

- **标准要求**：应对主机的 CPU、内存、磁盘等资源使用进行限制；应对单个用户的资源使用进行限制；应能监控资源使用情况并在资源紧张时告警。
- **平台适用性分析**：K8s 通过 L0.12 弹性调度（HPA/KEDA/ResourceQuota/LimitRange）落地资源控制：每个 Namespace 配 ResourceQuota 限制 CPU/内存/Pod 数总量；每个 Pod 配 resources.requests/limits 限制单 Pod 资源；L0.9 可观测基座（Prometheus）采集资源使用指标，超过阈值经 Alertmanager 告警；L5.7 FinOps 看板提供租户/工作空间/任务维度的资源用量可视化与优化建议。

### 1.4 应用安全

#### 1.4.1 身份鉴别

- **标准要求**：应对登录应用系统的用户进行身份鉴别；应对用户标识唯一；应对鉴别信息进行保护（如加密存储、加密传输）；应提供双因素认证；应对登录失败进行处理。
- **平台适用性分析**：平台通过 X1 统一身份权限模块落地应用身份鉴别：所有应用入口（L5.1 控制台、L5.2 运营后台、CLI、IDE 插件、引擎作业提交）经 X1 Keycloak OIDC/OAuth2.1 鉴权，签发 RFC9068 JWT Token。用户标识唯一性由 Keycloak Realm 保证。鉴别信息保护：密码经 SM3+盐（信创）/ SHA-256+盐（非信创）存储；Token 签名经 SM2withSM3（信创）/ RS256（非信创）；传输层经 TLCP（信创）/ TLS1.3（非信创）加密。双因素：信创环境支持 SM2 证书登录（等效双因素）；非信创环境支持 OTP（TOTP）双因素。登录失败经 Keycloak Brute Force Protector 限制次数并临时锁定账号。

#### 1.4.2 访问控制

- **标准要求**：应实现应用自主访问控制，对功能、数据等客体进行权限管理；应限制用户对敏感功能的访问权限；应提供访问控制策略的统一管理。
- **平台适用性分析**：平台通过 X1 RBAC + ABAC 混合模型落地应用访问控制：RBAC 层级为租户 → 组织 → 项目 → 角色 → 权限（`module:resource:action`，如 `lake:table:write`、`dev:job:submit`），角色绑定到用户/用户组；ABAC 层以 Token claim + 资源属性做运行时判定，与 L3.7 数据安全行级权限联动。高敏感资源（如导出、跨租户访问）走 UMA 2.0 在线授权。访问控制策略经 X1 统一管理，业务模块零硬编码鉴权（鉴权逻辑收敛到 X4 网关 + Keycloak SPI）。

#### 1.4.3 安全标记

- **标准要求**：应对重要应用资源设置安全标记；应根据安全标记控制主体对客体的访问。
- **平台适用性分析**：同 1.3.3，应用层安全标记由 L3.7 数据安全模块落地，数据资产四级标注作为安全标记，X1 ABAC 层在运行时根据安全标记做访问判定。

#### 1.4.4 剩余信息保护

- **标准要求**：应保证应用用户的鉴别信息所在的存储空间被释放或再分配前得到完全清除；应保证存有敏感数据的存储空间被释放或再分配前得到完全清除。
- **平台适用性分析**：应用层敏感数据（如 Token、凭据、临时密钥）在内存中使用完即销毁（如 Keycloak Token 在会话结束即从 Infinispan 缓存清除）；持久化敏感数据（如数据库密码、API Key）经 KMS SM4/AES-GCM 加密存储，使用时解密到内存，使用完销毁。应用日志不记录敏感数据明文（如密码、Token 完整值），仅记录脱敏后的摘要。

#### 1.4.5 通信完整性

- **标准要求**：应采用密码技术保证通信过程中数据的完整性；应能检测到通信过程中的数据完整性被破坏。
- **平台适用性分析**：平台通信完整性由传输层保障：信创环境经 TLCP（基于 SM2/SM3/SM4 的国密 TLS）保证完整性与机密性；非信创环境经 TLS1.3（HMAC + AEAD）保证。Service Mesh（L0.13 Istio）启用 mTLS STRICT 模式，组件间通信强制 mTLS，Envoy sidecar 校验对端证书与消息完整性。检测到完整性被破坏（如 TLS 握手失败、MAC 校验失败）时连接被拒绝并告警。

#### 1.4.6 通信保密性

- **标准要求**：应采用密码技术保证通信过程中数据的保密性；应对敏感数据传输进行加密保护。
- **平台适用性分析**：同 1.4.5，传输层经 TLCP/TLS1.3 加密。敏感数据（如凭据、个人信息）在应用层额外经 SM4/AES-GCM 加密后再传输（双层加密）。KMS 凭据经 KMS API 传输，不落明文。

#### 1.4.7 抗抵赖

- **标准要求**：应具有在请求的情况下为数据原发者或数据接收者提供数据原发证据的功能；应具有在请求的情况下为数据原发者或数据接收者提供数据接收证据的功能。
- **平台适用性分析**：平台通过 X2 统一审计中心落地抗抵赖：所有关键操作（登录、配置变更、作业提交、数据访问、数据导出、审批）经审计留痕，记录主体（用户 ID + Token ID）、客体（资源 ID）、时间戳、操作类型、结果、来源 IP 等，写入 WORM 存储不可篡改，作为抗抵赖证据。数据导出等高敏感操作额外经 UMA 2.0 在线授权 + 二次审批，审批记录作为接收证据。审计日志可经 `/api/compliance/v1/audit/export` 导出作为测评材料。

#### 1.4.8 软件容错

- **标准要求**：应提供软件容错能力，能检测到软件故障并自动恢复；应能处理异常情况，避免软件崩溃。
- **平台适用性分析**：平台通过 K8s 原生容错能力落地软件容错：Pod 经 Deployment/StatefulSet 配置 liveness/readiness probe，故障自动重启；经 PodDisruptionBudget 限制自愿驱逐数量，保证最小可用副本；经 Service Mesh（L0.13 Istio）启用熔断（连续 5xx ≥ 5 触发熔断 30s）、重试（默认 3 次）、超时（按链路配置）防止级联故障；经 L0.12 弹性调度（HPA/KEDA）自动伸缩应对负载。应用层经 Spring Boot Actuator / FastAPI 健康端点暴露健康状态，异常时 K8s 自动隔离。

#### 1.4.9 资源控制

- **标准要求**：应对应用系统的会话、并发连接、资源使用进行限制；应能监控应用资源使用情况并在资源紧张时告警。
- **平台适用性分析**：应用层资源控制经 X4 APISIX 网关 + K8s 落地：APISIX 启用 limit-conn 插件限制单客户端并发连接数、limit-req 插件限制请求速率；会话超时经 Keycloak 配置（access token TTL 短 + refresh token TTL 长，闲置超时自动登出）；K8s ResourceQuota/LimitRange 限制应用 Pod 资源；L0.9 可观测基座监控应用资源使用，超过阈值告警。

#### 1.4.10 代码安全

- **标准要求**：应对应用代码进行安全审查；应采用安全编码规范；应对代码中的敏感信息（如硬编码密钥）进行检查；应对第三方组件进行漏洞扫描。
- **平台适用性分析**：平台通过工程规范落地代码安全：自研代码经 CodeArts 代码扫描（静态分析 + SAST）+ 单元测试 + Code Review 才允许合入；安全编码规范遵循 OWASP Top 10 / CWE Top 25 防护要求（如输入校验、参数化查询、输出编码、CSRF Token）；敏感信息经 KMS 管理，禁止硬编码，CI 流水线经 secret scanning 检测硬编码密钥；第三方依赖经 Trivy/Dependabot 定期漏洞扫描，CVE 高危依赖强制升级。镜像经 Trivy/国产扫描在准入前检测已知漏洞。

### 1.5 数据安全

#### 1.5.1 数据完整性

- **标准要求**：应采用密码技术保证数据在存储过程中的完整性；应能检测到数据在存储过程中完整性受到破坏；应采用密码技术保证数据在传输过程中的完整性。
- **平台适用性分析**：存储完整性由 L2.1 统一存储底座落地：对象存储（Ceph RGW / 云对象存储）启用多副本 + CRC32C 校验，副本损坏自动修复；Iceberg 表启用快照与版本化，每次写入生成新快照，旧快照保留可追溯，数据误删/篡改可经快照恢复；敏感数据经 SM3/SHA-256 摘要存储，校验时比对摘要。传输完整性同 1.4.5，经 TLCP/TLS1.3 保障。检测到完整性破坏时告警 + 自动恢复。

#### 1.5.2 数据保密性

- **标准要求**：应采用密码技术保证数据在存储过程中的保密性；应对敏感数据存储进行加密保护。
- **平台适用性分析**：平台通过 L3.7 数据安全 + X1 国密 CryptoSpiFactory 落地数据保密性：存储加密分两层——对象存储层经 L0.8 CSI 启用静态加密（SSE-S3 等效，信创用 SM4，非信创用 AES-256）；表数据层经 L3.7 列级加密，敏感列（如身份证号、手机号）经 SM4-CBC（信创）/ AES-GCM（非信创）加密存储，密钥经 KMS 管理（SM2 主密钥 + SM4 数据密钥，分级分层）。传输保密性同 1.4.6。

#### 1.5.3 数据备份恢复

- **标准要求**：应提供本地数据备份与恢复功能；应提供异地数据备份功能；应提供重要数据的冗余措施；应保证备份数据的完整性。
- **平台适用性分析**：平台通过 L3.7 数据备份恢复策略落地：本地备份——对象存储启用多副本（3 副本），Iceberg 表启用快照定期生成（按小时/天）；异地备份——对象存储跨集群/跨 AZ 复制（RPO 按租户配置，核心数据 RPO ≤ 1h），数据库（PostgreSQL/openGauss）经主从复制 + 异地日志归档；冗余措施——K8s StatefulSet 多副本，Keycloak/PostgreSQL 等关键组件多 AZ 部署；备份完整性——备份数据经 SM3/SHA-256 校验，定期演练恢复。备份策略经 L5.2 运营后台配置，备份状态经 X3 可观测看板监控。

#### 1.5.4 剩余数据保护

- **标准要求**：应保证鉴别信息所在的存储空间被释放或再分配前得到完全清除；应保证存有敏感数据的存储空间被释放或再分配前得到完全清除。
- **平台适用性分析**：同 1.3.4，剩余数据保护在主机层与应用层共同落地。数据层额外：Iceberg 表快照过期清理时，数据文件经 shred 多次覆写；对象存储删除对象时按租户配置决定是否 shred；KMS 临时数据密钥使用完即销毁，主密钥经 HSM 保护。

### 1.6 管理安全

#### 1.6.1 安全管理制度

- **标准要求**：应制定信息安全工作的总体方针和安全策略；应制定安全管理制度（如人员管理、机房管理、设备管理、介质管理、变更管理、应急预案等）；应定期审查和修订安全管理制度。
- **平台适用性分析**：平台交付物含《数据引擎大数据平台安全管理制度模板》，客户基于模板裁剪落地。平台侧通过 L5.2 运营后台提供"合规制度管理"页面，支持制度的发布、版本管理、定期审查提醒。安全策略（如密码策略、会话策略、审计策略）经 X1/X2 配置项落地，变更经 GitOps 版本化并审计留痕。

#### 1.6.2 安全管理机构

- **标准要求**：应设立信息安全管理机构；应配备安全管理负责人；应建立信息安全领导小组；应明确机构与人员的职责。
- **平台适用性分析**：由客户组织架构落地，平台不直接涉及。平台侧通过 X1 角色模型预置"安全管理员""合规审计员""租户管理员"等角色，对应等保要求的岗位职责分离。安全管理员负责平台安全配置（如策略、规则），合规审计员负责审计日志审查与合规报告导出，租户管理员负责本租户内用户/角色管理，职责分离经 RBAC 强制。

#### 1.6.3 安全管理人员

- **标准要求**：应对安全管理人员进行安全教育与培训；应对安全管理人员进行安全技能考核；应对安全管理人员进行安全背景审查。
- **平台适用性分析**：由客户人力资源落地，平台不直接涉及。平台交付物含《数据引擎大数据平台安全运维手册》《数据引擎大数据平台应急响应手册》，作为安全教育与培训材料。平台侧通过 L5.2 运营后台记录运维人员培训记录与考核结果，作为测评材料输入。

#### 1.6.4 安全建设管理

- **标准要求**：应在系统建设过程中进行安全方案设计；应在系统建设过程中进行安全工程实施；应在系统建设过程中进行安全测试与验收；应在系统上线前进行安全评审。
- **平台适用性分析**：平台建设过程遵循安全开发生命周期（SDL）：需求阶段——安全需求纳入 PRD（如本任务 T000-1）；设计阶段——安全设计纳入详细设计（如 X1/X2 详细设计）；开发阶段——安全编码规范 + CodeArts 静态扫描；测试阶段——安全测试用例 + 渗透测试；上线阶段——安全评审 + 等保测评。平台交付物含完整安全设计文档与测试报告，作为客户等保测评的输入材料。

#### 1.6.5 安全运维管理

- **标准要求**：应进行日常安全运维（如漏洞管理、补丁管理、变更管理、备份管理、应急响应）；应进行安全事件监测与处置；应定期进行安全评估。
- **平台适用性分析**：平台通过 X2 安全合规 + X3 统一运维观测 + L0.15 GitOps 落地安全运维：漏洞管理——镜像/依赖漏洞经 Trivy/国产扫描定期检测，高危漏洞工单跟踪修复；补丁管理——K8s 节点 OS 补丁经 L0.6 SKE 节点池滚动升级，组件补丁经 Helm Chart 版本升级；变更管理——所有变更经 GitOps 提交 Git，经审批后 ArgoCD 同步，漂移自动检测回滚；备份管理——同 1.5.3；应急响应——告警经 Alertmanager 路由到值班人员，应急预案在交付物中提供；安全事件监测——X2 审计中心 + HIDS/Falco 实时监测，事件经 SOAR（可选）自动处置；安全评估——平台提供等保自检报告（`/api/compliance/v1/report/level-protection`）与密评自检报告，定期生成。

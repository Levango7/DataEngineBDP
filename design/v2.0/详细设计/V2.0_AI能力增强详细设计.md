> 归属：数擎大数据平台 V2.0 · L4.5 智能数据层深化演进

### 1.3 设计原则

1. **封装一致性**：所有 AI 服务均为多租户 Pod，由 L0.11 封装层 Operator 托管，客户不持 K8s 权限。
2. **能力复用**：优先复用 V1.0 引擎层（Milvus/ES/NebulaGraph/IoTDB/Kafka/Redis）与 MLflow 底座，不重复造存储。
3. **多模态优先**：网关、RAG、助手均原生支持文本/图像/语音/视频多模态。
4. **可观测可计量**：所有 AI 调用经 X4 APISIX 采集指标，接入 L5.2 计量链路。
5. **租户隔离**：模型、知识库、Agent、评测任务、微调任务、助手会话均按租户隔离。

#### 2.3.2 Agent基类设计

```python
代码示例：Agent基类与内置Agent定义（Python）
from abc import ABC, abstractmethod
from typing import Any, Dict, List, Optional

class BaseAgent(ABC):
    """Agent基类，所有内置与自定义Agent继承此类"""
    agent_type: str
    tools: List[str]
    llm_model: str

    @abstractmethod
    async def run(self, input: Dict[str, Any], context: "AgentContext") -> Dict[str, Any]:
        """执行Agent逻辑，返回结构化结果"""

    @abstractmethod
    def plan(self, input: Dict[str, Any]) -> List["ActionStep"]:
        """规划执行步骤"""

class DataAnalysisAgent(BaseAgent):
    agent_type = "data_analysis"
    tools = ["sql_query", "stat_compute", "data_sample"]

class SQLGenerationAgent(BaseAgent):
    agent_type = "sql_generation"
    tools = ["schema_search", "sql_validate", "explain_plan"]
```

### 2.4 编排模式

#### 2.4.1 五种编排模式

| 模式 | 语义 | 典型场景 | LangGraph 映射 |
| --- | --- | --- | --- |
| 顺序编排 Sequential | Agent A → Agent B → Agent C | NL2SQL → 执行 → 解读 | add_edge 顺序连边 |
| 并行编排 Parallel | Agent A ∥ Agent B → 汇总 | 多维度同时分析后合并 | add_node(fan_out) + add_node(reduce) |
| 条件分支 Conditional | if cond → A else → B | 有权限走执行，无权限走申请 | add_conditional_edges |
| 循环 Loop | while cond: run(A) | 迭代优化SQL直至通过校验 | 自环边 + 条件终止 |
| 人工审批 Approval | run(A) → 人工审核 → run(B) | 高风险SQL需DBA审批后执行 | `interrupt` + `Command(resume=...)` 节点（`from langgraph.types import Command`，最小版本 LangGraph 0.6+） |

#### 2.4.2 工作流DSL示例

```yaml
配置：Agent工作流DSL定义（YAML）
workflow:
  name: "智能数据分析流"
  mode: "sequential_with_branch"
  nodes:
    - id: "nl2sql"
```

### 2.5 Agent通信机制

#### 2.5.1 消息队列通信

Agent 间异步通信通过 Kafka 实现，Topic 命名遵循租户隔离规范 `tenant.<tid>.agent.<workflow_id>.event.vN`。

| 通信场景 | 机制 | 说明 |
| --- | --- | --- |
| 同步编排内传递 | Redis 共享上下文 | 同一 workflow 内 Agent 共享 ContextManager 状态 |
| 跨工作流异步事件 | Kafka 消息 | 工作流完成事件通知下游工作流 |
| 人工审批通知 | Kafka + WebSocket | 审批节点产生事件，前端 WebSocket 推送待办 |
| Agent 状态变更 | Kafka 事件 | 状态机变更广播，供可观测采集 |

#### 2.5.2 共享上下文设计

```python
代码示例：Agent共享上下文管理（Python）
class AgentContext:
    """工作流共享上下文，基于Redis实现租户隔离"""
    def __init__(self, tenant_id: str, workflow_id: str):
        self.namespace = f"tenant:{tenant_id}:wf:{workflow_id}"
        self.redis: Redis  # 租户专属Redis连接

    async def set(self, key: str, value: Any, ttl: int = 3600):
        """写入上下文变量，TTL默认1小时"""
        await self.redis.setex(f"{self.namespace}:{key}", ttl, json.dumps(value))

    async def get(self, key: str) -> Any:
        """读取上下文变量"""

    async def append_message(self, agent_id: str, message: dict):
        """追加Agent消息到上下文历史"""
```

### 2.6 工具注册与执行沙箱

#### 2.6.1 ToolRegistry设计

ToolRegistry 统一管理所有 Agent 可调用的工具，支持静态注册与动态发现。

| 工具类别 | 内置工具 | 说明 |
| --- | --- | --- |
| SQL 类 | sql_query / sql_validate / explain_plan | 调用 L2.7 统一 SQL 网关 |
| 检索类 | vector_search / keyword_search / graph_search | 调用 L2.10 多模型引擎 |
| 绘图类 | echarts_render / matplotlib_plot | 生成图表配置 |
| HTTP 类 | http_get / http_post | 调用外部 API |
| 文件类 | file_read / file_write | 读写工作空间存储 |
| 治理类 | quality_check / lineage_query | 调用 L3 治理层 |

#### 2.6.2 执行沙箱

工具执行在受控沙箱中运行，防止恶意代码逃逸。

| 沙箱维度 | 机制 | 说明 |
| --- | --- | --- |
| 计算隔离 | gVisor / Kata Containers | 工具 Pod 运行在沙箱运行时 |
| 网络隔离 | NetworkPolicy | 仅放行白名单目标（SQL 网关/检索引擎） |
| 资源限制 | CPU/Memory/Timeout | 单工具调用默认 2C4G，超时 60s |
| 文件隔离 | tmpfs 临时挂载 | 工具仅可读写临时目录 |
| 权限隔离 | ServiceAccount 最小权限 | 工具 Pod 使用专用 SA，无集群资源操作权限 |

### 2.7 与DolphinScheduler集成

Agent 工作流作为 DolphinScheduler 的新任务类型 `AGENT_DAG` 接入，实现定时触发与依赖编排。

```mermaid
sequenceDiagram
    participant DS as DolphinScheduler
    participant AOE as Agent Orchestrator
    participant AGT as Agent池
    participant GW as L2.7 SQL网关

    DS->>AOE: 触发 AGENT_DAG 任务(workflow_id)
    AOE->>AOE: 加载工作流DSL
    AOE->>AGT: 调度首个Agent
    AGT->>GW: 调用SQL查询工具
    GW-->>AGT: 返回结果
    AGT-->>AOE: Agent完成
    AOE->>AOE: 推进状态图
    AOE->>AGT: 调度下一Agent
    AGT-->>AOE: 工作流完成
    AOE-->>DS: 回写任务状态
```

集成方案要点：
1. **任务类型扩展**：在 DolphinScheduler TaskPlugin 中注册 `AGENT_DAG` 类型，任务参数为 `workflow_id`。
2. **状态回写**：Agent Orchestrator 通过 DS API 回写任务实例状态（成功/失败/超时）。
3. **依赖编排**：Agent 工作流可作为 DS DAG 的一个节点，与其他任务类型（SQL/Shell/Spark）混合编排。
4. **定时触发**：复用 DS 的定时调度与依赖触发能力，无需在 Orchestrator 重复实现。

### 2.10 多租户隔离

| 隔离维度 | 机制 | 说明 |
| --- | --- | --- |
| 工作流隔离 | tenant_id 字段 + 查询过滤 | 工作流 DSL 按 tenant_id 隔离，租户仅可见自有工作流 |
| 执行隔离 | K8s Namespace + Pod 级隔离 | Agent 执行 Pod 运行在租户 Namespace，受 ResourceQuota 约束 |
| 上下文隔离 | Redis key 前缀 `tenant:<tid>:` | 共享上下文按租户 key 空间隔离 |
| 消息隔离 | Kafka Topic `tenant.<tid>.agent.*` | Agent 通信消息按租户 Topic 隔离 |
| 工具隔离 | 工具白名单按租户配置 | 租户管理员可禁用特定工具（如 http_post） |
| 审批隔离 | 审批人按租户角色域 | 审批待办仅推送给租户内角色 |

### 2.11 技术选型与版本

#### 2.11.1 编排框架对比

| 框架 | 优势 | 劣势 | 选型结论 |
| --- | --- | --- | --- |
| LangGraph | 状态图原生、循环/条件/中断支持完善、与 LangChain 生态融合 | 仅 Python、无内置多 Agent 通信 | ✅ 选用（编排核心） |

| LangChain | 0.3.x 最新 | Agent 与工具抽象 |

### 3.5 混合检索

#### 3.5.1 四路检索

V2.0 多模态 RAG 检索路设计为**向量 + 关键词 + 图谱 + 时序预聚合向量**四路。其中时序检索路采用"预聚合后入 Milvus 向量索引"方案，避免直接对 IoTDB 进行 NL2IoTDB 转换（IoTDB SQL 语法复杂，自然语言到时序 SQL 的转换不稳定）。

表：四路检索设计表

| 检索路 | 引擎 | 检索方式 | 召回策略 |
| --- | --- | --- | --- |
| 向量检索 | Milvus (V1.0 L2.10) | ANN 近似最近邻 | topK=20, HNSW 索引 |
| 关键词检索 | Elasticsearch (V1.0 L2.10) | BM25 + 分词 | topK=20, 中文 IK 分词 |
| 图谱检索 | NebulaGraph (V1.0 L2.10) | 实体/关系多跳 | 提取查询实体，2跳邻居 |
| 时序检索 | Milvus（时序预聚合向量） | ANN 近似最近邻 | IoTDB 时序数据预聚合后向量化入 Milvus 专 collection，按时间窗口+测点维度检索 |

**时序预聚合方案说明**：
- 离线阶段：定时任务（DolphinScheduler 调度）从 IoTDB 拉取时序数据，按时间窗口（如 1 小时/1 天）聚合（sum/avg/max/min/count），生成时序片段文本（如"2024-Q3 产品A 日销售额序列：[120, 135, ...]"），经 Embedding 向量化后写入 Milvus 专 collection `tenant_<tid>_timeseries`。
- 在线检索：用户提问"Q3 销售趋势"→ Query 理解识别时间条件与实体 → 向量检索 Milvus 时序 collection → 返回相关时序片段（含聚合值与时间窗口）→ 拼入 LLM 上下文生成解读。
- 该方案避免 NL2IoTDB 转换的不稳定性，复用 Milvus 向量检索能力，时序数据预聚合后语义清晰，LLM 可直接解读。
- 缺点：时序数据实时性受预聚合窗口限制（最新数据延迟 1 个窗口），V2.0 通过缩短聚合窗口（如 5 分钟）+ 增量更新缓解。

#### 3.5.2 检索融合

```python
代码示例：混合检索融合策略（Python）
class HybridRetriever:
    """四路混合检索器，支持加权融合与去重"""
    def __init__(self, weights: dict = None):
        self.weights = weights or {"vector": 0.4, "keyword": 0.3, "graph": 0.2, "timeseries": 0.1}
        self.retrievers = {
            "vector": MilvusRetriever(),
            "keyword": ESRetriever(),
            "graph": NebulaGraphRetriever(),
            "timeseries": IoTDBRetriever(),
        }

    async def retrieve(self, query: str, top_k: int = 20) -> list:
        results = {}
        for name, retriever in self.retrievers.items():
            try:
                hits = await retriever.search(query, top_k=top_k)
                results[name] = self._normalize(hits)
            except Exception:
                results[name] = []  # 单路失败不影响整体
        return self._fuse(results, top_k)

    def _fuse(self, results: dict, top_k: int) -> list:
        """加权融合 + 去重"""
        fused = {}
        for name, hits in results.items():
            w = self.weights[name]
            for hit in hits:
                key = hit.chunk_id
                score = fused.get(key, 0) + w * hit.score
                fused[key] = max(fused.get(key, 0), score)
        return sorted(fused.items(), key=lambda x: -x[1])[:top_k]
```

#### 3.6.2 MMR多样性重排

Maximal Marginal Relevance 算法在相关性与多样性间平衡，避免返回高度相似的 chunk。

```python
代码示例：MMR多样性重排（Python）
def mm_rerank(query_vec, chunk_vecs, lambda_: float = 0.7, top_k: int = 10):
    """MMR：兼顾相关性与多样性"""
    selected = []
    candidates = list(range(len(chunk_vecs)))
    for _ in range(top_k):
        scores = []
        for i in candidates:
            rel = cosine(query_vec, chunk_vecs[i])
            div = max([cosine(chunk_vecs[i], chunk_vecs[j]) for j in selected], default=0)
            mmr = lambda_ * rel - (1 - lambda_) * div
            scores.append((i, mmr))
        best = max(scores, key=lambda x: x[1])[0]
        selected.append(best)
        candidates.remove(best)
    return selected
```

- V1.0 architecture.md 仅说"Milvus（向量）"未明确版本，V1.0 platform/vector-engine/README.md 也未指定版本。

**Milvus 2.3 → 2.4 升级影响评估**：

**V1.0 vector-engine Go SDK 升级路径**：
- V1.0 vector-engine 使用 milvus-sdk-go v2.3.x，V2.0 升级到 v2.4.x。
- 升级方式：`go get github.com/milvus-io/milvus-sdk-go/v2@v2.4.0`，API 向后兼容，V1.0 代码无需改动（仅新增方法如多向量字段支持）。
- V2.0 多模态 RAG 新增多向量字段 API 调用（`InsertMultiVector`），V1.0 单向量字段 API（`InsertVector`）继续可用。

**升级风险与缓解**：
- **风险**：Milvus 2.4 引入 SCANN/GPU 加速索引为新增能力，不影响 V1.0 现有索引；Collection schema API 新增 properties 参数为可选，V1.0 代码不传仍可用。
- **缓解**：V2.0 升级前在 staging 环境验证 V1.0 collection 在 2.4 的读写兼容性；升级后 V1.0 vector-engine Go SDK 同步升级到 v2.4.x，V1.0 代码无改动。
- **回滚方案**：若升级失败，Milvus 2.4 collection 元数据可降级回 2.3（删除 2.4 新增元数据字段），vector-engine Go SDK 回退到 v2.3.x。

### 4.5 模型路由

#### 4.5.1 按模态路由

```python
代码示例：多模态模型路由器（Python）
class ModalityRouter:
    """按输入模态路由到不同模型"""
    ROUTING_TABLE = {
        "text": {"default": "qwen-max", "fallback": "qwen-plus"},
        "image_understanding": {"default": "cogvlm-17b", "fallback": "gpt-4v"},
        "asr": {"default": "paraformer-large", "fallback": "whisper-large"},
        "tts": {"default": "cosyvoice", "fallback": "tongyi-tts"},
        "image_generation": {"default": "sdxl", "fallback": "cogview-3"},
    }

    def route(self, modality: str, tenant_config: dict = None) -> str:
        table = tenant_config or self.ROUTING_TABLE
        entry = table.get(modality, table["text"])
        return entry["default"]
```

#### 4.5.2 路由策略

| 策略 | 说明 |
| --- | --- |
| 模态优先 | 按输入模态选择模型族 |
| 租户配置覆盖 | 租户可覆盖默认路由表，指定自有模型 |
| 健康度降级 | 主模型不可用时自动 fallback |
| 负载均衡 | 同模型多副本按权重/健康度分发 |
| 成本优化 | 低复杂度请求路由到小模型，降低成本 |

```python
class MultimodalAdapter(ABC):
    """多模态模型适配器基类，统一各厂商多模态API差异"""
    @abstractmethod
    async def chat(self, messages: list, modality: str, stream: bool = False):

    @abstractmethod
    def parse_request(self, unified_req: dict) -> dict:
        """将统一请求转换为厂商特定格式"""

    @abstractmethod
    def parse_response(self, vendor_resp: dict) -> dict:
        """将厂商响应转换为统一格式"""

class OpenAIAdapter(MultimodalAdapter):

class ParaformerAdapter(MultimodalAdapter):
```

**多模态网关选用 Go 的理由**：
1. **V1.0 演进复用**：V2.0 多模态网关演进自 V1.0 llm-gateway（Go 实现），复用 V1.0 适配器框架、Token 计量、JWT 鉴权、限流等基础设施，避免重写。
2. **高并发低延迟**：Go goroutine + channel 模型适合多模态网关高并发 SSE 流式响应场景（每请求一 goroutine，轻量上下文切换），相比 Java/Python 内存占用更低、GC 停顿更短。
3. **gRPC 原生支持**：多模态网关与 vector-engine（Go）、Catalog（Go）等 V1.0 Go 组件通过 gRPC 高效通信，protobuf 跨语言兼容。
4. **镜像精简**：Go 静态编译 + multi-stage build 产出 ~20MB 镜像，适合 Knative 冷启场景（镜像拉取快）。

**Go 版本统一说明**：
- V2.0 多模态网关统一基线为 **Go 1.22**（V2.0 跨文件协调标准）。
- V1.0 llm-gateway README 标注 Go 1.23、go.mod 标注 Go 1.25.0，存在 V1.0 内部版本漂移。V2.0 建议 V1.0 llm-gateway 同步对齐到 Go 1.22 基线（属 V1.0 已知问题，不阻塞 V2.0 开发；V2.0 多模态网关演进时统一基线为 Go 1.22）。
- Go 1.22 相比 1.21 新增 range-over-func、loopvar 语义修正等特性，满足多模态网关需求；Go 1.23/1.25 新特性（如 iterator）非必需，统一为 1.22 避免构建矩阵混乱。

**自托管多模态模型 GPU 资源需求矩阵（B-09 修复）**：

§4.7.2 适配器矩阵"自托管"行覆盖 Qwen/CogVLM/SDXL/Whisper/CosyVoice 五个模型，按模态路由到不同自托管模型，各模型 GPU 资源需求与节点池规划如下：

表：自托管多模态模型 GPU 资源需求表（模型 × 显存 × QPS × 节点池规格）

| 模型 | 模态 | 参数规模 | 推理最小显存 | 推荐 GPU 型号 | 单卡 QPS | 节点池规格 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Qwen-7B-Chat | 文本 | 7B | 16 GB | A10 24G / 昇腾 910B 32G | 20-30 req/s | 2 卡/节点 × N 节点 | 文本对话主力，可量化降显存 |
| CogVLM-17B | 图像理解 | 17B | 40 GB | A100 40G / 昇腾 910B 64G | 5-10 req/s | 1 卡/节点 × N 节点 | 图像理解，FP16 推理 |
| SDXL-1.0 | 图像生成 | 6.6B | 24 GB | A10 24G / A100 40G | 2-5 img/s | 1 卡/节点 × N 节点 | 图像生成，可量化到 12GB |
| Whisper-large | 语音识别(ASR) | 1.5B | 8 GB | A10 24G / 昇腾 910B 32G | 5-10 audio/s | 1 卡/节点 × N 节点 | 语音识别，可 CPU 推理但 GPU 加速 |
| CosyVoice | 语音合成(TTS) | 7B | 16 GB | A10 24G / 昇腾 910B 32G | 10-20 audio/s | 1 卡/节点 × N 节点 | 语音合成，流式推理 |

**节点池规划原则**：
1. **按模态分池**：文本/图像理解/图像生成/ASR/TTS 各自独立 GPU 节点池，避免资源争抢，按模态路由到对应节点池。
2. **信创适配**：昇腾 910B 32G 适配 Qwen/Whisper/CosyVoice（显存足够），昇腾 910B 64G 适配 CogVLM-17B；SDXL 在昇腾上需验证 torch_npu 兼容性，不保证 V2.0-alpha 支持。
3. **弹性伸缩**：各节点池按 QPS 自动伸缩（KEDA + Knative），低峰缩到 0，高峰按预置比例扩容。
4. **多租户隔离**：节点池按租户配额隔离，避免单租户耗尽 GPU 资源；通过 `nvidia.com/gpu` 或 `npu.com/npu` 资源配额限制。

### 5.3 评测维度

#### 5.3.1 六维评测指标

| 维度 | 指标 | 计算方式 | 说明 |
| --- | --- | --- | --- |
| 准确性 | 准确率 Accuracy | 正确数/总数 | 与标准答案比对 |
| 准确性 | 召回率 Recall | TP/(TP+FN) | 信息检索场景 |
| 准确性 | F1 Score | 2*P*R/(P+R) | 精确率与召回率调和均值 |
| 性能 | 延迟 P50/P99 | 百分位延迟 | 单次请求耗时分布 |
| 性能 | 吞吐 QPS | 请求数/秒 | 并发压力测试 |
| 成本 | Token 费用 | Σ(token_count × unit_price) | 按模型定价计算 |
| 安全 | 幻觉率 Hallucination | 幻觉数/总数 | 事实一致性校验 |
| 安全 | 毒性 Toxicity | 毒性检测分 | 内容安全评分 |

#### 5.3.2 评测指标计算

```python
代码示例：评测指标计算器（Python）
class EvalMetricsCalculator:
    """多维度评测指标计算"""
    def compute_accuracy(self, predictions: list, references: list) -> float:
        correct = sum(p == r for p, r in zip(predictions, references))
        return correct / len(predictions)

    def compute_f1(self, predictions: list, references: list) -> dict:
        precision = self._precision(predictions, references)
        recall = self._recall(predictions, references)
        f1 = 2 * precision * recall / (precision + recall) if (precision + recall) > 0 else 0
        return {"precision": precision, "recall": recall, "f1": f1}

    def compute_latency(self, latencies_ms: list) -> dict:
        sorted_l = sorted(latencies_ms)
        return {
            "p50": sorted_l[len(sorted_l) // 2],
            "p99": sorted_l[int(len(sorted_l) * 0.99)],
            "avg": sum(sorted_l) / len(sorted_l),
        }

    def compute_cost(self, token_usages: list, pricing: dict) -> float:
        return sum(u["prompt_tokens"] * pricing["input"] +
                   u["completion_tokens"] * pricing["output"]
                   for u in token_usages)
```

**昇腾 910B 适配路径**（信创主推）：
- 基础环境：CANN 7.0+ + torch_npu 2.1+ + Python 3.9+
- LLaMA-Factory：使用 V2.0 维护的 fork 分支（`LLaMA-Factory-npu`），将 `torch.cuda` 调用替换为 `torch.npu`

#### 6.5.2 任务排队与调度

```python
代码示例：GPU资源调度器（Python）
class GPUResourceScheduler:
    """GPU资源池调度器，支持优先级队列与弹性伸缩"""
    def submit(self, job: FineTuningJob) -> str:
        """提交微调任务到优先级队列"""
        quota = self._check_quota(job.tenant_id, job.gpu_count)
        if not quota.ok:
            raise QuotaExceededError(quota.message)
        return self.queue.put(job, priority=job.priority)

    def schedule(self) -> list:
        """调度就绪任务到GPU节点"""
        runnable = []
        for job in self.queue.peek_by_priority():
            nodes = self.node_pool.find_available(job.gpu_type, job.gpu_count)
            if nodes:
                self.queue.pop(job.id)
                runnable.append((job, nodes))
        return runnable
```

```python
代码示例：NL2SQL安全校验（Python）
class SQLSecurityValidator:
    """NL2SQL生成SQL的安全校验"""
    FORBIDDEN_KEYWORDS = {"DROP", "DELETE", "UPDATE", "INSERT", "ALTER", "TRUNCATE"}
    MAX_LIMIT = 1000

    def validate(self, sql: str, user_perms: set) -> ValidationResult:
        ast = self.parser.parse(sql)
        if not self._is_select_only(ast):
            return ValidationResult(ok=False, reason="仅允许SELECT")
        if self._has_forbidden(ast):
            return ValidationResult(ok=False, reason="包含禁止操作")
        if not self._check_table_perms(ast, user_perms):
            return ValidationResult(ok=False, reason="表权限不足")
        sql = self._ensure_limit(ast, self.MAX_LIMIT)
        return ValidationResult(ok=True, sanitized_sql=sql)
```

### 7.8 与SQL网关集成

| 集成点 | V1.0 SQL 网关 | V2.0 集成方式 |
| --- | --- | --- |
| SQL 执行 | L2.7 统一 SQL 网关 | NL2SQL 生成的 SQL 提交至 SQL 网关执行 |
| 引擎路由 | ANTLR4 + Calcite 联邦优化 | 复用，NL2SQL 不感知引擎选择 |
| 权限校验 | SQL 网关行级权限 | NL2SQL 生成的 SQL 经网关权限校验 |
| Schema 检索 | 资产目录元数据 | NL2SQL Schema 检索调用 L3.5 资产目录 |
| 结果归并 | 跨源结果归并 | 复用，多源查询结果统一归并 |

完整链路：`NL2SQL → SQL 网关（ANTLR4 解析 → Calcite 优化 → 引擎路由）→ 引擎执行 → 结果归并 → 智能解读 → 图表推荐`

## 第10章 风险与对策

### 10.1 技术风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Agent 工作流死循环 | 资源耗尽 | 循环次数上限 + 超时熔断 + 单次执行 Token 上限 |
| NL2SQL 生成危险 SQL | 数据泄露/破坏 | 只读强制 + 表权限校验 + 人工确认高风险查询 |
| 多模态检索精度不足 | RAG 召回质量差 | 四路混合检索 + Cross-Encoder 重排 + MMR 多样性 |
| GPU 资源争抢 | 微调/推理互饿 | GPU 节点池租约隔离 + 优先级队列 + 配额上限 |
| 微调过拟合 | 模型泛化下降 | 验证集早停 + 评测门禁 + 对比基座模型 |
| 多模态模型延迟高 | 用户体验差 | 流式响应 + 模型路由降级 + 缓存 |
| 对话上下文丢失 | 多轮分析断续 | Redis 持久化上下文 + 会话恢复 |

### 10.2 安全风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Agent 工具逃逸 | 沙箱突破 | gVisor 隔离 + NetworkPolicy + 最小权限 SA |
| Prompt 注入 | 恶意指令注入 | 输入消毒 + 系统 Prompt 隔离 + 输出过滤 |
| 多模态内容安全 | 有害图像/语音 | 内容安全检测 + 毒性过滤 + 审计日志 |
| 模型泄露 | 微调模型被窃取 | 模型加密存储 + 端点鉴权 + 访问审计 |
| 跨租户数据泄露 | 租户隔离突破 | tenant_id 强制过滤 + 索引隔离 + 网络隔离 |

### 10.3 成本风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| LLM 调用成本失控 | 费用超支 | Token 配额 + 模型路由降级 + 缓存 + 按租户计费 |
| GPU 资源闲置 | 资源浪费 | 弹性伸缩 + 低优先级任务填充 + Spot 节点 |
| 向量索引膨胀 | 存储成本高 | 增量索引 + 冷热分层 + 索引压缩 |
